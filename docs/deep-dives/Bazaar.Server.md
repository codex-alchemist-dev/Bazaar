## 1. Product Identity

- **[DECIDED]** Philosophy: **"Run the company."** The living organism. All real compute happens here: Git, Godot/engine headless ops, all agent logic, OmniRoute, DB, and every agent's VM/environment (see **Bazaar.Soul**). Runs on your NUC as a headless service — **[DECIDED 2026-10-24]** one OS-agnostic .NET build that runs on Windows or Linux, with every OS-specific piece (service host, VM backend, cache, search) behind a provider interface. First supported and tested host: Windows. This refines the 2026-08-07 "Bazaar.Server.Windows for now" note, which scoped the first platform, not the architecture. If nobody connects for 48 hours, the company should still be functioning — discussing, researching, reviewing, planning.
- **[DECIDED]** No web *client*, ever, on any client. **[DECIDED 2026-10-24, owner — clarification]** The server may serve a small **read-only status page** (health, agents online, queue depth) for easy browser checks; it never shows chat, code or Vault content. Bind and enable rules are OPEN. **[DECIDED 2026-10-24, owner]** An interactive sign-in page (for example passkeys) is also allowed as a narrow exception to sign the owner in from a new device. **[DECIDED 2026-10-25, owner — DECISIONS-LOG round 11, C42]** Its scope is three routes only (sign-in, pairing approval, recovery), it is off by default, and it shows no content (no chat, code or Vault content). It is separate from the status page. **Server does everything** — Windows/Android/Linux are thin-but-rich renderers over WebSocket state sync, except for the client-side exceptions the owner ratified (DECIDED 2026-10-25, DECISIONS-LOG round 4, C17): NPU inference on the device (summaries, voice cleanup, prompt rewrite), the human's local terminal, the Roblox Studio bridge relay, and syncing your currently-viewed branch to a local folder for live playtesting. Layout stays server-side. **[DECIDED 2026-10-25, owner — C31]** Bazaar.Server and Bazaar.Windows are completely separate apps: the server gives each agent its own terminals inside its VMs (streamed by the server), while Bazaar.Windows' terminal is a built-in replacement for Windows Terminal running locally. *Origin (owner, ChatGPT conversation): a web interface "wont be a thing" because the clients must be native and meet minimum hardware specs, since being a client means being able to develop on that machine. **[DECIDED 2026-10-24, owner — clarification]** The rule concerns browser-based clients of the server, not native clients that embed components such as Monaco in a WebView.*

## 2. GitHub & Community Presence Architecture

*(Superseded from an earlier "machine accounts" plan — corrected after research.)*

- **[DECIDED — corrected]** **Machine accounts are a dead end.** GitHub's ToS caps one free machine account per person/legal entity, no paid path to buy more — confirmed, no account-level workaround exists.
- **[DECIDED]** **The real answer: GitHub Apps, not accounts.** A GitHub App is an application *registration*, not a user account — create as many for free as you want, all owned by the `codex-alchemist-dev` org. Plan: one App per agent (`claude-bazaar[bot]`, `deepseek-bazaar[bot]`, `gemi-bazaar[bot]`, `chatgpt-bazaar[bot]`), each with its own name, avatar, description — genuinely distinct identities, disclosed as bots via GitHub's own `[bot]` suffix.
- **[DECIDED]** Install the App(s) on the **org** — gives write access to org-owned repos (where forks live), and combined with GitHub's baseline public-repo read access, unlocks the standard **fork-and-PR flow on any public repo**: fork into the org, push a branch, open a PR against upstream. No installation on the upstream repo required — same mechanism any human contributor uses. **[DECIDED 2026-10-25, owner — DECISIONS-LOG round 3, C13]** Kept as decided. *Risk noted once: GitHub's docs say the App must be installed on the source repo, so this may not work; spike S22 is the cheap way to find out, and if the GitHub API refuses, the feature degrades to repos where the App is installed.*
- **[RESEARCHED — unverified]** One community-confirmed report suggests a GitHub App's installation token can open *issues* directly on a public repo it was never installed on, since public-repo writes for issues may follow the same "no special permission needed" rule as public reads. Not primary documentation. **Action item: test empirically on a throwaway low-stakes public repo before designing anything load-bearing around it.**
- **[DECIDED]** GitHub Apps have **no native email inbox or notification system** — user-account-only feature. Apps get **webhooks** instead (real-time HTTP events). Want the *feel* of "Claude got an email about GitHub activity"? Build it: webhook → Bazaar server → routed into the agent's GC and/or its configured-domain email inbox. Arguably better than native GitHub notifications since Bazaar decides how each agent experiences the event.
- **[DECIDED]** Git operations on the server (clone/fetch/branch/commit): **libgit2** via **LibGit2Sharp** (C# binding), not shelling out to the `git` CLI — structured, fast. **[DECIDED 2026-10-25, owner — DECISIONS-LOG round 3, C12]** Spike S23 comes first; LibGit2Sharp stays decided unless the spike shows it cannot do worktrees, merges or concurrency, and the engine hides behind one `IGitProvider` (CLI use is an alternative implementation, not the default). **[DECIDED 2026-10-25, owner — round 2, C05]** Git pushes run host-side so tokens never enter a VM.
- **[DECIDED]** Diff rendering for the custom GitHub interface reuses **Monaco's built-in diff-editor mode** (see Bazaar.Windows) rather than a separate component.

## 4. Backend language — decided: .NET

- **[DECIDED 2026-10-24]** .NET (C#) for the server and every client. Target **.NET 10 LTS** (supported until November 2028; .NET 8 LTS and .NET 9 STS end November 2026) **[RESEARCHED, primary source]**. One language across server and clients, one shared contracts project, LibGit2Sharp for Git, Npgsql for PostgreSQL, Hyper-V management through WMI/PowerShell, Avalonia for UI.
- **Hosting [RESEARCHED]:** Worker Service with `AddWindowsService()` on Windows (systemd on Linux — standard .NET pattern, not re-verified). Keep mutable data under `%ProgramData%`. A hard kill can skip `StopAsync`, so in-flight agent turns must persist their own state. Crash-restart recovery settings still need verification.
- **Transport [RESEARCHED]:** raw ASP.NET Core WebSockets; SignalR is the fallback; gRPC is not recommended for v1.
- **Admin console:** none inside the service process. Use a CLI or the Avalonia client over the same API. Terminal.Gui v2 is viable as a *separate* TUI client attached over the WebSocket API. Whether to build a TUI client at all is an **[OPEN]** question for the owner.
- **Background work [RESEARCHED]:** `BackgroundService` plus durable Postgres tables; Quartz.NET if cron triggers are needed. Orleans (virtual actors, one per agent) is worth a one-agent spike. Native AOT: not for v1.
- **Considered and not chosen:** Bun, Go, Elixir/Phoenix (the BEAM supervision model fits agents well), and Rust. Rust offers no advantage here: the workload is I/O-bound on model APIs, VMs and Postgres, and Windows/Hyper-V management plus shared C# contracts favor .NET. Keep every boundary a process or protocol boundary so a non-.NET component can still be added later.
- **Exceptions:** code that must run *inside* an engine (Luau for Roblox Studio, GDScript or C# for Godot). Engine adapters are out-of-process and talk to the server over a protocol.

2. **Bazaar SDK — actual shape** — agreed in principle, no concrete API surface designed.
3. **CI/CD actual engine** — concept is clear (build+test on every push/PR, auto-ship on pass) but no implementation chosen: self-built minimal task-runner vs. an existing tool like Woodpecker.
4. **Repo internal folder structure** — the two-repo split (public/private) is decided; detailed internal layout of each, including the shared-UI project from Bazaar.Windows, is not finalized.
5. **Provider interfaces** — DECIDED direction (2026-10-24): define cache/pub-sub, search, VM-backend and service-host interfaces so one build runs on Windows and Linux. The interface shapes are OPEN. Garnet's StackExchange.Redis compatibility and Windows persistence still need a spike.
6. **Model supply policy** — **[DECIDED 2026-10-25, owner — DECISIONS-LOG round 4, C14]** the Claude lane uses both the owner's Anthropic API key (Haiku-heavy budget) and FreeLLMAPI free tokens, by availability; this supersedes the 2026-10-24 "API keys only" wording. Routing Pro/Max subscription credentials through a gateway is not permitted by Anthropic's current terms (primary source, fetched 2026-10-24). The NIM "~1,000 requests/day" figure has no source.
7. **Admin console** — superseded by item 10.
8. **Licence** — **[DECIDED direction 2026-10-24, owner]** AGPL-3.0 for the server and clients, Apache-2.0 for the SDK and contracts. DCO vs CLA is OPEN. Counsel review is required before the first public release (including the `pg_search` bundling question).
9. **Email subsystem** — **[DECIDED 2026-10-24]** domain-agnostic, with four supported back ends in v1: a built-in Bazaar mail client, generic IMAP/SMTP providers, Cloudflare Email Routing + an HTTPS sender (e.g. Resend), and a built-in SMTP/IMAP server. **[RESEARCHED]** A home-hosted mail server usually fails deliverability (port 25, PTR); document it as suited to a VPS. The built-in client's scope is OPEN.
10. **Server admin surface** — **[DECIDED 2026-10-24]** an admin panel inside the apps (Windows, Android, ...). A read-only browser status page is also allowed (see Section 1); a TUI status client is OPEN.
11. **Gateway (FreeLLMAPI)** — the owner routes most traffic through it and sources free tokens for cheap agents from it; the Claude member uses both the owner's Anthropic key and FreeLLMAPI's free tokens by availability (C14). Evaluation (2026-10-24): it documents no per-agent whitelist, calls itself personal-experimentation-only, and maps Claude names to its free pool; its provider-terms review is self-assessed. Owner decision (2026-10-24): FreeLLMAPI gets priority support and the gateway layer is pluggable per install; the Gemini lane follows the install's choice. Whitelist enforcement lives in Bazaar.Server's own gateway (DECIDED 2026-10-24).
12. **Free-tier data policy** — **[DECIDED 2026-10-24, owner]** operator's choice: the platform sets no rule on which data free-tier lanes may see. **[RESEARCHED]** Some free tiers use prompts to improve their products (for example Gemini's free tier), so setup shows a clear warning.
13. **Untrusted-input handling** — **[DECIDED 2026-10-24, owner]** taint tracking plus a human gate: the server tracks whether a session has seen untrusted input (email, strangers' issues, web), and once tainted, high-impact actions (post, send, spend, push to a repo) need the owner's approval. **[DECIDED 2026-10-25, owner — DECISIONS-LOG rounds 2 and 6, C06/C18]** External content taints a session hard; agent text taints softly and propagates only from a tainted source session; Tier 2 actions are gated on hard taint, with a fresh-session path using an approved summary. The reader/actor split ships in v1 for external input: reader sessions read untrusted content and hand over summaries, actor sessions never read it directly, and the approval gate applies to outward high-impact actions (posting, sending, spending, repo push/merge), not routine internal work. **[OPEN / FOLLOW-UP]** The owner's statement is that agents work independently with no human input for the daily workflow; Claude's reading that the reader/actor split is the mechanism is still to be confirmed. Approval tiers follow the ladder in doc 15 with stricter community defaults (C21).
14. **Claude lane escalation** — **[DECIDED 2026-10-24, owner]** automatic routing between Haiku and Sonnet; the routing rules, and whether Opus or Fable are ever used, are OPEN.
15. **Remote access** — **[DECIDED 2026-10-24, owner]** the operator's choice; the setup guide documents Tailscale, Headscale, WireGuard and Cloudflare Tunnel. Tailscale's free plan is for non-commercial use [RESEARCHED].
16. **Public posting approvals** — **[DECIDED 2026-10-24, owner]** operator-configured tiers: Bazaar ships a tier system with defaults and each operator sets thresholds per platform. CAPTCHA, phone, ID and passkey steps being human-only is a research recommendation, not yet decided.
17. **Privacy compliance** — **[DECIDED 2026-10-24, owner]** a Bazaar instance is normally one person's or one company's private workspace. When a company has several human members, Bazaar provides privacy-law compliance settings, global and not only the Philippines. **[DECIDED 2026-10-25, owner — DECISIONS-LOG round 2, C01]** Erasure works by per-person encrypted payloads from day 1: destroying the key and appending a tombstone, with structure, authorship and timestamps kept. Legal sufficiency still needs counsel (OPEN), and erasure for personal data inside Markdown Vault files and git history is OPEN (consequence of C38).
