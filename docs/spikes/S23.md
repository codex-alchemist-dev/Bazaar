# Spike S23: LibGit2Sharp vs git CLI for worktrees, merge with conflicts, two writers behind `IGitProvider`

Branch: `spike/S23` (code stays there under `spikes/S23/`; only this record reaches main). Design source: `docs/design/35-spikes-plan.md`, `docs/design/17-coding-agent-harness.md`, `docs/design/18-vault.md`.

## Question
git: LibGit2Sharp vs git CLI for worktrees, merge with conflicts, two concurrent writers, behind `IGitProvider` (C12).

## Pass criteria (fixed before the first run)
LibGit2Sharp does all three without corruption; else the git CLI becomes an alternative `IGitProvider` (bundling git needs counsel). Concretely, "does all three" was fixed as:
1. Worktrees: add (new and existing branch), commit inside, list, prune; worktrees made by the other engine are usable; `git fsck --strict` clean.
2. Merge: disjoint edits to one file merge; overlapping edits report the conflicting path with markers; abort restores a clean tree at the old HEAD and keeps the branch; rename-vs-edit and modify/delete behave; clean results have the same tree as the git CLI.
3. Concurrent writers: 8 writers in separate worktrees/branches lose no commits, in-process and mixed with the CLI; fsck clean. Writers merging into one shared checkout are expected to need an external lock (the Vault already has one `VaultWriter` queue); it is recorded what happens without it.
Fail consequence: the CLI implementation ships first and bundling `git` goes to counsel.

## Time-box
2 d (plan). Took well under that.

## Method
Throwaway console project `spikes/S23/` (own `Directory.Packages.props`, own `global.json` because the host had .NET SDK 10.0.401 and the repo pins 10.0.402; no shared file touched). Two engines behind a spike-local interface shaped like `IGitProvider`: LibGit2Sharp 0.31.0 (native libgit2 2.0.323 package) and `git` 2.54.0 CLI (config isolated: no global/system config, `core.autocrlf=false`). Each scenario runs on fresh temp repos with both engines; the CLI is also the oracle for tree comparison, status and `fsck`.

Environment: **Windows 11 Pro (10.0.26300), 24 logical CPUs, 96 GB RAM, local SSD, .NET 10.0.13, Release.** This is the owner's PC, not the cloud Linux container the plan names; no Linux run was made (no WSL or container here). Linux is the open part: see Consequence.

## Runs
Three full runs, same machine. All scenario outcomes were identical in every run (the first run's only anomaly was a harness bug in the C4 child launcher, fixed before runs 2 and 3; run 1's other numbers are kept).

| Scenario | LibGit2Sharp | git CLI |
|---|---|---|
| A1 worktree add, commit inside, list, prune, fsck | pass | pass |
| A2 worktree on an existing branch | pass | pass |
| A3 worktree made by the other engine, committed to by this one | pass | pass |
| A4 sparse worktree (`paths` argument of the doc 18 sketch) | **no API** (no `Sparse` member anywhere in the assembly) | pass (`sparse-checkout set --no-cone`) |
| B1 disjoint edits, same file | clean, 2 parents | clean, 2 parents |
| B2 overlapping edits | conflict `doc.md`, markers, abort restores, branch kept | identical |
| B3 rename vs edit | clean (rename followed) | clean, same tree |
| B4 modify/delete | conflict `other.md`, abort restores | identical |
| B5 one clean file plus one conflicting | conflict only `doc.md`, abort restores | identical |
| B6 `*.md merge=union` | honoured, clean | honoured, same tree |
| B-tree: result tree of B1, B3, B6 | identical to the CLI's | |
| C1 8 writers, own worktree, 40 commits each | 320 commits, 0 errors, fsck ok | 320 commits, 0 errors, fsck ok |
| C2 same, half LibGit2Sharp and half CLI at once | 320 commits, 0 errors, fsck ok | |
| C3 4 writers merging into one shared checkout, **with** a lock | 24 merges, nothing lost, clean, fsck ok | same |
| C3 same, **no** lock | broken (below) | broken (below) |
| C4 8 threads reading through one shared `Repository` | 0 errors, 0 wrong counts (runs 2 and 3) | n/a |

Timings, median of three runs (ms):

| Measure | LibGit2Sharp | git CLI |
|---|---|---|
| A1 worktree lifecycle | 336 (324 to 461) | 470 (460 to 499) |
| B1 setup plus merge | 288 (271 to 294) | 619 (592 to 621) |
| C1 8 writers x 40 commits (320 commits) | 2,545 (2,394 to 3,021) | 6,795 (6,126 to 8,174) |
| C2 mixed 8 writers x 40 | 6,299 (6,100 to 6,359) | |
| C3 locked, 24 merges | 1,829 (1,523 to 2,237) | 3,443 (3,406 to 3,738) |
| D1 400 sequential one-file commits | 13,601 (13,337 to 15,053), about 34 ms/commit | 35,772 (35,432 to 36,691), about 89 ms/commit |

Growth (D1, 400 commits on 40 small files): LibGit2Sharp left 1,606 loose objects, about 516 KiB; the CLI's count varied with its automatic housekeeping (168 to 960 loose). Neither shows anything alarming at 400 commits; 10k-commit growth and a `gc` policy were not measured.

C3 without a lock, all three runs, both engines: failed attempts (index lock or stale-parent errors) in the hundreds, 2 to 23 writers per run gave up after 60 retries, 3 to 4 of 4 branches not fully in `main`, 7 to 23 files missing from `main`, and the shared checkout left dirty (part of that is one writer's `abort` undoing another's in-flight merge). `fsck` stayed clean: the object database is not corrupted, but the checkout, index and branch tip are not trustworthy. LibGit2Sharp failed faster and left less damage than the CLI, but both fail.

## Result
**pass.** LibGit2Sharp completed worktrees, merge with conflicts (same conflict paths, markers, abort and result trees as git), and parallel writers in separate worktrees without corruption, and it is about 2.4x faster for commits and 2x for merges here. One gap: it has no sparse-checkout API, so the `paths` argument of the doc 18 `AddWorktreeAsync` sketch cannot be done natively. Two writers on one checkout is unsafe for both engines unless serialised, which the Vault design already requires ("one writer per repo", `VaultWriter` queue) and doc 17 requires ("one writer per worktree, by host lock").

## Consequence
- Keep LibGit2Sharp as the default `IGitProvider`; S23 does not fail (C12 stands). No DECISIONS-LOG change to the engine; add this to round 3 or the next round: "S23 passed on Windows; LibGit2Sharp stays; sparse worktrees need a gap decision".
- Sparse worktrees (doc 18 "a sparse worktree contains no other agent's area"): LibGit2Sharp cannot do it. Options for the main session to choose: (a) the `paths` argument is implemented by the CLI for that one call (needs `git` on the host, a provisioning step on Windows, bundling still needs counsel), (b) build the worktree by materialising only the allowed paths (checkout then delete, or `git archive` equivalent) and mark the rest `assume-unchanged`, or (c) drop the sparse promise and enforce privacy at the Vault read layer instead. This is a design call, not made here.
- `IGitProvider` must say: a repo checkout has one writer (host lock per worktree and a single merge lane into the main checkout). Do not rely on engine-level locking: both engines fail without it. A startup step must still abort unfinished merges and remove stale worktrees (doc 18), as `git worktree prune` plus `Reset(Hard)` both worked here.
- Mixed use is safe: worktrees and branches created by either engine can be used by the other, so a CLI fallback can be adopted per operation.
- Not covered (open, say so before relying on this): **Linux** (the plan's runner; native binaries for linux-x64, linux-arm64, osx-arm64 and win-x64 are in the NuGet package, 1.2 to 1.7 MB each, but nothing was executed on Linux), long histories (10k+ commits), file locking behaviour on SMB shares between VMs (doc 17 puts worktrees on a work share), submodules, LFS, hooks, and push/fetch (`IGitProvider` network paths, run host-side per C05). A cloud Linux rerun of `spikes/S23` (`dotnet run -c Release`) is a small follow-up.
- Packaging: the native libgit2 ships inside the package, no `git` install needed; the CLI alternative would need `git` provisioned on the host.
- Process note: the repo's `global.json` pins SDK 10.0.402; the spike used its own `global.json` for 10.0.401. Nothing else from the shared build config was changed.
