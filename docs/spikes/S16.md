# Spike S16: SOCKS5 through `SocketsHttpHandler`; `https://` proxy URIs on Linux

Branch: `spike/S16` (code stays there; only this record reaches main). Design source: `docs/design/35-spikes-plan.md`.

## Question
Can `SocketsHttpHandler` on .NET 11 send requests through a local SOCKS5 proxy, and do `https://` proxy URIs work on Linux (dotnet/runtime#102441)?

## Pass criteria (fixed before the first run)
Request succeeds via local SOCKS5 proxy (fail: outbound proxy stays schema-only)

Plan row S16 (`docs/design/35-spikes-plan.md`, line 47) also reads: "SOCKS5 through `SocketsHttpHandler` on .NET 10; `https://` proxy URIs on Linux (dotnet/runtime#102441)", time-box 0.5 d, dependencies None, machine Cloud, risk 05 (low). This run targets .NET 11 as the owner directed; the plan text was not edited.

## Time-box
0.5 d.

## Method
Harness: `spikes/S16/` (Program.cs, S16.csproj). Everything runs in one process: a tiny HTTP/1.1 target on loopback, an in-process proxy (SOCKS4, SOCKS4a, SOCKS5 with and without user/pass, HTTP with absolute-form forwarding and CONNECT, and an HTTPS-wrapped HTTP proxy with a self-signed cert), and a `HttpClient` on `SocketsHttpHandler` with `WebProxy` set. Each variant does one untimed warm-up and 30 timed `GET` requests. The proxy counts CONNECTs and forwards, and logs the SOCKS ATYP (1 = IPv4, 3 = domain name).

Changes made on this branch for the Linux runs:
- `spikes/S16/S16.csproj`: `TargetFramework` changed from `net10.0` to `net11.0`.
- Root `global.json`: the spike branch was based on an older commit and pinned SDK `10.0.402`, which is not installed here. I copied the `origin/main` version (`11.0.100-rc.2.26504.105`, the installed SDK). Nothing else on the branch was merged.

Environment, Linux runs (this container):
- OS: Linux 6.18.44-fc-v153 (x86_64 VM)
- CPU: 4 vCPU (`nproc`); CPU model string not captured
- RAM: 16 GB
- `dotnet --version`: 11.0.100-rc.2.26504.105
- Runtime: Microsoft.NETCore.App 11.0.0-rc.2.26504.105
- Build: `dotnet build -c Release`, 0 errors, 16 analyzer warnings (not errors)
- Runs: `dotnet run -c Release --no-build`, three times, each run covering all 12 variants

Environment, Windows runs (`results/run1-3.*`, from the earlier branch state): .NET 10 on a Windows PC. OS, CPU, RAM and exact SDK/runtime versions were not recorded in the branch; they are not reported here. The Windows results were not re-run.

Raw output: `spikes/S16/results/linux-net11-run{1,2,3}.jsonl` and `.err` (Linux, .NET 11); `spikes/S16/results/run{1,2,3}.jsonl` and `.err` (Windows, .NET 10, untouched).

## Result
**pass.** On .NET 11 on Linux, `SocketsHttpHandler` with `WebProxy("socks5://127.0.0.1:PORT")` completes all 31 requests per run through the in-process SOCKS5 proxy, in all three runs. The proxy saw CONNECT with ATYP 1 for the IPv4 target and ATYP 3 (domain name sent to the proxy) for `localhost`. Credentials work: with user/pass set on `WebProxy`, the SOCKS5 user/pass subnegotiation succeeds (`socks5: auth ok`). With no credentials, the handshake fails as expected. Stopping the proxy gives a connection-refused failure, so the successes are real traffic through the proxy, not a bypass. SOCKS4 and SOCKS4a also work. The Windows .NET 10 runs agree for `socks5://`, `socks4://` and `socks4a://`.

**socks5h:// (this contradicts an assumption in the brief).** On Windows .NET 10, `socks5h://` is rejected with `NotSupportedException: Only the 'http', 'https', 'socks4', 'socks4a' and 'socks5' schemes are allowed for proxies.` in all three runs. On .NET 11 on Linux, the same scheme is accepted and all 31 requests pass per run. So the rejection is not universal across the two runs. The on-wire behavior for `socks5` is the same on both platforms: the domain form is sent as ATYP 3 to the proxy. I did not run .NET 10 on Linux, so I cannot tell whether the difference comes from the .NET version, from the OS, or from both. Do not treat `socks5h://` as portable until it is re-run on Windows on .NET 11.

**https:// proxy URIs on Linux (dotnet/runtime#102441).** With certificate validation bypassed (`SslOptions.RemoteCertificateValidationCallback` returning true), an `https://` proxy URI works on Linux on .NET 11: all 31 plain-HTTP requests pass per run, forwarded through the TLS-wrapped proxy in absolute form. With default validation and a self-signed proxy certificate, it fails with `UntrustedRoot`, which is the correct outcome for an untrusted chain. Not tested: an `https://` proxy with a certificate that chains to a trusted root (the default-validation case with a trusted CA), and `https://` proxy with credentials. I did not check issue 102441 itself, so I cannot say whether this run reproduces or closes it.

**Surprising:** the `https://` proxy path is about 48 ms median per request on Linux .NET 11 but about 2.5 ms on Windows .NET 10, with very small spread in both. I did not investigate the cause. It could be a TLS or Nagle/delayed-ACK interaction in the in-process proxy, or the Linux networking stack; it was not measured further. The `https://` numbers therefore should not be used for latency comparisons.

**Verdict vs pass criterion:** request succeeds via local SOCKS5 proxy: met on .NET 11 Linux (all three runs) and on Windows .NET 10 for `socks5://`. The outbound proxy is not schema-only.

## Consequence
Suggested DECISIONS-LOG entry for the main session to write (not written here):
- `socks5://` through `SocketsHttpHandler` works on .NET 11 (Linux verified; Windows verified on .NET 10). It is usable for the outbound-proxy setting.
- `socks5h://` is rejected on Windows .NET 10 and accepted on Linux .NET 11. Keep the setting on `socks5://` until `socks5h://` is re-verified on Windows .NET 11.
- `https://` proxy URIs work on Linux .NET 11 only with certificate validation bypassed in this test. Before relying on them, run the trusted-chain case and the credentials case.
- Re-check dotnet/runtime#102441 against the current state before recording it as resolved; this spike did not read it.

Open items from this run (not done, out of time-box): Windows .NET 11 run of the same harness (to settle the socks5h question); `https://` proxy with a trusted certificate and with credentials; .NET 10 on Linux, to separate version from OS in the socks5h difference.
