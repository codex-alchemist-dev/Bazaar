# Spike S16: SOCKS5 through `SocketsHttpHandler` on .NET 10

Branch: `spike/S16` (code stays there; only this record reaches main). Design source: `docs/design/35-spikes-plan.md`.

## Question
Does a request go through a local SOCKS5 proxy using `SocketsHttpHandler` on .NET 10 (`Proxy = new WebProxy("socks5://127.0.0.1:PORT")`)? Also: do `https://` proxy URIs work (dotnet/runtime#102441 says Linux was an issue; record what happens on this Windows machine and say the Linux half was not run).

## Pass criteria (fixed before the first run)
Pass criteria: request succeeds via local SOCKS5 proxy (fail: outbound proxy stays schema-only).

Fail consequence: the outbound proxy stays schema-only (the gateway outbound proxy in doc 05 is not implementable on this stack as planned; low priority).

Proof conditions fixed with the criteria: a request counts as "via proxy" only if the in-process proxy logged a CONNECT for it. A control run with the proxy stopped must FAIL. Result is pending until the runs are recorded below.

## Time-box
0.5 d (hard stop from the plan). Used well under the box.

## Method
**Environment.** Windows 11 Pro (build 26300), Intel Core Ultra 9 285K, 95.3 GB RAM, loopback only. .NET SDK 10.0.401 installed; the repo's `global.json` pins 10.0.402, which is not installed, so the spike was built outside the repo (scratch folder with no `global.json` in its parents) and only the source was committed. The app is `net10.0` and ran on the installed 10.0.x runtime (10.0.12 and 10.0.13 are present). No Postgres involved.

**Code.** `spikes/S16/` on `spike/S16` (commit `8a98e60`): `Program.cs`, `S16.csproj`. Raw output: `spikes/S16/results/run1.jsonl` to `run3.jsonl` (one JSON line per variant) and the matching `.err` summaries.

**Harness.**
- Target: tiny HTTP/1.1 server on 127.0.0.1, answers `ok-from-target` with `Connection: close`. Because the target closes every connection, each timed request opens a new tunnel, so proxy CONNECT count should equal request count.
- Proxy: in-process `TcpListener` on an ephemeral port. Kinds: SOCKS5 (no auth, RFC 1929 user/password, IPv4/IPv6/domain ATYP), SOCKS4 and SOCKS4a, HTTP forward proxy (absolute-form requests, plus HTTP CONNECT), and the HTTP forward proxy wrapped in TLS with a self-signed cert (CN=localhost, SAN 127.0.0.1 and localhost) for `https://` URIs. The proxy counts SOCKS/HTTP CONNECT requests and absolute-form forwards, and logs each one.
- Client: `new SocketsHttpHandler { Proxy = new WebProxy("<scheme>://127.0.0.1:PORT") { BypassProxyOnLocal = false }, UseProxy = true }` inside an `HttpClient`. Per variant: one untimed warm-up, then 30 timed `GetStringAsync` calls. Latency is per request, end to end.
- Controls: proxy stopped (port closed) must fail; SOCKS5 user/password proxy with no credentials must fail; `https://` proxy with default certificate validation must fail (self-signed cert, no trust store change). The HTTP absolute-form variant is a baseline.
- Variants marked "domain" target `localhost` rather than `127.0.0.1`.
- Procedure: `dotnet S16.dll` (all 12 variants), three separate process runs.

**Harness problems found and fixed before the official runs** (criteria unchanged):
1. First full matrix (discarded; its stderr is kept as `spikes/S16/results/discarded-run0-first-attempt.err`): the server-side TLS setup used `EphemeralKeySet`, which Schannel rejects ("platform does not support ephemeral keys"), so every `https://` variant failed inside the harness. Fixed by loading the cert with `Exportable`.
2. Same first matrix: the proxy tried `::1` before `127.0.0.1`. On this machine a refused loopback connect takes about 2 s (measured: refused connect to `::1:9` 2069 ms, to `127.0.0.1:9` 2041 ms), so the domain variants showed about 2044 ms per request. Fixed by trying IPv4 addresses first. The domain variants then measure about 0.8 ms. This is a property of this machine's loopback, not of .NET; it is recorded because the 2 s figure would otherwise be read as proxy overhead.

## Result
**PASS** for the pass criterion: a request succeeds via a local SOCKS5 proxy on .NET 10 with `SocketsHttpHandler` on Windows. 31 of 31 requests succeeded in each run and the in-process proxy saw a CONNECT for each one (31 per run), so the traffic really went through the proxy. The stopped-proxy control fails with connection refused, so success is not a direct connection. Latency through the proxy is about 0.5 ms median on loopback (run medians 0.45 to 0.48 ms). SOCKS4, SOCKS4a, SOCKS5 with user/password, and SOCKS5 with a domain name (the proxy receives the name, so DNS happens proxy-side) also pass.

Two things did not work as the plan hoped:
- `socks5h://` is rejected outright by .NET 10 (`NotSupportedException: Only the 'http', 'https', 'socks4', 'socks4a' and 'socks5' schemes are allowed for proxies.`). Not needed for proxy-side DNS: `socks5://` already sends domain names to the proxy.
- `https://` proxy URIs work on Windows only when the proxy certificate is accepted. With the spike-only callback (`SslOptions.RemoteCertificateValidationCallback = true`) all 31 requests pass via the TLS proxy. With default validation the handshake fails with `UntrustedRoot` for the self-signed cert. The callback does govern the proxy hop, since the target is plain HTTP. A real `https://` proxy therefore needs an OS-trusted certificate or an explicit validation policy. The accept-any callback is spike-only and must not reach product code. This run did not install a trust root (that would change system security settings).

**Not run:** the Linux half of the question (dotnet/runtime#102441 was not reproduced or ruled out); a real third-party SOCKS server (for example `ssh -D` or Dante), so the proxy is our own in-process implementation; a trusted-certificate `https://` proxy; IPv6 targets; a wrong-password auth case (only the no-credentials control); traffic over a real network (all loopback); connection reuse through a tunnel (every request opens its own tunnel by design). Also the 0.5 d time-box was not exceeded.

## Consequence
- **Unblocks:** the gateway outbound proxy in doc 05 can use a SOCKS5 option on Windows with .NET 10 `SocketsHttpHandler`. Doc 05 stays low priority per the plan. The "schema-only" fail mode does not apply to SOCKS5 on this platform.
- **Constraints to carry into doc 05:** use `socks5://` (or `socks4a://`), not `socks5h://`, which .NET 10 rejects. `https://` proxy URIs need an OS-trusted proxy certificate or an explicit validation policy; no accept-any callbacks in product code.
- **Still open:** the Linux half of #102441 (needs a Linux run); a real external SOCKS server; a trusted-cert `https://` proxy test.
