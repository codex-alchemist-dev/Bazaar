# Spike S11: Local terminal control on ConPTY (Windows) and PTY (Linux client)

Branch: `spike/S11` (code stays there under `spikes/S11/`; only this record reaches main). Design source: `docs/design/35-spikes-plan.md`, `docs/design/28-windows-client.md` (Local terminal), `docs/design/30-linux-client-and-packaging.md` (section 2, PTY backend).

## Question
Local terminal control on ConPTY (Windows) and PTY (Linux client). Agent VM terminals are server-streamed and not tested here (C31).

## Pass criteria (fixed before the first run)
Plan text, verbatim: "Shell, resize, colour and Ctrl-C correct on both; licence OSI-compatible for the OSI-only build (C23) (fail: own terminal widget)."

Operational definitions, fixed before the first run:
- Shell: `cmd.exe` and `pwsh` each start under the pseudo console; a command's marker output appears in the output stream.
- Resize: after `ResizePseudoConsole` to 100x30 and then to 132x40, `mode con` (cmd) and `$Host.UI.RawUI.WindowSize` (pwsh) report the new size.
- Colour: the child emits ESC[31m, ESC[38;5;196m (256-colour) and ESC[38;2;255;0;0m (truecolor), each followed by text and ESC[0m; pass when the output stream contains the parameter sequences `31`, `38;5;196` and `38;2;255;0;0` in SGR form. ConPTY re-encodes VT output, so the check is for the SGR parameters, not byte equality.
- Ctrl-C: `ping -t 127.0.0.1` runs in cmd and in pwsh; byte 0x03 is written to the input pipe; within 10 s the ping process exits and the shell returns a prompt that runs `echo ALIVE` successfully.
- Clean shutdown: `ClosePseudoConsole` returns, the shell process exits, and no shell or ping process started by the harness remains 5 s later.
- Time from process creation to first output byte is recorded in each run (informational, no threshold; reported as median and spread).
- Licence: each candidate library's licence is read from its NuGet metadata or repository and must be OSI-approved or a permissive licence compatible with an AGPL-3.0 build. A candidate that is not OSI-approved fails.
- Overall result: pass only when the ConPTY checks pass, the licence check passes and the Linux PTY half has also been run and passes. With only the ConPTY half run, the result is inconclusive, not pass, even if every ConPTY check passes.
- Fail consequence (plan): own terminal widget. A failed licence or ConPTY check for the chosen approach reopens the terminal library choice; the local terminal is not built on an incompatible licence.

## Time-box
2 d (plan). Hard stop at 2 d of work.

## Method
Windows (ConPTY) half only. The Linux PTY half has not been run.

- **Environment.** Owner's PC: Windows 11 Pro 10.0.26300, x64, 24 logical CPUs. Harness built with the .NET 10 SDK targeting `net10.0`, run on .NET 10.0.13 (the repo now targets .NET 11; the harness does not depend on that).
- **Harness.** `spikes/S11/Spike.S11.Conpty/` on `spike/S11` (commit `70b12ef`). It is an own thin P/Invoke wrapper over kernel32 with no third-party code: `CreatePipe`, `CreatePseudoConsole`, `ResizePseudoConsole`, `ClosePseudoConsole`, `STARTUPINFOEX` with `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE`, `CreateProcessW`. It drives `cmd.exe` and PowerShell 7 through the five checks defined above (SHELL_ECHO, RESIZE, COLOUR, CTRL_C, SHUTDOWN).
- **Licence check.** No library is used, so there is no third-party licence to read. This leaves the library choice (own wrapper versus a terminal-emulation component) open; the licence criterion is satisfied trivially for the wrapper and is not evidence about any candidate library.
- **Raw output.** `spikes/S11/results/` on `spike/S11`.

## Runs
Three official runs, 2026-10-25, each starting `cmd.exe` and `pwsh` fresh. Each run executed 10 checks (5 per shell). The first harness trial failed two checks; the cause was in the harness (see Findings) and was fixed before the official runs. The pass criteria did not change.

| 2 | 10 | 0 | 13.5 ms | 54.4 ms | 13.8 ms | 305.3 ms |
| 3 | 10 | 0 | 13.8 ms | 51.6 ms | 13.1 ms | 304.4 ms |

A second set of three runs from a build made before the SDK was pinned (`rc2-sdk-official-run1..3.txt`) gave the same result, 10 of 10 in each run.

Findings during the trial:
- **Ctrl-C was ignored when the host had Ctrl-C disabled.** In the first trial, writing 0x03 to the input pipe did not stop `ping -t`, left `ping.exe` running and the shell unresponsive (`trial-before-harness-fixes.txt`, CTRL_C fail in both shells). Children inherit the "ignore Ctrl-C" disposition of the process that creates the pseudo console. Calling `SetConsoleCtrlHandler(NULL, FALSE)` in the host before creating the child fixes it (`diag-ctrlc-after-fix.txt`). A real terminal host must do the same.
- **Pwsh start-up is slower than cmd.** Prompt after `CreateProcess` returned is about 300 ms for pwsh and about 55 ms for cmd; first output byte is about 13 ms for both.

## Result
**inconclusive.** All ConPTY checks pass in all three runs (shell, resize, colour, Ctrl-C and clean shutdown, for both `cmd.exe` and `pwsh`, no orphaned `ping.exe`). Under the pass criteria fixed before the first run, the overall result is pass only when the Linux PTY half has also been run and passes; with only ConPTY run, the result is inconclusive, not pass.

What this does not show: the Linux PTY half; any terminal-emulation or rendering component (the harness reads the VT stream and checks SGR parameters, it does not render); behaviour under a GUI host (no Avalonia in the loop); older Windows builds (only 10.0.26300 tested); shells other than cmd and pwsh 7.

## Consequence
- The Windows ConPTY mechanism meets the criteria on the tested build, so the plan's fail consequence (own terminal widget) is not triggered by the Windows half.
- The host must clear the inherited Ctrl-C ignore flag (`SetConsoleCtrlHandler(NULL, FALSE)`) before spawning a pseudo console; this belongs in doc 28 (Local terminal) as an implementation note. Not edited here; the main session decides.
- Open: Linux PTY half (doc 30 section 2); choice of terminal-emulation component and its licence against the OSI-only build (C23).
