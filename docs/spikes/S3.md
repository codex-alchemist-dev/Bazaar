# Spike S3: GC log at scale, owner's PC run

Harness and Linux baseline: `spikes/S3/` (Program.cs, schema.sql). Raw results: `spikes/S3/results/`. Criteria from `docs/design/35-spikes-plan.md` (S3): p95 append under 50 ms; no lost events after reconnect; `gc_id` plus timestamp indexing measured, not assumed. The Linux baseline is in the DECISIONS-LOG round 16 S3 row. This section adds the owner's PC run; the NUC is gone, so it replaces the NUC run.

## Method (owner's PC)
- **Environment.** Owner's PC: Windows 11 Pro 10.0.26300, x64, 24 logical CPUs. PostgreSQL 18.6 from the EDB Windows binaries zip (same SHA-256 as S25), run as the interactive user on `127.0.0.1:54318`, `shared_buffers` 1 GB, `max_connections` 300, no service.
- **Build.** .NET 10 SDK 10.0.402 installed per-user to `%USERPROFILE%\.dotnet-s25`, matching the repo's `global.json` pin. The harness was built in a copy outside the repo because the first build attempt failed on the 10.0.402 pin.
- **Runs.** Each run: `--parts 16 --notify batch`, default phases (load, hot, page, replay, index, reconnect), fresh database, `--tag full --rep 1` for runs 1 to 3. Run 21 is the timestamp-index variant: `--tag variant --rep 1 --tsindex on`.

## Verdict
- **Append p95 under 50 ms: pass** at the 500/s load phase (15.7 to 16.2 ms in all four runs).
- **No lost events after reconnect: pass** (0 lost of 9,600 in every run, 4 reconnects each).
- **Hot-GC burst: above 50 ms.** 200 concurrent appends into one GC reach p95 264 to 289 ms, consistent with the per-GC `head_seq` row lock the Linux baseline measured (one GC tops out near 400 to 700 appends/s). This is a finding for the design, not a pass or fail; bulk writers should batch, as the baseline recommended.
- **Timestamp index measured:** the `(gc_id, created_at)` index adds 62 MB on 1M events (991 to 1,053 MB) and does not change page or replay latency in a way the runs can separate from noise (page p95 12.9 ms with the index against 9.9 to 12.8 ms without). The default stays without the index, as the baseline recommended.

## Problems seen
- **Exception on the first run.** Run 1 printed an unhandled `57P01` ("terminating connection due to administrator command") after writing its results. It came from an earlier background attempt at run 1 that used the same database name: the second run's `DROP DATABASE ... WITH (FORCE)` killed the first run's connections. A clean rerun of run 1 has no exception, and runs 2, 3 and 21 have none. The results above are from the clean rerun.
- **Exit code.** The harness exits 0 even when its background tasks throw, so a failure can look like a pass in the exit code. Check the log for `Unhandled` before trusting a results file.

## Not tested
- The multi-server fan-out and the periodic head-versus-cursor sweep (the baseline did not test them either).
- A registered Windows service, or the NUC.
- Antivirus or a slow disk.
