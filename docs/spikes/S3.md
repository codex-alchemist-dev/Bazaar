# Spike S3: GC log at scale

Branch: `spike/S3` (code stays there; only this record reaches main). Design source: `docs/design/35-spikes-plan.md`.

## Question
Does the `gc_event` / `gc_message` / `gc_message_version` model (C09), hash-partitioned by `gc_id` (C10), hold up under chat load on real Postgres 18: append plus NOTIFY and replay at burst rates, a 200-message page, a 10k replay, and a forced listener reconnect? Is `gc_id` plus timestamp indexing needed, measured rather than assumed?

## Pass criteria (fixed before the first run)
From doc 35: **p95 append under 50 ms; no lost events after reconnect; `gc_id` plus timestamp indexing measured, not assumed.** Fail consequence: batch or partition-count redesign.

Thresholds the plan does not give, fixed by the spike runner before the first run (proposals for the owner to accept or change):
- Append p95 is judged at a paced 500 appends/s for 30 s (open loop, latency taken from the scheduled start so queueing counts), NOTIFY on, a consumer attached, 30% of appends to one hot GC.
- 200 simultaneous appends to one GC give gap-free seq.
- 200-message page p95 under 50 ms. 10k replay is contiguous in seq and the paged form finishes in a median under 2 s.
- Reconnect: the listener backend is killed four times under load; zero events missing once the consumer has caught up.

## Time-box
2 d (doc 35). Used about 2 h of runner time.

## Method
Harness: `spikes/S3/` on branch `spike/S3` (C#, Npgsql 10.0.3, .NET 10.0.402). Schema is doc 01's: `gc` (with `head_seq`), `gc_event`, `gc_message`, `gc_message_version`, `gc_mention`, all but `gc` hash-partitioned by `gc_id`, primary keys led by `gc_id`, the FKs, the idempotency unique key and the UPDATE/DELETE-refusing triggers. Bodies are 400-byte `bytea`.

- **Append:** one SQL statement (one round trip, one transaction): `UPDATE gc SET head_seq = head_seq + 1 ... RETURNING`, then event, message, version and (20% of appends) mention rows as data-modifying CTEs.
- **Preload:** 1000 GCs, 1,000,099 events (one hot GC of 100k, 999 GCs of 901), about 1 GB, then `ANALYZE` and `CHECKPOINT`. A fresh database per full run.
- **Consumer:** one `LISTEN gc` connection used only as a wake hint. A hint queues a read of the log from a per-GC cursor; the cursor advances only over contiguous seq. On reconnect it re-listens and then reads every GC whose `head_seq` is past its cursor.
- **NOTIFY modes compared:** `on` (`pg_notify` inside the append transaction, as doc 01 sketches), `post` (a separate statement after commit), `batch` (appends record the newest seq per GC; one notifier sends them in one transaction every 5 ms), `off`.
- **Environment:** Linux 6.18 container, 4 vCPU Intel Xeon 2.1 GHz, 16 GB RAM; Postgres 18.6 (`pgvector/pgvector:pg18`, Docker, default config: `shared_buffers` 128 MB, `fsync` and `synchronous_commit` on) on the same host as the load generator, so the harness competes with Postgres for CPU. This is the Linux baseline; the NUC run is still owed (doc 35: "Cloud (Linux baseline); NUC (pass)").

Process note, for honesty: the first run (in-transaction NOTIFY, no `CHECKPOINT` after preload) gave p95 309 ms. I added the checkpoint (steady state) and investigated the tail; that run is not counted. Diagnostic runs are in `spikes/S3/results/diagnostic/`. Two harness bugs (a negative delay in the kill schedule; the consumer reading a GC it did not track) crashed the first attempt of the full runs before any result file was written; they were fixed and all three full runs repeated from scratch.

## Runs
Three full runs on fresh 1M-event databases, 16 partitions, batched NOTIFY. Raw JSON in `spikes/S3/results/full*.json`.

| Run | Append p95 at 500/s | Append p99 | Page-200 p95 (random, hot 100k GC) | 10k replay, paged (median) | Hot GC, 200 at once (gap-free) | Reconnect: events lost / recovered only by catch-up | Insert-to-consumer-read p95 |
|---|---|---|---|---|---|---|---|
| 1 | 8.95 ms | 292 ms | 4.36 ms | 122 ms | yes; p95 264 ms | 0 / 81 of 9,600 | 10.7 ms (reconnect test), 16.0 ms (load) |
| 2 | 6.38 ms | 9.2 ms | 4.61 ms | 126 ms | yes; p95 441 ms | 0 / 75 of 9,600 | 10.6 ms, 11.6 ms |
| 3 | 7.12 ms | 9.0 ms | 4.34 ms | 121 ms | yes; p95 464 ms | 0 / 78 of 9,600 | 10.9 ms, 11.5 ms |

Median append p95: **7.1 ms**, spread 6.4 to 9.0 ms. Median page p95: 4.4 ms (4.3 to 4.6). Paged replay median 122 ms (121 to 126); a single 10k statement 92 to 96 ms; seq contiguous in every replay. Each forced kill re-established `LISTEN` in 57 to 61 ms. Gap check after load (every GC's row count equals `head_seq` equals max seq): zero violations in all three runs. Append p50 about 4.3 ms throughout.

Other measurements (all from the three full runs unless noted):
- **Closed-loop saturation**, 32 workers: 1,425 to 1,568 appends/s; p50 about 3.7 ms, p95 107 to 121 ms (queueing on the hot GC), p99 217 to 232 ms.
- **Hot-GC serialisation:** `gc.head_seq` is a row lock held to commit, so appends to one GC are serial. A 200-append burst to one GC finished in 270 to 470 ms (1.4 to 2.4 ms per append, roughly 400 to 700 appends/s for a single GC). Gap-free every time.
- **Tail noise:** run 1 had p99 292 ms and max 1.2 s; run 2 and 3 max 45 ms. NOTIFY-off runs on this host also showed 270 to 420 ms maxima, so stalls are environmental (shared 4 vCPU, container storage), not NOTIFY.

### NOTIFY placement (load phase, 500/s, 30 s, 3 repeats each, interleaved)
| Mode | p95 (ms) per repeat | p99 (ms) | Max (ms) |
|---|---|---|---|
| `on` (in the append transaction) | 9.8, 6.8, **115** | 372, 56, **611** | 1634, 442, **1963** |
| `post` (after commit) | 6.5, 8.6, 7.8 | 13.7, 44.7, 24.4 | 243, 455, 426 |
| `batch` (coalesced, 5 ms) | 6.5, 7.2, 6.6 | 18.4, 9.2, 8.7 | 333, 77, 32 |
| `off` | 7.3, 8.1, 6.9 | 16.3, 74.4, 23.3 | 274, 418, 362 |

`pg_notify` inside the transaction took the shared notification lock through the commit's WAL flush, so notifying commits serialise. One repeat in three blew the tail (p95 115 ms, consumer read p95 567 ms) even though the median append was unchanged. `batch` is as steady as no NOTIFY at all and kept the insert-to-consumer-read p95 near 11 ms (p50 about 8 ms, mostly the 5 ms tick).

### Partition count (single run each, load, hot, page, replay phases; `spikes/S3/results/variant20-*`)
| Partitions | Append p95 | Page-200 p95 | 10k paged replay | Hot 200-burst p95 |
|---|---|---|---|---|
| 1 | 6.9 ms | 3.8 ms | 96 ms | 812 ms |

Append latency does not depend on partition count at this size. Reads cost more with 64 partitions (page p95 about 4x, still under 50 ms). Single runs; spread unmeasured.

### `gc_id` plus timestamp indexing
Query: events in one GC in the last hour (hot GC, about 11k matching rows). With only the `(gc_id, seq)` primary key the planner scanned the partition: median 21 ms, p95 26 to 40 ms (three full runs). With an added `(gc_id, created_at)` index: median 4.6 ms, p95 5.7 ms, at a cost of 66 MB per 1M events (about 7% of the database) and no append regression beyond noise (p95 9.8 ms against 6.7 ms in the paired single runs, p99 61 ms; not repeatable at n=1). Neither shape is needed for the paths tested: page, replay and catch-up all go by `seq`.

## Result
**pass** on the Linux baseline, with a design change to the NOTIFY step. Median append p95 is 7.1 ms at 500 appends/s against a 1M-event, 16-partition database (all three runs under 9 ms, limit 50 ms). No events were lost across 12 forced reconnects (0 of 28,800); about 0.8% of events landed during an outage and were recovered only by the catch-up read. Pages and replays are far inside the limits. The doc 01 sketch as written (`pg_notify` inside the append transaction) did not pass reliably: one repeat in three had a p95 of 115 ms and p99 over 600 ms, so that exact form is **fail on tail stability**. Moving NOTIFY out of the transaction fixes it. The NUC run is still needed to close the spike formally (doc 35).

Limits of this evidence: one host class, Postgres and load generator sharing four vCPUs, default Postgres config, 400-byte bodies, no personal-field encryption, no viewer filtering, no Garnet/Valkey. Idle-listener behaviour over hours, NOTIFY queue growth with many slow listeners, and multi-server fan-out were not tested.

## Consequence
Unblocks G1 (schema) and G3/G4 as designed, with these changes for the main session to write into DECISIONS-LOG and doc 01/04:
1. **NOTIFY is sent after commit by a coalescing notifier (newest seq per GC, one transaction per few ms), not by `pg_notify` inside the append transaction.** Doc 01's append sketch and the Testing line "a rolled-back append emits no NOTIFY" still hold (nothing is sent until commit). A crash between commit and notify only delays a hint, so consumers need a periodic head-versus-cursor sweep as well as the reconnect catch-up (the sweep was not tested here).
2. **Consumers treat NOTIFY as a hint and read the log from a per-GC cursor that advances only over contiguous seq.** Advancing the cursor to the seq in a notification skips the events missed during an outage (I wrote that first; the contiguous rule is what keeps loss at zero).
3. **Default partition count 16**; 64 costs about 4x on page latency here. No change to "count chosen at setup".
4. **No `(gc_id, created_at)` index by default.** Time-range reads should resolve to a seq through `read_state` or `consumer_cursor`; add the index only if a measured time-window path needs it (21 ms unindexed, 66 MB per 1M events indexed). This closes the "scale claim" in doc 35 for `gc_id` indexing: `(gc_id, seq)` is sufficient for the log paths tested.
5. **One hot GC tops out at about 400 to 700 appends/s** because `head_seq` serialises appends per GC. Fine for chat; bulk system writers should batch events into one append rather than fan many appends at one GC.
6. Open for the owner: accept the proposed thresholds above; run the same harness on the NUC (`dotnet run -c Release -- --run N --notify batch`) before calling S3 passed.
