# Spike S28: GPU graph retrieval on the Arc B580 (GraphDRAG)

Branch: `agent/s28-gpu-graph-retrieval` (code stays there under `tests/Bazaar.GraphRetrieval.Spike`; only this record and the result CSVs reach main). Design source: `docs/design/64-gpu-graph-retrieval.md` section 13 (PROPOSED; S28 is not yet in `docs/design/35-spikes-plan.md`).

## Question
Which engine should be the default for each retrieval stage (Postgres, multi-core CPU, GPU on the owner's Arc B580), with exact parity? Is any GPU graph kernel worth building at all? (doc 64, 13.1)

## Pass criteria (fixed before the first run)
Copied from doc 64 section 13.4. These gate `graph_retrieval.gpu.enabled` defaulting to `true`, per stage:

| Gate | Threshold |
|---|---|
| Parity, fp16 | 100 percent id-set and level parity on every query in the suite, within section 8 tolerance; zero scope mismatches |
| Latency | GPU p99 at most half of pgvector exact p99 at the corpus size the install has, and better than the CPU engine for the same stage |
| Small corpora | GPU p50 not worse than pgvector at 10k vectors, or the module declines below a size threshold |
| Recall, int8 | recall@k at least 0.99 for int8 to ship at all (still opt-in) |
| Stability | 24-hour soak with the client renderer running on the same card: no device loss, no leaked VRAM, every forced fault ends in a correct fallback |
| Freshness | a removal is never served after its commit returns |

A GPU stage joins the defaults only if it passes against the CPU engine for that stage. If no stage passes, the Vulkan provider stays opt-in and the CPU engine is the default. Fail consequence for the graph kernels: WP13 (GPU expansion, closure, PPR) is not built.

## Time-box
Set by the coordinator on 2026-11-20 (arm groups, progress note after each). Not a fixed number of hours in the plan. CPU arms were cut to fit (see Method).

## Method
Environment: Intel Arc B580 (11.9 GiB device-local heap, driver 0.406.842 then 0.406.983, Vulkan 1.4), Intel Core Ultra 9 285K (24 cores, 24 threads, AVX2), 95 GB RAM, Windows 11. .NET 11, Vortice.Vulkan 3.3.0, Release build, `BAZAAR_BENCH_BOOST=1` (High priority). Postgres 18 with pgvector 0.8.7 in the `pgvector/pgvector:pg18` image run in WSL2 (Ubuntu 24.04, distro on V:), own container `s28-pgvector` (the CI containers were not touched). All data on V:.

**Vector top-k (arm groups 1 and 2).**
- Data: synthetic unit vectors, deterministic per row, rounded to fp16 (the stored value). D = 768, 1024, 1536; N = 10k, 100k, 1M, 5M, 10M. Queries: planted at cosine about 0.35 to a stored row (one clear hit and a field of near ties), 128 distinct queries cycled. This is not a real embedding distribution; see Limits.
- CPU engine: exact, fp32 values of the stored fp16 rows, AVX2 dot with queries blocked four at a time, bounded heaps per thread, fixed partition. At all cores it is the reference for recall. It stores fp32 (4 B per dimension), not Half, so it is faster than a Half-based engine would be and uses twice the memory.
- GPU fp16: row-major fp16 matrix in 2 GiB chunks, one thread per row, 8 queries per row pass, cosine score = dot times 1/norm; per chunk a two-level histogram of the ordered float key finds the k'-th score (k' = k + 16), then a gather writes the candidates; the host merges the chunk lists and cuts at k. int8 mode: per-row symmetric int8 with fp32 scale as the first pass, 4k + 16 survivors per query rescored exactly on the host from the fp16 values. Latency is wall time per call including the host merge (and the rescore for int8).
- pgvector exact: `halfvec` column with `STORAGE PLAIN` (see Results: the default storage is 4 to 5 times slower above 1000 dimensions), sequential scan (index scans off), 8 workers per query alone, 2 per query with 8 clients, `ORDER BY emb <=> $1 LIMIT k`. Server time is `EXPLAIN ANALYZE` execution time; end-to-end adds about 40 to 50 ms of client path over the Windows to WSL loopback and is in the CSV.
- Series: k and batch combinations (10,1) (20,1) (50,1) (10,8) (10,32) (50,32) (10,128); 3 to 100 repetitions per series within an 8 second budget per series after 2 warm-up repetitions.
- Time-box cuts: CPU at 1 and 4 threads only up to 1M rows, 8 threads up to 5M rows; D = 1536 at 10M rows skipped (the fp32 host copy would pass the memory budget); pgvector only up to 1M rows (D = 1024 and 768) and 100k rows at D = 1536; pgvector HNSW (arm 2) and software Vulkan (arm 6) not run.

**Graph kernels (arm group 3).**
- Graph: synthetic CSR, typed directed edges (kinds link 1.0, derived_from 0.8, supersedes 0.5), mean out-degree about 10 with a heavy tail (1 percent of nodes at 30 times the mean), link targets skewed to low ids, DAG kinds pointing 1 to 64 below the source so chains are long. Sizes 0.93M, 9.3M, 93M, 465M and 930M edges (nodes 0.1M to 100M). The 930M graph holds 4.8 GiB on the GPU.
- Expansion and DAG closure: level-synchronous BFS, visited bitset, indirect dispatch per level, 3 hops (1 to 3 tested) or depth 2, 8 and 32 over the DAG kinds, 1, 8 and 32 seeds, batches 1 and 32 (queries run back to back, not interleaved). CPU: parallel frontier with atomic bitset at 1, 8 and 24 threads. Verified per query against the CPU by per-level (count, sum, xor) of the reached ids.
- Personalised PageRank: 20 fixed iterations, alpha 0.15, 8 seeds, pull form over the transposed CSR, float32, subgraphs of 1k, 10k, 100k and 1M nodes (generated with the same generator at mean degree 10, not cut out of the big graph), top-50 selection included, GPU scores read back. Verified against the CPU scores.
- Not tried: per-node and per-query frontier caps in deterministic order, the mask by range, multi-hop with typed predicates on the GPU, interleaving several queries in one dispatch, GPU top-k of the PPR scores.

## Runs
One run per configuration (the CSVs hold every series; each series has its own repetitions). The three-run minimum of the template is not met; run-to-run spread was not measured (the earlier benchmark sections show small rows can differ by a factor of two). ## Result
**inconclusive overall; interim: the vector kernels pass the speed gates, the graph kernels do not.** The 24-hour soak, the retrieval-quality evaluation on real data and the repeat runs are missing, so no default can be set by this record alone.
- **Vector top-k (GPU fp16 and int8).** Parity: every row has recall 1.0000 against the exact CPU result, int8 included (planted queries; see Limits). Speed: at 1M x 1024 the GPU takes 8.3 ms (p99 11.5) against 85 ms for pgvector exact (p99 122), 43 ms for the 24-thread CPU engine and 359 ms for one CPU thread: 10 times faster than pgvector and 5 times faster than all 24 cores; with batches of 32 the GPU does 260 queries per second (int8 458) against 88 on 24 cores. At 10k vectors the GPU p50 (0.3 to 1.2 ms) is below pgvector (5 ms) and the CPU (2 to 3 ms), so the small-corpus gate holds on this card. Residency: fp16 fits at 5M x 768 (7.8 GiB) and 5M x 1024 (10.1 GiB) and at 1M x 1536 (3.2 GiB) but not at 5M x 1536; int8 about halves the memory (10M x 768 at 8.5 GiB, 50 ms).
- **Expansion and DAG closure on the GPU.** Not worth building at these sizes: a bounded 3-hop expansion reaches 4 to 20 thousand nodes and takes 0.06 to 0.93 ms on one CPU thread, even on the 930M-edge graph, against 0.3 to 1.1 ms on the GPU; closure to depth 32 takes 0.4 to 0.7 ms on the CPU and 1.3 to 1.7 ms on the GPU. The work is too small to cover the dispatch and synchronisation cost; the GPU fails the "better than the CPU engine" gate for these stages at every size tested. A large frontier, deep caps or interleaved batches could change this; none was tested.
- **Personalised PageRank on the GPU.** Slower than the 24-thread CPU at every size (1M nodes: 94 ms against 58 ms) and only faster than one thread from 100k nodes. The kernel is a plain pull loop with one thread per node and no load balancing for hubs, so this is a first-kernel result, not a bound.
- **pgvector exact.** 85 ms at 1M x 1024 single client, with a pitfall: the default TOAST storage pushes a `halfvec` of 1024 or more dimensions out of line and an exact scan then costs 381 ms; `STORAGE PLAIN` on the column brought it to 85 ms.

## Consequence
Proposed for the main session (not written to the DECISIONS-LOG by this spike):
1. Default CPU engine for graph expansion, DAG closure and PPR (doc 64 3A.9 already expects this for closure); do not build the GPU expansion, closure or PPR kernels (WP13) on this evidence. Reopen only with large frontiers or interleaved batches measured on real graphs.
2. Keep the GPU vector top-k kernel behind its gates: it is the stage with a large, repeatable gain (5 to 10 times), within the residency limits above. int8 is worth keeping for residency (twice the rows) and speed, still opt-in and subject to the recall gate on real embeddings.
3. If pgvector exact stays a backend, the schema must set `STORAGE PLAIN` on embedding columns of 1000 or more dimensions.
4. Still to do before the gates close: real-embedding recall for int8 (R6), parity on a scope-mask workload, a shadow checker run, the soak, freshness under write load, a second run of everything, and the Linux run.

## Limits
- Synthetic vectors and planted queries; recall 1.0 is a property of well-separated planted neighbours as much as of the kernels. Real embeddings are clustered and may sit close to ties; int8 recall must be re-measured on them.
- One run per configuration; no spread across runs. One machine. The GPU score kernel is a first implementation at about 0.4 TFLOP/s.
- The graph is synthetic with my own degree and kind mix, not the Vault graph; reached sets are small because 3 hops at mean degree 10 reach thousands of nodes.
- The CPU baselines at 1 and 4 threads stop at 1M rows; the CPU engine uses fp32 storage.
- The B580 allows allocations far beyond its heap through paging; a product build must check the budget itself (doc 64 section 6).

## Soak (gate "stability")
Started 2026-11-22 at about 19:05 UTC and meant to run 24 hours (stop file `soak.stop`, log `s28-soak.csv`, one line per minute). It is running now; its result is **not in this record yet**. What it does: a 1M x 1024 fp16 vector index (2.4 GiB), a 93M-edge graph and a 100k-node PPR graph stay resident on the B580 (about 3 GiB) while a loop runs about 20 iterations per second (one top-10 query, one 8-seed 3-hop expansion, a PPR every tenth iteration); every five minutes the GPU results are compared with the CPU (vector recall at least 0.9 on four queries and exact per-level digests of an expansion); every ten minutes a 40 GiB allocation is attempted (an injected allocation failure) and the next parity check shows the resident indexes still answer correctly. Next to it the Vulkan bench renders the combined frame in a loop (`renderer-soak`, 300 frames per second in bursts over the 30 cells, 2 frames in flight, one log line per second) on the same card. The log records errors, parity failures, per-minute p50 and p99 of each query, device memory allocated by the process and the process working set after a forced collection.
Pass: zero errors, zero parity failures, every injected fault recovered, device allocation constant, no device loss. Not exercised: a deadline fault, a forced device loss, the freshness gate under writes.
A 6-minute smoke run before the start: 0 errors, parity ok, 4 061 iterations, flat memory (working set rose 40 MB per minute until a forced collection showed it was garbage-collector slack).
