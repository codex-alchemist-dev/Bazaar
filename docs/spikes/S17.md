# Spike S17: FreeLLMAPI surface: key scoping, fallback, subscription reachability

Branch: `docs/S17-result` (read-only half: source and docs only). Design source: `docs/design/35-spikes-plan.md` (row S17). Gateway design: `docs/design/05-model-gateway.md`.

## Question

Read FreeLLMAPI's `server/src` and docs for: key scoping, `sk-cp-` client-profile keys, chat family lock, usage and health, prompt logging. Check whether a forced fallback can reach a model the caller excluded, and whether any subscription login (Pro or Max) is reachable through the Claude route.

This record covers the read-only half only. The live half (run the pinned version with non-Claude free keys and test a forced fallback) was NOT run: no keys, no provider calls, nothing that spends money.

## Pass criteria (from the plan, fixed before the first run)

"Forced fallback never reaches an excluded model (pass: policy upstream); else unpolicied upstream. Anthropic key not loaded into FreeLLMAPI (default, Q3)."

## Answers

### Q1. Can an API key be scoped to a subset of models?

**Unknown, with no documented per-caller model allowlist found.**

- Callers authenticate with one unified `freellmapi-…` bearer key. README: "Keys are stored encrypted" and apps "only ever see a single unified `freellmapi-…` bearer token" (https://github.com/tashfeenahmed/freellmapi). The architecture page says callers use "a single `freellmapi-…` bearer token" and does not say the token can be limited to models (https://github.com/tashfeenahmed/freellmapi/blob/main/docs/en/architecture/00-high-level-index.md).
- Client-profile keys `sk-cp-…`: the REST API page says they authenticate `/v1/messages` and the Gemini routes "with the profile's enforced prompt injected." It says keys are "scoped away from this model" in the model-listing section, with no mechanism given (https://github.com/tashfeenahmed/freellmapi/blob/main/docs/en/api/01-rest-api.md).
- Code: `resolveAuth` accepts unified keys and `sk-cp-*` profile keys; a profile key "authenticates inference only and can carry a server-enforced system prompt" (`server/src/routes/anthropic.ts`). Model access comes from named profile chains (`profile_models`), selected by the caller's `auto:<name>` model string (`server/src/services/router.ts`, `getActiveChain`). The code I read does not show a key being bound to a profile, so a profile key's model access is not confirmed.
- Provider keys are scoped by model availability (`routableKeyIdsForModel`, `skipKeys`), which is different from a caller's key being scoped.
- Conflict: release v0.16.6 (20 Oct) reads "Unified key only; client-profile keys get 403" (https://github.com/tashfeenahmed/freellmapi/releases). That contradicts the REST page and the `resolveAuth` code. Which applies to the pinned version is unknown.

### Q2. When a fallback happens, can the request reach a model the caller excluded?

**Yes, in the source as read. FreeLLMAPI does not enforce a caller-side exclusion, so Bazaar must enforce policy upstream (the plan's "else unpolicied upstream" branch).**

- The fallback loop `runFallbackLoop` (MAX_RETRIES = 20) retries through the candidate chain (`groupChain ?? resolvedChain?.chain`) (`server/src/routes/proxy.ts`).
- `routeRequest` starts from `prefetchedChain ?? getActiveChain(db)`, filters to enabled models, and walks the whole ordered chain. A pinned `preferredModelDbId` is moved to the front. If it is not in the chain, it is injected from `models` with `enabled = 1`. Only `skipModels`, `skipPlatforms`, `skipKeys` and capability or size gates exclude candidates. Nothing caller-supplied narrows the chain (`server/src/services/router.ts`).
- Pinned models: `routePinnedModel` "NEVER substitutes a different model", but `routeRequest`'s fallback does not use that path (`server/src/services/router.ts`).
- Caller-facing: "Plain `auto` follows your active fallback chain"; `auto:*` profiles "rank every enabled model, ignoring your chain order" (https://github.com/tashfeenahmed/freellmapi/blob/main/docs/en/api/01-rest-api.md).
- The API page says "failover never crosses models" only for embeddings. Chat fallback is not family-locked in the code read (the chain is not restricted to one family).
- Response header `X-Fallback-Attempts` reports hops (REST API page), so the operator can see a fallback after the fact. It does not prevent one.

### Q3. Is a subscription login (Pro or Max credentials) reachable through FreeLLMAPI?

**No subscription or OAuth credential path found in the source read. Runtime behaviour: unknown (not run).**

- `server/src/routes/anthropic.ts` (`POST /v1/messages`) authenticates only with `x-api-key` or Bearer tokens, which identify a FreeLLMAPI key or profile. It "contains no OAuth, Claude Code login, or subscription-login handling." `X-Claude-Code-Session-Id` is used only for session affinity. The caller's token is not forwarded upstream: upstream calls use the key the router selected.
- `server/src/providers/index.ts`: authentication is by Bearer or API keys; no OAuth, Pro, Max or Claude Code credential type. "Anthropic" appears only in a LongCat comment.
- Docs: Claude Code "can run against your free pool" with a unified key. Setup uses `ANTHROPIC_AUTH_TOKEN` (Bearer), not `ANTHROPIC_API_KEY` (REST API page). The README and API page mention no subscription login.
- Release v0.16.0: "Claude Code tiers" maps the Claude model names to `tier:pro`, `tier:mid` or `tier:normal` (releases page). This is a routing label, not a credential path. The name "tier:pro" could be read as a subscription tier, and the code that maps it was not read. Unknown whether it has any subscription effect.
- Not read: `server/src/services/anthropic-map.ts` (Claude-name mapping) and `middleware/inference-auth` (the path returned 404). The Claude Code legal terms (`code.claude.com/docs/en/legal-and-compliance`) were relayed only through the local note, not fetched in this pass; they say Pro and Max credentials may not be routed through third-party developers' tools.
- Consistent with Bazaar's design: `docs/design/05-model-gateway.md` and `docs/deep-dives/Bazaar.Server.md` item 11 keep subscription logins off every route. The Anthropic key is not loaded into FreeLLMAPI (C14).

### Q4. What does FreeLLMAPI document about per-agent whitelists?

**Nothing per-agent. No whitelist, allowlist or per-client model restriction is documented.**

- README and API reference describe one unified key and per-provider-key monthly caps. No per-client model allowlist. The API reference "Not found" list: `forcedModel`, `/api/keys/{id}/access`, allowed-model lists, subscription, OAuth, Pro/Max (checked in this pass).
- Architecture page: no per-agent whitelist or allowlist; under "Not yet supported" it lists "Per-user billing / multi-tenant auth," and the gateway is "single-user by design."
- SECURITY (quoted in the local note): "FreeLLMAPI is a single-user, trusted-network tool," binds `127.0.0.1` by default, and has "no multi-tenant auth by design." The opt-in Host-header allowlist is a DNS-rebinding guard, not a model policy.
- The only restriction-like wording is "scoped away from this model" in the model listing (Q1), with no documented mechanism.
- Bazaar's design already says this: `docs/deep-dives/Bazaar.Server.md` item 11 and `docs/design/05-model-gateway.md` ("Policy", "Delegated routes") put per-agent enforcement in Bazaar.Server's own gateway.

## Other S17 checklist items (not closed)

- **Chat family lock:** not family-locked in code read (Q2). Embeddings are family-locked per the REST page.
- **Usage and health:** `/v1/usage` is restricted to the unified key (`proxy.ts` excerpt). Dashboard behaviour not read in full.
- **Prompt logging:** not examined. Gap.
- **Pinned version:** not chosen. The code read is `main` at 2026-10-25, which the local note says moves fast (v0.16.x in October 2026). Results may change by version.

## Result

**Partial: the read-only pass answers all four questions, but the plan's pass criterion ("forced fallback never reaches an excluded model") is not tested live, and the source read says it can fail.**

- Q1: unknown. No documented caller-key model allowlist. `sk-cp-` profile key model scope not confirmed, and v0.16.6 conflicts with the docs on whether `sk-cp-` works at all.
- Q2: yes, fallback can reach any enabled chain member the caller did not request. Failover does not honour a caller exclusion list (none exists).
- Q3: no subscription or OAuth path in the code read; runtime not tested.
- Q4: none documented.

Gap summary: `anthropic-map.ts`, `extractApiToken` in `proxy.ts` and the full auth middleware were not read. The live forced-fallback test and the prompt-logging, usage and health checks need the pinned version and free keys, which are owner-supplied, so they are not done here.

## Consequence

- The S17 "else unpolicied upstream" branch applies to the source read: Bazaar.Server's own gateway must enforce per-agent model policy and check the served model and `X-Fallback-Trail`/`X-Fallback-Attempts` after every call (`docs/design/05-model-gateway.md`). This matches what the design already assumes; no design change is needed.
- Do not rely on FreeLLMAPI `sk-cp-` profile keys for per-agent scoping until the v0.16.6 conflict is settled in the pinned version.
- Live half (owner): pick a pinned version, run a forced-fallback test with non-Claude free keys and an excluded model, and record the served model. Only then does this result become pass or fail. The main session should write the DECISIONS-LOG entry after that run.
- No DECISIONS-LOG change from this read-only pass.
