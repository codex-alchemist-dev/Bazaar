# Spike S25: Restore drill, Linux and Windows halves

Branch: `claude/project-thread-1m8ydd` (the session's designated branch; the plan names `spike/S25`, so the branch can be renamed if the owner wants it). Throwaway code is in `spikes/S25/`. Design source: `docs/design/35-spikes-plan.md`, `docs/design/33-backup-dr-and-export.md`.

## Question
Can a Postgres 18 base backup plus WAL archive restore the GC log to a chosen timestamp, and does the proposed rollback policy (sequence floor plus a `system` recovery entry, doc 33 and C10) leave no sequence gap and no sequence reuse after the recovery entry?

## Pass criteria (fixed before the first run)
Copied from `spikes/S25/README.md`, committed in `a0334da` before any counted run. The file has not changed since.

- **P1 Restore matches the target.** At the restore timestamp T, every GC has the same row count, max `seq` and `head_seq` in the restored database as in the source at T. Restored replay timestamp is at or before T, and no row committed after T is present.
- **P2 Floor and recovery entry.** For each GC, `apply_recovery` writes one `system` entry at `seen_head + 1`, with the lost range recorded. `head_seq` equals the entry's `seq`.
- **P3 No gap after the recovery entry.** No row in the lost range. Rows before it are contiguous from 1. Rows from the entry onward are contiguous.
- **P4 No reuse.** The first message appended after recovery gets `seen_head + 2` in every GC.
- **P5 Measured, against the proposed budgets (doc 33).** Archive lag under RPO 1 h; restore time reported as a lower bound against RTO 1 d.

Fail consequence: any failed P1 to P4 in any run fails the spike.

## Time-box
2 days (doc 35). The drill itself took about a minute per run; the whole spike took under an hour of wall time, including harness fixes.

## Method
- **Environment.** Cloud container, Linux 6.18 kernel, 4 vCPU (Intel Xeon 2.1 GHz), 16 GB RAM, 252 GB disk with about 30 GB free. Docker 29.9.2 (overlayfs), started by hand with `dockerd`. Image `pgvector/pgvector:pg18`, PostgreSQL 18.6 (Debian).
- **Source.** `wal_level=replica`, `archive_mode=on`, `archive_command = sh archive.sh %p %f`. The archiver copies to a temp name, runs `sync`, checks the size, then renames. It fails on any doubt, so PostgreSQL keeps the segment. Base backup with `pg_basebackup -Fp -X stream`.
- **Data (synthetic).** 4 GCs, hash-partitioned by `gc_id` into 4 partitions. 100,000 messages per GC before T (400,000 rows). 20,000 per GC after T (80,000 rows, the range the rollback discards). Sequences are per GC, assigned under the GC row lock.
- **Drill.** Base backup, batch A, archive, pick T with `clock_timestamp()`, batch B, archive, record each GC's head as the "surviving source" view, then `kill -9` the source. Restore a fresh copy of the base backup with `recovery_target_time = T` and `recovery_target_action = promote`, using `restore_command` from the archive. Compare with the snapshot taken at T. Then run `apply_recovery` per GC with the surviving heads, check the system entries, append one message per GC, and check the next seq.
- **Not used.** pgBackRest and WAL-G (the doc 33 Linux choice) were not tested. This is a bare `pg_basebackup` plus a copy-based archiver.

## Result
**pass.** All three runs passed P1 to P4, with each GC's restored head equal to the source at T, no rows after T, and the lost range (`lost_from` to `seen_head`) absent. After the recovery entry, the sequence is contiguous, and the first post-recovery append gets `seen_head + 2` in every GC. Restore to promotion took 1.95 to 2.10 s on 400k rows (57 MB). Archive lag was 0.74 to 0.80 s, far inside the 1 h RPO. These numbers say nothing about the 1 d RTO for a full owner's PC rebuild. The data volume (480k rows, 57 MB) is far below a real instance, so the restore time is a lower bound only.

What this does not show: it tests the mechanism, not the production writer, and it does not test the Windows half, pgBackRest or WAL-G, an offsite store, or a real client cache as the surviving source. The "surviving source" here is each GC's head as read from the source just before the kill. See Limits below.

## Consequence
- The Linux mechanism behind C10's restore policy works on PostgreSQL 18.6: PITR to a timestamp, a sequence floor above what the surviving source saw, a `system` entry that records the lost range, and no reuse afterwards. The policy in doc 33 is viable on this path. The main session should decide whether to record it in DECISIONS-LOG as confirmed for the Linux path. Not written here, since DECISIONS-LOG is the main session's record.
- Doc 04 WP4 and doc 33 WP8 and WP9 (restore runner, recovery entry in the GC writer) can rely on this shape. The production writer still needs its own tests.
- Still open: the owner's PC half (Windows `pg_basebackup` under the service account, Hyper-V; doc 35 Wave B), a real RTO measurement at realistic volume, and whether pgBackRest or WAL-G is the Linux engine.

### Limits
1. Bare `pg_basebackup` and a copy-based archiver. pgBackRest and WAL-G were not tested.
2. Local archive only. The 1 h RPO here measures archive lag, not offsite age, which doc 33 requires for the RPO.
3. Synthetic data, 480k rows total (400k restored). The restore time is a lower bound on RTO.
4. The surviving source is the source's own head read before `kill -9`, not client caches or an offsite audit head.
5. The kill came after the archive had caught up, so the loss window was zero by construction. The loss window under a live crash was not measured.
6. Not tested: the restore runner's refusal on a non-empty target, the schema-mismatch refusal, or a latest-recoverable-point restore (doc 33 rule 2).

## Windows half
Same drill, same pass criteria (P1 to P4 fixed in `spikes/S25/README.md` before the Linux runs; unchanged), same SQL, run natively on Windows with `spikes/S25/windows/run_drill.ps1` and `archive.ps1`. Those scripts live on branch `spike/S25-win` (spike code stays on spike branches; only this record reaches main).

### Method (Windows)
- **Environment.** Owner's PC: Windows 11 Pro 10.0.26300, x64, 24 logical CPUs, NTFS, local disk. PostgreSQL 18.6 from the EDB Windows binaries zip (`postgresql-18.6-1-windows-x64-binaries.zip`, SHA-256 `FBE23DA234EE31547BF8A36D29DFD81E82B849DF2D2B78D2EECB43D360252F8C`), unpacked, no installer, no Windows service. Run as the interactive user, not a service account. No pgvector (the drill schema does not use it).
- **Source and drill.** As in the Linux half: `wal_level=replica`, `archive_mode=on`, 4 GCs hash-partitioned, 100,000 messages per GC before T, 20,000 after. The archiver (`archive.ps1`) copies to a temp name, flushes, checks the size, then renames. Base backup with `pg_basebackup -Fp -X stream`. The source is killed with `taskkill /F /T` on the postmaster (no clean shutdown). Restore: a copy of the base backup with `recovery_target_time = T`, `recovery_target_action = promote`, `restore_command` using `copy`.
- **Harness bugs fixed before the counted runs** (no change to criteria): `pg_ctl start` hung when run with its output piped or with `Start-Process -Wait`, because the server inherits the handles; the script now starts it detached and polls `pg_isready`. Backslashes in the `restore_command` path were eaten by the `postgresql.auto.conf` string parser (recovery then ended before the target); the path now has doubled backslashes. These showed up as failed starts, not as wrong results.

### Runs (Windows)
Three counted runs on 2026-10-25, fresh data directories each time.

| 2 | pass | 3744 ms | 1843 ms | 1067 ms | 3082 ms |

### Result (Windows)
**pass.** P1 to P4 hold in all three runs on Windows with PostgreSQL 18.6: restored rows match the source at T, the sequence floor and `system` entry leave no gap, and no sequence is reused. Archive lag is far inside the 1 h RPO; the restore time is a lower bound only (synthetic 480k rows).

Not shown: running under a Windows service account (the owner's PC case, doc 35 Wave B); Hyper-V; pgBackRest or WAL-G on Windows (neither tested); an offsite archive; behaviour with antivirus or a slow disk; a clean-shutdown versus live-crash loss window (the archive had caught up before the kill, as in the Linux half). The tested mechanism is bare `pg_basebackup` plus a copy archiver, not the production restore runner.

### Consequence (Windows)
- The C10 restore policy works on both paths tested; the mechanism has no Windows-specific gap. Recording that in DECISIONS-LOG is the main session's call.
- Windows implementation notes for the archiver and restore runner: `archive_command` and `restore_command` run through `cmd`, so quote paths and double backslashes in `postgresql.conf` strings; start the server detached from any pipe the tool is reading.
- Open: a registered Windows service run (the owner's PC runs used a non-admin account, not a service), and archive engine choice (pgBackRest or WAL-G on Windows).

## Owner's PC run, service-style account (Windows)

Same drill, same pass criteria, same SQL and archiver as the Windows half above. The NUC is gone, so this run is on the owner's PC (Windows 11 Pro 10.0.26300, x64). It runs under a local, non-admin account, `CKORVIX_V1\bzdrill`, created for the drill, not the interactive owner account. PostgreSQL is started with `pg_ctl` under that account. It is not registered as a Windows service: registering needs an elevated shell, and the drill did not need one.

### Method (owner's PC)
- **Environment.** Same machine as the Windows half. PostgreSQL 18.6 EDB binaries zip, SHA-256 `FBE23DA234EE31547BF8A36D29DFD81E82B849DF2D2B78D2EECB43D360252F8C`, staged at `V:\s25-drill\pgsql` outside the repo.

- **Source and drill.** As in the Windows half: 4 GCs, 100,000 messages per GC before T, 20,000 after, `kill`ed postmaster, restore by `copy` to T with promotion.
