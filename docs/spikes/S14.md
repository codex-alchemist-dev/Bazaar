# Spike S14: Graph layout tick and render cost (layout part only)

Branch: `spike/S14` (code stays there; only this record reaches main). Design source: `docs/design/35-spikes-plan.md`.

## Question
Graph: 5k and 10k nodes, render (Windows and Android) and server layout tick (layout stays server-side, C17)

## Pass criteria (fixed before the first run)
5k render at 60 fps with at most 10 ms draw; layout tick at most 8 ms at 10k on the NUC (the absolute budget from doc 19); Android not gated until measured

Fail fallback: none is stated in the plan row (the S14 row has no fallback column entry). The consequence of a fail is recorded in the Consequence section after the runs.

## Time-box
3 d

## Method
Built and run (all under `spikes/S14/` on branch `spike/S14`, commit aa4e75d; the criteria were committed first in e8f58d2):

- `Layout.cs`: ForceAtlas2-style layout. Barnes-Hut repulsion (theta 1.2), linear edge attraction, strong gravity toward the origin, FA2 adaptive global speed (swing and traction), per-node displacement cap of 100 units. One `Tick` is one full iteration over all nodes, so each tick is the same fixed unit of work. No Avalonia dependency.
- `QuadTree.cs`: Barnes-Hut quadtree in flat arrays, rebuilt every tick. Positions and forces are packed interleaved float arrays (x at 2i, y at 2i+1), as in LayoutFrame.
- Reverse gravity: `SetFocus` pins the focus node at the origin (the layout is translated), gives each node a ring target of 40 units per BFS hop distance, and adds a radial spring toward it. Warm start from the converged layout.
- Node addition: 1 percent new nodes (10, 50, 100) from the same generator, placed at the mean of their earlier neighbours with a small jitter, then warm start.
- Graphs: preferential attachment, m = 2 (average degree about 4), SplitMix64 seed 14, so the 1k, 5k and 10k graphs are prefixes of one sequence.
- Per N in {1k, 5k, 10k}: a cold start (500 ticks, reported for information), then warm-start scenarios: steady (30 warm-up ticks discarded, 300 measured), focus change (300 ticks from the change), node addition (300 ticks). Each is run single-threaded and parallel (`Parallel.For` over 4 x cores chunks; the tree build is serial).
- Timing: `Stopwatch` timestamps around each tick. Allocations: `GC.GetAllocatedBytesForCurrentThread` around each tick. Parallel runs report allocations on the coordinating thread only.
- Checks in every pass: parallel and single-threaded positions after 5 ticks are identical (max difference 0), so the parallel numbers are the same computation. Barnes-Hut against brute force on about 20 sampled nodes at the converged state: worst relative force error 0.080 (1k), 0.033 (5k), 0.040 (10k).
- Parameters: Kr 1.0, Kg 0.1, KRing 0.2, theta 1.2, FA2 jitter tolerance 1.0, max rise 0.5. They were not tuned for layout quality, so they are only roughly representative of a production layout.
- Build: Release, .NET SDK 10.0.401, with the project built from outside the repo, because `global.json` pins 10.0.402 and that SDK is not installed here. The root `Directory.Build.props` still applies (warnings as errors, nullable). Run with `spikes/S14/run.sh`. Each pass is a separate process (fresh JIT, graphs and layouts).
- Note on the three passes: a first set of three passes ran the same timing code before a `tree_cells` diagnostic column was added to the output. Its 10k single-threaded steady medians were 6.22, 6.27 and 6.32 ms, consistent with the reported set. Those files were replaced and are not reported separately.

Environment (this machine, all runs on 2026-10-25 UTC):
- OS: Windows 11 Pro, 10.0.26300.
- CPU: Intel Core Ultra 9 285K, 24 cores, 24 logical processors (Win32_Processor).
- RAM: 96 GB installed.
- Machine: ASUS desktop (model string "System Product Name").
- Runtime: .NET 10.0.13 runtime, SDK 10.0.401. GC: workstation, concurrent.
- Power plan: not captured (the `powercfg` query returned nothing).
- PostgreSQL: not used by this spike.

Not run, and said plainly: the render half (5k at 60 fps, at most 10 ms draw, on Windows and Android), the Android half, and the NUC. The absolute layout gate (8 ms at 10k on the NUC) was not measured. The NUC CPU model and core count are not recorded in the docs (doc 31, question 3, asks which Core Ultra generation the NUC is).

Caveat, not a gate: the layouts are not settled. The per-tick displacement at the end of a run is a single sample, not an average, and it stays at 0.1 to 0.4 units per tick (deterministic across runs). The reverse-gravity ring error (mean absolute difference between radius and ring target, in units) went from 56 to 79 at 1k, from 81 to 68 at 5k, and from 364 to 144 at 10k over 300 ticks. So these are per-tick costs in a not-yet-settled state. Ticks to settle, and whether the ring mechanism converges, were not measured. Doc 19's "focus change to settled layout, at most 1 s" is therefore untested here.

## Result
Inconclusive. The layout tick was measured relatively, on this machine only (Intel Core Ultra 9 285K, 24 logical processors, 96 GB, Windows 11, .NET 10.0.13). The absolute gate (layout tick at most 8 ms at 10k on the NUC) cannot be decided from this run, because the NUC was not run. On this machine, the 10k single-threaded steady tick has a median of 6.31 ms over three runs, a p95 of 6.5 to 6.6 ms, and a single-tick maximum of 7.67 to 8.20 ms. The parallel tick has a median of 1.87 ms. This is a statement about this machine: it does not establish whether the NUC meets 8 ms, and no factor between the two machines is assumed. The criteria do not say whether the 8 ms applies to the median or to every tick, so both are reported. The render half (5k at 60 fps, at most 10 ms draw) and the Android half were not run. Android is not gated, as the criteria say.

Relative scaling: single-thread steady ticks cost 0.31, 2.11 and 6.31 ms at 1k, 5k and 10k. Going from 5k to 10k nodes costs 3.0 times as much, more than the roughly 2.1 times an N log N model predicts; the cause was not investigated. Parallel ticks cost 0.12, 0.88 and 1.87 ms, and the 5k to 10k step is 2.1 times. Focus change and node addition cost about the same per tick as steady state at 10k.

## Consequence
- Doc 19: the layout budget ("server layout tick, 10k nodes, at most 8 ms on the NUC") stays [PROPOSED]. This record does not confirm it. Doc 19's "focus change to settled layout, at most 1 s" is untested (see the caveat above), so it needs a settle-time study before it can be checked.
- Doc 27 and the render gate: unaffected, because the render half was not run. The client-side render budget (5k at 60 fps, at most 10 ms draw) stays open for Windows and Android.
- Constellation WP3 (the layout engine, plan row S14): this record does not clear it on the NUC number. Its layout-tick gate is open until the NUC run. If the NUC misses 8 ms, the options (not decided here) are parallel ticks (about 3.4 times faster on this 24-core machine; NUC core count unknown), fewer nodes per view, or a lower tick rate. Settle time must be measured before any of them is chosen.
- Open question from the 5k add-node result: a 38 percent slowdown that the tree size does not explain. Check it on the NUC run before relying on the add-node cost.

The 8 ms NUC gate (doc 19) and the render gate (S14, Windows and Android) are OPEN. Layout stays server-side (C17). Doc 19 budgets stay [PROPOSED]."
