# Spike S14: Graph layout tick and render cost (layout part only)

Branch: `spike/S14` (code stays there; only this record reaches main). Design source: `docs/design/35-spikes-plan.md`.

## Question

Fail fallback: none is stated in the plan row (the S14 row has no fallback column entry). The consequence of a fail is recorded in the Consequence section after the runs.

## Time-box

## Method
Layout part only. The render half (5k at 60 fps on Windows, Android) was not run; it needs the owner's Windows desktop.

**Algorithm (spikes/S14/Layout.cs).** ForceAtlas2-style layout: Barnes-Hut repulsion over a quadtree rebuilt each tick (opening angle theta 1.2), linear attraction along edges, strong gravity toward the origin (Kg 0.1, scaled by mass), adaptive global speed (jitter tolerance 1.0, max rise 0.5 per tick), per-node displacement capped at 100. Pinned node and ring targets for reverse gravity (ring spacing 40, spring 0.2).

**Graphs.** Synthetic preferential attachment (Barabasi-Albert style), m = 2, seed 14: each new node links to two earlier nodes chosen in proportion to degree, average degree about 4. A 10k graph is the prefix of a 10,100-node graph from the same seed, so the 5k and 10k runs share structure. The add scenario uses the 1 percent extra nodes at the end of that graph.

**Seeds.** Graph 14; cold random start 1000 + N; focus node 7000 + N; added-node jitter 8000 + N. Results are deterministic: the parallel and single-threaded layouts agree exactly after 5 ticks (`par_vs_st_max_abs_pos_diff = 0` at 1k, 5k and 10k in every run). Barnes-Hut against brute force on about 20 sample nodes at theta 1.2: worst relative error 0.080 at 1k, 0.033 at 5k, 0.040 at 10k (identical in every run, since the graph and the converged state are seeded).

**What a tick is.** One call to `Layout.Tick()`: quadtree build, force pass over all nodes, swing and traction, speed update, position update. Measured with `Stopwatch` around the whole call. Per measurement set: 30 warm-up ticks discarded, then 300 measured ticks (`steady`, `focus_reverse_gravity` and `add_N_nodes` at 5k and 10k). The cold convergence run (500 ticks, single-threaded, reported for information) gives the warm start. Median, p95 and max are in each CSV.

**Threads.** `st` is one thread. `par` is `Parallel.For` over `min(4 x logical processors, 128)` chunks on the thread pool; the tree build and the position update stay single-threaded.

**Environment of the cloud runs (this container).** Ubuntu 24.04.5 LTS (kernel 6.18.44-fc), virtualised Intel Xeon Processor at 2.10 GHz, 4 logical processors, 16 GB RAM (16,477,348 kB), .NET SDK and runtime 11.0.0-rc.2.26504.105 (the SDK pinned on main's `global.json`), Release, workstation GC, concurrent GC, invariant globalization. Project retargeted from net10.0 to net11.0 for these runs. The spike branch's own `global.json` still pins 10.0.402, so the build ran from a directory outside the repo (as `run.sh` does).

**Earlier run set (spikes/S14/results/run1-3.csv).** Recorded as Windows 10.0.26300, x64, 24 logical processors, .NET 10.0.13. The CSVs do not record CPU model, RAM or the machine's name, so their hardware is not confirmed. The commit author's timezone (+0800) points to a developer's Windows machine, but nothing in the repo proves it is not the NUC; the owner should confirm. They predate the .NET 11 retarget, so they are not comparable with the cloud runs as hardware numbers, and must not be read as NUC numbers unless the owner confirms the machine.

**Not measured.** Render, Android, NUC, the real Constellation graph (synthetic only), memory pressure during a live server, and the server's own concurrency (the benchmark runs one layout at a time).

Caveat on the 8 ms gate: the criterion names the NUC and the cloud container is a 4-vCPU shared VM, so these numbers say nothing final about the NUC.

## Result
inconclusive. The absolute criterion (layout tick at most 8 ms at 10k on the NUC) is not decided. On this cloud container the 10k steady tick is about 9.7 ms single-threaded (above 8 ms) and about 4.8 ms with `par` on 4 vCPU (below 8 ms). Neither is decisive: the NUC's core count and speed are not known here, and the answer depends on whether the server runs the layout single-threaded or parallel, which the spike does not settle. The parallel tick cost also depends on core count (the earlier 24-thread machine gives about 1.9 ms at 10k against about 4.8 ms on 4 vCPU). Render half not run, so the 5k criterion is untested. Android not gated.

## Consequence
- **DECISIONS-LOG (for the main session to write; not written here):** record that S14's layout part is inconclusive on cloud relative numbers only (cloud 4 vCPU, .NET 11 rc.2: 10k steady tick 9.7 ms single-threaded, 4.8 ms parallel; the earlier 24-thread Windows machine: 6.3 ms and 1.9 ms). The 8 ms absolute layout gate on the NUC stays open. Layout stays server-side (C17 unchanged). The render half and Android stay open, pending the owner's Windows desktop.
- **Open question for the owner or main session:** which layout threading the server uses per view (single-thread or parallel, and the thread cap). The NUC gate can only be judged against the mode the server ships with. Per the configurability rule, the thread cap is an operator setting with a safe default, not a hard-coded value.
- **NUC runbook step (Wave B):** on the NUC, install the .NET SDK version from main's `global.json`, run `spikes/S14/run.sh <outdir>` (three passes, Release), and save the CSVs. Record CPU model, physical and logical core count, RAM, OS, power plan and the `.NET` runtime line from each CSV header. Judge the criterion on the 10k steady median in the mode the server will ship with, and record both single-threaded and parallel. A median at or under 8 ms passes. Over 8 ms fails and reopens the layout design (fewer nodes per view, a coarser tick, or a different algorithm), which needs a new design decision, not a tuning pass.
- **Render half (Wave C, owner's Windows desktop):** run the 5k render at 60 fps, 10 ms draw criterion through the Avalonia client spike; not started.
