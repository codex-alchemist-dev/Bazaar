# Spike S1 runbook: PostgreSQL 18 service and pgvector on the NUC

Runbook for the owner. Code stays on branch `spike/S1`; only `docs/spikes/S1.md` reaches main. Design source: `docs/design/35-spikes-plan.md` (catalogue row S1).

## 2. Question

Can PostgreSQL 18 (EDB install) run as a service on the NUC image with a pgvector MSVC build holding one `halfvec` profile (C39), and does the service come back after a restart?

## 3. Pass criteria

Fixed before the first run; do not edit after running. Copied from doc 35:

- Service survives reboot.
- `vector` loads.
- FTS and vector queries return expected rows.

"Expected rows" must be written down as a fixture with expected row IDs before run 1 (open question 1).

## 4. Fail consequence and fallback

Fail: Linux VM for search (doc 35 wording, copied as written). This conflicts with C23 and doc 03; see open question 7. Until resolved, a fail blocks docs 03, 04 and 18, the docs S1 unblocks.

## 5. Time-box

1 day, a hard stop. At expiry the result is recorded as `inconclusive`. An extension needs owner approval (open question 5 covers what the day counts).

## 6. Prerequisites and environment

The owner needs:

- The NUC, with an elevated (admin) PowerShell.
- The EDB PostgreSQL 18 Windows installer (source, version and checksum: open question 3).
- A Visual Studio C++ build environment for the MSVC build (toolset: open question 3).
- A pgvector release tag (open question 3).

Record these in the record's Method section:

- Windows edition and build: `Get-ComputerInfo | Select-Object WindowsProductName, WindowsVersion, OsBuildNumber`
- CPU and RAM: `Get-CimInstance Win32_Processor | Select-Object Name` and `Get-CimInstance Win32_ComputerSystem | Select-Object TotalPhysicalMemory`
- PostgreSQL version: `SELECT version();`
- pgvector version: `SELECT extversion FROM pg_extension WHERE extname = 'vector';`
- .NET version: only if a .NET client is used. S1 does not need one; record `dotnet --list-runtimes` only then.

## 7. Safety rules

- Use a scratch database only (`bazaar_spike_s1`). No live Bazaar data.
- S1 makes no model calls and needs no API keys, so no spend cap applies.
- Passwords and keys never go into git, the record or chat. Keep the PostgreSQL superuser password outside the repo (open question 4).
- Scripts go under `spikes/S1/` on `spike/S1`. They are throwaway: not shipped, not merged.
- Reboot the NUC only when no other work is running on it.
- Never push `spike/S1` to main or touch the default branch.

## 8. Steps

Each step names what to record. Record in `docs/spikes/S1.md` on `spike/S1`.

1. **Branch and criteria.** `git fetch origin`, then `git switch -c spike/S1 origin/main`. Copy sections 2 to 4 of this runbook into `docs/spikes/S1.md` and commit before any run. Record the commit SHA; it proves the criteria were fixed first.
2. **Environment.** Run the commands in section 6. Record every value.
3. **Install PostgreSQL 18.** Run the EDB installer with the service option (options: open question 3). Then run `Get-Service postgresql*` and `Set-Service -Name <service> -StartupType Automatic`. Record installer version, install directory, data directory, service name and start type. Service account: open question 6.
4. **Confirm the service.** `Get-Service <service>` shows Running. Connect as the superuser to the default database and run `SELECT version();`. Record the output.
5. **Build pgvector.** Follow the pgvector project's Windows build instructions for the tag from open question 3, pointed at the EDB install. Exact commands and flags are open question 3; do not improvise them. Record the tag, commit SHA, and any build errors.
6. **Load the extension.** `CREATE DATABASE bazaar_spike_s1;`, then in that database `CREATE EXTENSION vector;`. Record the result and `extversion`. This is the "`vector` loads" check.
7. **Create the fixture.** In `bazaar_spike_s1`, create table `s1_block` with:
   - `id uuid primary key default uuidv7()` (native in PostgreSQL 18, doc 04)
   - `profile_id uuid not null` (one profile per install, C39)
   - `body text not null`
   - `tsv tsvector generated always as (to_tsvector('english', body)) stored` (shape from doc 18)
   - `embedding halfvec(N)`, with N from open question 2

   Add a vector index using cosine ops (doc 18 HNSW, PROPOSED; parameters open) and a `tsv` index (open question 8). Insert a fixed set of rows with fixed text and fixed vectors. Save the SQL under `spikes/S1/`. In the same folder, write the expected row IDs for one FTS query and for one vector query filtered by `profile_id`. Commit this before run 1.
8. **Query check.** Run both queries. Record the returned IDs and whether they match the expected IDs.
9. **Reboot.** `Restart-Computer`. After sign-in, record the boot time with `(Get-CimInstance Win32_OperatingSystem).LastBootUpTime`. Check that `Get-Service <service>` is Running with start type Automatic, then repeat step 8. Record the service state, the IDs returned, the match result, and the boot-to-Running time as an observation only (doc 35 sets no timing threshold).
10. **Decide.** Apply section 11 to the results.

## 9. Three runs

Do steps 8 and 9 three times. Measure in each run:

- Service state after boot and its start type.
- `vector` `extversion`.
- Whether the FTS IDs match the expected IDs.
- Whether the vector IDs match the expected IDs.
- Boot-to-Running seconds (report median and spread; this value is informational).

A run passes only if all pass criteria hold in that run. The spike passes only if all three runs pass. Enter results in the run table of section 10.

## 11. Consequence

The main session writes the DECISIONS-LOG entry (number assigned by the main session) for each outcome:

- **Pass.** Entry: PostgreSQL 18 as a Windows service with pgvector and one `halfvec` profile meets S1 on the NUC, with restart verified. Unblocks doc 03 (the Postgres dependency and the NUC acceptance checklist), doc 04 (Postgres on Windows as the relational and vector store) and doc 18 (Vault index on Windows).
- **Fail.** Entry: the failed criterion and the owner's chosen fallback. The plan's fallback is a Linux VM for search. This reopens the Windows search choice in C23 and doc 03. Docs 03, 04 and 18 stay blocked until the entry lands.
- **Inconclusive.** No DECISIONS-LOG entry. Record the cause under Findings. The spike stays open until the owner approves an extension or a re-run. Docs 03, 04 and 18 stay blocked.

Only `docs/spikes/S1.md` is merged to main. Code and scripts stay on `spike/S1`.

## 12. Open questions

1. **Expected rows.** Doc 35 does not define the fixture or the expected IDs. They must be fixed before run 1.
2. **Dimension N and embedding model** for the spike profile. Docs 04 and 18 leave N to setup (doc 18 Q4).
3. **Install and build details.** EDB installer version, checksum and options; pgvector tag; MSVC toolset; exact build commands. None are in the docs.
4. **Superuser password location** on the NUC, outside git. No Windows location is decided.
5. **Time-box meaning.** Does the 1 day count elapsed or working time? Do three runs need three reboots, or three query passes after one reboot? Should a crash or power-off test be added? Doc 35 says only "restart".
6. **Postgres service account.** Doc 03 requires a dedicated local account for the host, never Administrator. Doc 03 does not decide the account for Postgres.
7. **Conflict.** Doc 35's fallback ("Linux VM for search") against C23 (Windows keeps `ts_rank`, OSI-only) and doc 03 ("Postgres FTS always usable"). Not resolved here.
8. **Index and text config.** Index type for `tsv`, HNSW parameters, and `english` or `simple` for full text (doc 18 Q5).
9. **Windows edition.** Doc 03 defaults to Server pending a licence answer. Record the NUC's edition; it may affect the result.
10. **Owner confirmation** of doc 35 Q1 (spike branches, records on main). The plan's default is yes.
