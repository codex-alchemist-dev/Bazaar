# Spike S4 runbook: Service recovery

Runbook for the owner, to run on the owner NUC. Code stays on branch `spike/S4`; only `docs/spikes/S4.md` reaches main. Design source: `docs/design/35-spikes-plan.md`.

## 1. Question

Does the Bazaar host come back within 60 s after a failure, and does a turn killed mid-run resume from its last persisted step without a duplicate message?

## 2. Pass criteria

Copied from doc 35 (fixed before the first run; do not edit after running):

> Host restarts within 60 s; turn resumes from last persisted step (06 `turn_step`) with no duplicate message

## 3. Fail consequence and fallback

The S4 row in doc 35 has no "fail:" clause, so the plan names no fallback. Until the owner names one, a fail blocks 03 WP8 and 06 WP3 and nothing else. See open question 1.

## 4. Time-box

1 day, a hard stop (doc 35). Expiry records `inconclusive`. Any extension needs owner approval. Record start and stop times in the record.

## 5. Prerequisites and environment

- Spike S1 has passed: PostgreSQL 18 runs as a Windows service on the NUC, survives a reboot, and `vector` loads.
- An admin shell on the NUC.
- A scratch target only: a scratch VM, or a copy of the data root plus a throwaway database created for this spike. Never the live Bazaar database or data root.
- The host runs under the dedicated local service account (doc 03 floor: never Administrator).
- A fake model gateway only (doc 35 Testing: real models only in S17 to S19).
- Record before the first run:
  - OS build (`winver` or `systeminfo`)
  - CPU model and RAM in GB
  - PostgreSQL version (`SELECT version();`)
  - .NET version (`dotnet --list-runtimes`) and the host build identifier

## 6. Safety rules

- Kill tests run only on the scratch target. Stop if any path or database name is not the scratch one.
- The hard kill is the test. No step may pass because of a shutdown hook; doc 06 says nothing relies on shutdown hooks.
- `sc stop` is used only in step 7.2.
- No keys, tokens or personal data go into logs kept in git. Run logs stay local; only the record reaches main.
- S4 has no model spend (fake gateway). If a real provider key is loaded, stop.

## 7. Steps

Repeat every step for each run (section 8). Write each value in the run table as you go.

**7.1 Configure and check service recovery (`sc failure`)**
1. Install the host as a Windows service under the service account, with Automatic start. The install command is open question 9.
2. Apply the failure actions from `host.service.restart_delays_minutes` (default 1, 1, 5) and `host.service.failure_reset_hours` (default 24). The `sc failure` arguments and units are open question 3.
3. Read back with `sc qfailure <service>`. Record the output and whether it matches the two settings.

**7.2 Measure ShutdownTimeout**
1. Start the host with a long scripted fake turn (script shape: open question 6).
2. Run `sc stop <service>` while the turn is running.
3. Record the seconds from the stop request to process exit, and the last `turn_step` n written before exit.
4. Compare with `host.shutdown_timeout_seconds` (default 20; allowed 5 to 120). Record whether the drain finished inside it.
5. This step measures the drain only. It is not part of the restart criterion.

**7.3 Kill mid-turn**
1. Start the service. Wait until `/health/ready` returns true on the status port (open question 5).
2. Start one scripted test turn with at least one tool step and several model steps before a final post.
3. When at least one `turn_step` row exists and the final post has not been written, find the service PID (`sc queryex <service>`) and hard-kill it (for example `taskkill /F /PID <pid>`). Record the kill time and the last persisted n.
4. Record restart seconds: kill time to the first `/health/ready` true. Pass on this sub-step is 60 s or less.
5. Wait for the turn to finish. Query `turn_step` and the GC for the test turn. Record the resume point (last n before kill, first n after restart), any completed tool re-executed (expected none), and the duplicate count (messages beyond the one expected post).

**7.4 Kill between two persisted steps (key case)**
1. Same setup as 7.3.
2. Poll `turn_step` until max(n) = k, then hard-kill before row k+1 is written. The boundary method is open question 6. Record k and the row count at kill time.
3. Restart and measure as in 7.3.4 and 7.3.5.
4. Expected per doc 06: resume from the last persisted step; no completed step repeated; no duplicate message. An in-flight tool that is not idempotent is recorded as `unknown`, and that is noted, not counted as a duplicate.

**7.5 Clean up**
1. Stop the service and remove the scratch database or data copy. Keep the local logs for the record.

## 10. Consequence

The owner or main session writes the outcome to the record. The main session then writes a DECISIONS-LOG entry (next free ID):

- **Pass:** Windows recovery configuration (03 WP8) and the turn resume rule (06 WP3) are confirmed on the NUC. Unblocks 03 WP8 (Windows module: service, recovery read-back) and 06 WP3 (lease and crash-recovery job). Note that the Windows recovery facts in 03 Conflict 2 are partly closed for this host.
- **Fail:** no fallback in the plan. 03 WP8 and 06 WP3 stay blocked. The main session asks the owner for a fallback (open question 1) and does not build the affected area.
- **Inconclusive** (time-box expired, or the between-steps boundary could not be reached): same blocked status as fail. The owner decides any extension.

## 11. Open questions

1. **Fail fallback.** The plan gives none for S4. Proposed: none, until the owner names one.
2. **Conflict: restart delay vs 60 s.** `host.service.restart_delays_minutes` defaults to 1, 1, 5 (doc 03). The first delay alone is 60 s, which leaves no time for the start. Not fixed here; owner or doc 03 to resolve.
3. **`sc failure` arguments and units.** Doc 03 gives setting names and defaults only. Confirm the syntax and units with `sc failure /?` on the NUC. Also confirm that failure actions fire on a hard kill and not on `sc stop`; doc 03 says these platform facts are unverified.
4. **Which "ShutdownTimeout".** The plan says ShutdownTimeout. Doc 03 has `host.shutdown_timeout_seconds` (default 20). The .NET host shutdown default and the SCM stop timeout have no source in the docs (doc 03 Conflict 2). Which one is measured?
5. **Restart end point and status port.** The runbook uses `/health/ready` true (doc 03) as "restarted". The status port has no default; the setup wizard chooses it. Owner to confirm.
6. **Step boundary and scripted turn.** The docs do not say how the test finds the boundary between two `turn_step` rows, or the shape of the scripted turn (step count, which tool step is idempotent). Any test hook must not be a shutdown hook.
7. **Lease length.** Doc 06 names `agent_lease(expires_at)` and a heartbeat but gives no value. Resume time after a kill depends on it, and the 60 s budget may not include it.
8. **Build under test.** Doc 03 WP1 to WP5 and doc 06 WP1 to WP3 are not built yet. Which host build and branch run on the NUC is not stated.
9. **Install command.** Doc 03 leaves the admin CLI (`bazaar-admin`) open. The runbook assumes plain `sc` steps until that is decided.
10. **Idempotent post.** Doc 03 and doc 06 require idempotency keys for side-effecting tools, but the GC post path and key format are not stated. This test measures whether replay can double-post.
