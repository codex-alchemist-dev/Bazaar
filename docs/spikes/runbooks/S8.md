# Spike S8 runbook: VM pair sizing on the owner NUC

Runbook for the owner. Code stays on branch `spike/S8`; only the filled record `docs/spikes/S8.md` reaches main.
Design sources: `docs/design/35-spikes-plan.md`, `docs/design/16-agent-vms-and-environments.md`, `docs/spikes/_TEMPLATE.md`.

## 1. Question

Can the owner's NUC (Windows host, Hyper-V) run at least 4 agent VM pairs at once in 32 GB, with 2 GB of host headroom and each VM reaching ready within 120 s, and what are the RAM, CPU, boot, save, restore and throughput figures per VM?

This is sizing only. The topology is DECIDED (C03): every agent gets a Windows VM and a Linux VM. S8 does not compare topologies and cannot change them.

## 2. Pass criteria

Fixed before the first run; do not edit after running. Copied from doc 35:

> At least 4 pairs running with 2 GB host headroom; boot-to-ready within 120 s.

The RAM, CPU, save, restore and throughput figures have no threshold in doc 35. They are reported as measured numbers.

## 3. Fail consequence and fallback

Doc 35: fewer pairs per host; topology unchanged. The host runs the highest pair count that met both conditions in the scale step (section 7, step 9). S9 and S26 list S8 as a prerequisite (open item 10).

## 4. Time-box

- 3 days, hard stop (doc 35). Record the start time at the first recorded step and the stop time at the end (open item 8).
- At expiry, stop all runs and record the result as `inconclusive`, with the reason.
- An extension needs owner approval. The main session does not extend on its own.

## 5. Prerequisites and environment

- Hyper-V enabled on the NUC, owner-confirmed.
- Golden images from the owner: one Windows parent disk and one Linux parent disk, versioned and read-only (doc 16). All three runs use the same two parents.
- Record in the Method section before run 1:
  - host OS build, CPU model and core count, installed RAM (doc 16 marks 32 GB as unverified; record the actual value), Hyper-V feature state and version;
  - for each parent: file name, SHA-256, guest agent version (doc 16 `golden_image` fields);
  - guest OS build for each VM (`ver` on Windows; `/etc/os-release` and `uname -r` on Linux);
  - per-VM RAM and vCPU used, starting from doc 16 values (Windows 2 vCPU, 4096 MB, 60 GB disk cap; Linux 2 vCPU, 2048 MB, 30 GB disk cap);
  - .NET and PostgreSQL versions only if the harness uses them; otherwise write `n/a`.

## 6. Safety rules

- Spike VMs only. Names start with `s8-`. Never attach a live agent's VM, Soul folder or workspace share.
- No secrets in any guest or share: no provider keys, GitHub App keys, Passport material or session cookies (doc 16: keys are never mounted).
- VMs stay headless. Enhanced session mode and clipboard sharing stay off (doc 16).
- No external switch for S8 VMs. Egress is tested by S9, not here.
- Never write to a parent disk. Confirm its SHA-256 before and after every run.
- Save and delete steps touch only spike child disks in a scratch folder.
- No model calls and no spend in S8 (open item 9).
- Do not change product `vm.*` settings or the topology. Spike scripts live on `spike/S8`.
- Logs and raw counters stay local. Only `docs/spikes/S8.md` is committed to main, with no secrets in it.

## 7. Steps

Run every step in each of the three runs. Log values in the run table (section 8).

1. **Prepare the host.** Record host build, CPU, RAM and Hyper-V state. Close other heavy work (open item 6). Create a scratch folder for child disks. Record the start time.
2. **Verify golden images.** Record SHA-256 and guest agent version for both parents. Confirm each is read-only. After first boot, record the guest OS build.
3. **Build the pair.** For each OS, create a differencing child from its parent (`New-VHD -Differencing -ParentPath`). Create `s8-win-<n>` and `s8-lin-<n>` with static memory, the start vCPU and disk caps from section 5, headless, no external switch and no mounts except the scratch mount step 7 needs. Record child paths, VM settings and the parent hash.
4. **Boot-to-ready.** Start each VM. Timestamp the start request and the guest `Hello` message (doc 16 create step; open item 4). Record seconds per VM. One cold boot per VM per run.
5. **Idle RAM and CPU.** After `Hello`, leave each VM idle with no exec. Sample assigned RAM, RAM demand and CPU use per VM (for example `Get-VM` fields `MemoryAssigned`, `MemoryDemand`, `CPUUsage`; the sampling method is open item 1). Turn idle save off for the spike only. Record mean and peak.
6. **Loaded RAM and CPU.** Run the same load profile (open item 1) in every VM. Record the same measures under load.
7. **Throughput.** Measure HvSocket (Windows VM to host), Linux vsock (Linux VM to host) and SMB (both VMs to the scratch share). Record MB/s per channel per VM and the number of pairs running at the time. The tools, payloads and share settings are open item 2.
8. **Save and restore.** Run `Save-VM` on each VM. Record save time and the saved-state file size on the host disk. Resume both VMs of the pair with `Start-VM`, together. Record time to `Hello` per VM and any skew between them (doc 16). Open item 7 covers what "restore" means here.
9. **Scale.** Start from one pair. Add pairs one at a time; boot each to ready and sample it idle. At each count record host free RAM (headroom) and each VM's boot-to-ready. Stop at the first count where headroom is below 2 GB, a VM misses 120 s, or a VM fails to send `Hello`. The result is the last count that met both conditions (open item 5). Saved pairs are not running pairs.
10. **Stop and clean up.** Stop all VMs and record the stop time. Delete the spike child disks and keep the parents. Confirm each parent SHA-256 is unchanged. Fill in the run row.

## 10. Consequence

The main session writes the DECISIONS-LOG entry for the outcome. It does not change the topology in any case.

- **Pass:** entry records the measured pairs per 32 GB host and the per-VM figures; replaces the unverified "about 4 pairs" estimate in doc 16 with measured numbers. Unblocks 16 (Hyper-V provider, work package 5, and sizing) and 17 (workload sizing). S9 and S26 may start (open item 10).
- **Fail (fewer pairs):** entry records the measured maximum pairs per host and that topology is unchanged. Doc 16 resources table is updated with measured figures. Any change to `vm.*` defaults goes to the owner under the settings rule (DECISIONS-LOG round 13). Still unblocks 16 and 17, with the lower number.
- **Inconclusive** (time-box expired, or a run was void): no DECISIONS-LOG entry. The main session lists the open items and asks the owner whether to extend.
- **One pair cannot reach ready within 120 s, or the figures suggest the pair cannot run at all:** do not change the topology. Record the finding under Conflicts and ask the owner, since C03 is DECIDED.

## 11. Open questions

1. **Load profile.** What work runs in each VM under load, and at what sampling interval and window are idle and loaded samples taken? Which tool reads the counters?
2. **Throughput method.** Tool, payload size, duration and direction for HvSocket, AF_VSOCK and SMB. SMB share settings: SMB version, signing or encryption, host path, guest mount options. Doc 16 names SMB throughput in Testing but gives no method, and CLAUDE.md marks SMB sharing OPEN.
3. **Boot-to-ready scope.** Does the 120 s apply per VM or per pair, and at idle or under load?
4. **"Ready".** Taken here as the guest `Hello` (doc 16). Confirm. Before the Bazaar guest agent (doc 16 work package 6) exists, does S8 use a spike-only agent on `spike/S8`, and does each golden image include it?
5. **Headroom and stop rule.** Headroom is read as host free RAM at steady state; which counter? The stop-at-first-failing-count rule in step 9 is this runbook's reading of "at least 4 pairs".
6. **Other host load.** Are PostgreSQL, the server or Garnet running during S8? Doc 16 reserves about 4 GB for the host plus an unsized share for PostgreSQL and the server.
7. **"Restore".** Saved-state resume (used here) or checkpoint restore (doc 16 `RestoreAsync`, not in S8's criteria)? Confirm.
8. **Time-box unit.** Is "3 d" 72 hours from the first recorded step?
9. **Spend.** The runbook assumes no model calls and no spend. Confirm.
10. **Dependents after a fail.** Doc 35 lists S8 as a prerequisite of S9 and S26 but does not say what a fail does to them.
11. **Owner RAM.** Confirm the NUC has 32 GB; doc 16 marks it unverified.
12. **Conflicts (not fixed here):**
    - DECISIONS-LOG C03 cites "Doc 16 Q13" and "35 Q4". Doc 16 has three questions, none on topology; doc 35 Q4 asks about a foldable device.
    - Doc 07 cites "16 Q2" for the second share. Doc 16 Q2 is about CAL licensing, and doc 16 has no SMB question.
    - Doc 16 Testing lists SMB throughput, but the workspace share has no protocol design in doc 16.
