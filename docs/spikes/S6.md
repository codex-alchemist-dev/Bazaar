# Spike S6: Wire codec, JSON source-gen vs Protobuf behind `IWireCodec` (part 1, cloud)

Branch: `spike/S6` (code stays there; only this record reaches main). Design source: `docs/design/35-spikes-plan.md`, `docs/design/02-wire-protocol-and-sync.md`.

## Question
Wire codec: JSON source-gen vs Protobuf behind `IWireCodec`; bytes and time; unknown and added fields; AOT warnings.

## Pass criteria (fixed before the first run)
JSON unless a non-.NET consumer is a v1 requirement or Android shows a JSON-specific failure (doc 02 rule). Part 1 measures the cloud-side evidence only: both codecs implement `hello`, `subscribe`, `gc.message`, `lagged` and a 200-message page; round trips pass with an unknown envelope field, an unknown payload field, an added field read by an old decoder, an old payload read by a new decoder, and an unknown message type; bytes and time for a 200-message page and a 10k replay; AOT/trim warnings. Fail consequence: the Protobuf codec would join the contracts design (generated types or a mapping layer).

## Time-box
2 d (plan). Part 1 took well under that.

## Method
Throwaway projects in `spikes/S6/` (own `Directory.Packages.props`; no shared file touched): `Wire` (envelope, payload records, `IWireCodec`, JSON codec on `System.Text.Json` source generation with a hand-written envelope reader/writer so `p` stays raw bytes, Protobuf codec on `Google.Protobuf` 3.33.0 + `Grpc.Tools` 2.76.0 with `wire.proto`), `Tests` (xUnit v3, 15 tests, all pass), `Bench`. Corpus: 10,000 synthetic messages (60% short chat, 40% long prose, code block, non-ASCII), fixed seed. Page = one `gc.page` event with 200 messages; replay = 10,000 `gc.message` frames. Environment: cloud container, Linux, 4 vCPU Xeon 2.1 GHz, 15 GB, .NET SDK 10.0.402, Release. Not run: NUC, Android device (part 2).

## Runs
Three separate processes; each process also does three timed rounds (round 1 includes JIT warm-up, so the steady value is round 3). Bytes are identical in every run.

| Measure | JSON | Protobuf |
|---|---|---|
| 200-message page, bytes | 61,052 | 34,938 (57%) |
| 200-message page, gzip / brotli | 4,250 / 3,502 | 4,260 / 3,911 |
| 10k replay, total bytes (avg per frame) | 4,013,516 (401) | 2,096,473 (210) |
| Page encode, steady, us (3 processes) | 116, 143, 122 | 71, 69, 75 |
| Page decode, steady, us | 435, 467, 570 | 77, 75, 74 |
| 10k replay encode, steady, ms | 16.4, 17.1, 14.2 | 5.5, 5.5, 5.3 |
| 10k replay decode, steady, ms | 28.8, 27.5, 25.4 | 5.0, 5.5, 5.0 |

Added after the owner's answer (see Revisit): a third codec, proto3 JSON, text frames from the same `wire.proto` (`ProtoJsonWireCodec.cs`, 42 lines, 6 more tests, 21 pass). Page 200: 55,674 bytes (gzip 4,282, brotli 3,443); 10k replay 3,716,552 bytes. Steady page encode 352 / 393 / 411 us, page decode 607 / 626 / 651 us; replay encode 20.7 / 21.1 / 22.9 ms, replay decode 35.4 / 33.5 / 33.6 ms (three processes). So it costs about 3x JSON source-gen on encode and the same on decode, and is 5 to 7 times slower than binary Protobuf on decode. It also runs under native AOT (same single Google.Protobuf IL3053/IL3050 warning). Proto3 JSON writes `int64` as strings.

Median steady: JSON page decode 467 us vs 75 us Protobuf; replay decode 27.5 ms vs 5.0 ms for 10,000 frames. Spread across processes is under 30% for every row. Native AOT build of the bench (linux-x64) also runs both codecs with the same ordering (JSON replay decode about 34 ms, Protobuf about 7-9 ms).

Behaviour (xUnit, 15 tests, both codecs where noted):
- Round trip of `hello`, `subscribe`, `lagged`, `gc.message` (with `n` and `ev`): pass, both.
- Added payload field read by an old decoder, old payload read by a new decoder (field absent gives null): pass, both.
- Unknown message type: envelope decodes, `p` stays opaque, so the dispatcher can answer `err unsupported` without parsing: pass, both.
- Unknown envelope field: ignored, pass, both.
- JSON golden bytes are stable and readable (one test pins them).

Cost to implement (lines): JSON codec 84, Protobuf codec 94 plus `wire.proto` 43, in both cases against the same 49-line contracts file. Protobuf generated classes are mutable and not records, so the shared records need a hand-written mapping layer (the 94 lines are mostly that, and it grows with every message type). Build steps: JSON none beyond the compiler; Protobuf adds `Google.Protobuf` + `Grpc.Tools` (downloads a native `protoc` per OS/arch at restore) and a `.proto` file kept in step with the records.

AOT/trim: the `Wire` project builds with `IsAotCompatible` and warnings as errors, 0 warnings, with both codecs. Native AOT publish succeeds on Linux, but `Google.Protobuf` 3.33.0 itself reports IL3050 (`RepeatedField.TryGetArrayAsSpanPinnedUnsafe` uses `Marshal.SizeOf`) and IL3053, which fails the publish under the repo's `TreatWarningsAsErrors`; it needs a suppression. The JSON path has no such warning.

## Result
Part 1 pass for both codecs; no JSON-specific failure. The final decision changes with the owner's answer (below).

## Revisit: owner says a non-.NET client IS a v1 requirement (2026-10-25)
The doc 02 rule was "JSON unless a non-.NET consumer is a v1 requirement", so JSON-by-default no longer holds on its own. Options, with what part 1 measured:

| | A. JSON (STJ source-gen) plus a published JSON Schema | B. Protobuf binary only | C. `wire.proto` as the schema, two encodings (binary Protobuf; proto3 JSON text) |
|---|---|---|---|
| Contract for other languages | JSON Schema generated from the records; generators exist but are less uniform per language; drift between records and schema needs a test | `.proto`: official codegen for Kotlin, Swift, Python, Go, TypeScript (via ecosystem), C++, Rust and more | same `.proto` |
| Evolution rules | convention (ignore unknown fields; tested) | field numbers and reserved ranges, enforced by the format; unknown fields skipped (tested) | same |
| Readable on the wire / debuggable | yes | no, needs a tool | text frames readable; binary optional |
| Consumer needs a protobuf runtime | no | yes | no for text frames, yes for binary |
| Size, 200-message page | 61 KB | 35 KB | 56 KB text, 35 KB binary |
| Decode, 10k replay (steady) | 27 ms | 5 ms | 34 ms text, 5 ms binary |
| .NET-side cost | none | mapping layer from records (94 lines for 6 types) or use generated classes as the contracts; `protoc` at restore; IL3050 suppression | A plus B costs, plus 42 lines for the text codec |
| Gap to doc 02 as written | adds JSON Schema work | doc 02 text frames/JSON becomes binary only | doc 02 already says text frames JSON, binary Protobuf; fits |

Recommendation: **C, `wire.proto` as the single schema source, JSON text frames as the default and binary Protobuf as a negotiated option in `hello`/`welcome`.** Why: the schema and its evolution rules then come from one file that every language can compile; a client without a protobuf runtime (a script, a Luau or other embedded plugin, a quick tool) can still speak plain JSON; the .NET side measured fine on speed (text encode and decode are within 3x of source-gen JSON and far below any human-visible budget) and the binary codec stays available for large replays and slow links. Rejected alternative A is workable if the non-.NET client is a single known language with a good JSON Schema generator, and it avoids all Protobuf tooling; choose it if that is the case and Protobuf tooling is unwelcome.

Costs to accept with C: the Protobuf toolchain enters the build (`Google.Protobuf` and `Grpc.Tools`; the latter downloads `protoc` per OS and arch at restore); `Bazaar.Contracts` either holds generated mutable classes (no mapping, but not records) or keeps records plus a mapping layer (what the spike did); proto3 JSON writes `int64` as strings, so every client must parse the stringified `n` and `ev`; `Google.Protobuf` raises an AOT warning that needs a documented suppression. CLAUDE.md says "no Protobuf tooling yet", and W1 and W2 in the dev plan assume STJ only, so both need the main session to change them first. Contracts keeps Apache-2.0, and `Google.Protobuf` is BSD-3-Clause.

Questions the owner must answer before W1: (1) which non-.NET client, in which language? That decides between A and C more than any measurement here; (2) generated classes as contracts, or records plus mapping?

Still unmeasured: Android and the NUC (part 2).
