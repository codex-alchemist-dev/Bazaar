# Spike S2: Garnet on Windows

Branch: `spike/S2` (code stays there; only this record reaches main). Design source: `docs/design/35-spikes-plan.md`. Runbook: `docs/spikes/runbooks/S2.md`.

## Question
Can Garnet on Windows, driven through StackExchange.Redis, run every command the cache and presence layer uses, and keep its data after a hard kill and restart?

## Pass criteria (fixed before the first run)
- Pass: all used commands pass; data survives restart.
- Fail: presence and cache need another Windows provider (doc 35, owner question 6); GC fan-out is unaffected.

## Time-box
1 d hard stop. Started: 2026-11-19 16:03 (local, UTC+8; 08:03 UTC). Ended: 2026-11-19 16:13 (08:13 UTC), about 10 minutes elapsed. Extension approved by owner: no (none needed).

## Method
OS build: Windows 11 Pro 10.0.26300. CPU: Intel Core Ultra 9 285K. RAM: 95 GB.
Garnet: 2.2.13 (newest stable release at the time, published 2026-11-16), source: official `microsoft/garnet` GitHub release asset `win-x64-based-readytorun.zip`, SHA-256 `cc8212d7c7a671c490e5c87967fc43025a22215922bdbdad5eccff00915c7b82` (matches the release's published digest), installed at `V:\TOOL\garnet\2.2.13\bin\net10.0\GarnetServer.exe` (server reports Redis protocol version 7.4.3). Garnet's own runtime is .NET 10 (the release ships a ready-to-run build; no separate runtime needed).
StackExchange.Redis: 3.4.35 (the version pinned in the repo's `Directory.Packages.props`; the spike project pins the same version because it is detached from central package management, like S3).
.NET: SDK 11.0.100 (`global.json`); spike runs on the .NET 11.0.0 runtime (`net11.0`).

Open items decided by the runner (most robust proposed reading each time):
- Version pins: newest stable Garnet; StackExchange.Redis as in the repo (open item 1).
- Network: bind `127.0.0.1` only, port 16379 (non-default), `--auth Password`. The password is random per run, held only in the environment variable `S2_GARNET_PASSWORD`, never written to disk, git or this record (open item 2).
- Data folder: scratch only, `V:\TOOL\garnet\scratch\run<N>`, emptied before each run. No Bazaar data (open item 6).
- Persistence (open item 3): append-only file with commit before reply. Exact flags (password redacted):
  `GarnetServer.exe --bind 127.0.0.1 --port 16379 --auth Password --password <redacted> -c <scratch>\ckpt --aof --aof-commit-wait` for the first start, and the same line plus `-r` (recover) for the restart. The AOF lands in `<scratch>\ckpt\AOF\`. Not used: `-l/--logdir`, which Garnet rejects without `--storage-tier` ("LogDir specified without enabling tiered storage"); it was dropped, no other change.
- N = 1000 keys (`s2:surv:0000` to `s2:surv:0999`), 1 hour TTL for the survival set, 5 second TTL for the expiry check (open item 5). Values are deterministic strings (about 80 bytes). Checksum is SHA-256 over the sorted `key=value` lines. A further 20 keys with a 5 s TTL are written just before the kill and must be gone after restart.
- Kill: `taskkill /F /PID <pid>` (open item 10: hard kill only, no power cut).
- Runs 2 and 3 use the same install with an empty scratch folder (open item 7). Run 1 is the first use of the fresh install.
- Presence (step 5d, open item 4): plain `PUBLISH`/`SUBSCRIBE` (and one `PSUBSCRIBE` pattern) through StackExchange.Redis, recorded separately below and not part of the pass criteria.

Commands run (all via StackExchange.Redis; each as a battery before the kill and again after restart):

| # | Command (design source) | Key pattern | Volume |
|---|---|---|---|
| a | `SET key value EX 60` (`ICacheProvider.SetAsync`, doc 03) | `s2:<pre\|post>:set:{i}` | 200 ops |
| b | `GET key`, values compared (`GetAsync`) | same | 200 ops |
| b2 | `GET` of a missing key returns null | `s2:<tag>:missing:{i}` | 200 ops |
| c | `SET`+`GET` of a 64 KiB binary value, bytes compared (projection snapshot, doc 11) | `s2:<tag>:snap:{i}` | 50 round trips |
| e | expiry: `SET EX 5`, `GET` after 6 s reads null | `s2:<tag>:exp` | 1 |
| 9 | `GET`, `TTL`, `DBSIZE` for the read-back (verification only) | `s2:surv:*` | 1000 |

Key count N: 1000. TTL: 3600 s survival, 5 s expiry. Presence command: `PUBLISH`/`SUBSCRIBE` (separate finding). Persistence setting: `--aof --aof-commit-wait`, recovered with `-r`.

Code, driver and raw per-run JSON are on `spike/S2` under `spikes/S2/` (`Program.cs`, `run.ps1`, `results/run1..3.json`, plus `results/run4-control-none.json`).

## Runs
Three runs. "Commands passed" is out of 5 command checks (a, b, b2, c, e), before the kill and after restart. "Keys" is matching out of N=1000 after restart. "Restart ms" is time from process start to the first successful authenticated PING over StackExchange.Redis, after the hard kill with recovery.

| Run | Date | Measure | Value |
|---|---|---|---|
| 1 | 2026-11-19 | commands passed; keys matched; restart ms | 5/5 before kill, 5/5 after restart; 1000/1000 (0 missing, 0 differ, checksum equal); 1566 ms |
| 2 | 2026-11-19 | commands passed; keys matched; restart ms | 5/5 before kill, 5/5 after restart; 1000/1000 (0 missing, 0 differ, checksum equal); 1418 ms |
| 3 | 2026-11-19 | commands passed; keys matched; restart ms | 5/5 before kill, 5/5 after restart; 1000/1000 (0 missing, 0 differ, checksum equal); 3932 ms |

Median restart-to-connect: 1566 ms. Spread (min to max): 1418 to 3932 ms. First-start-to-connect (no data): 1606, 1451, 2402 ms. Keys matching: 1000/1000 in every run. In every run the 20 short-TTL keys were gone after restart (0 present) and survival keys kept their remaining TTL (about 3560 to 3595 s left of 3600).

Command latency (per-run medians over the ops, ms, as `run1 / run2 / run3`; client and server on the same loopback host, async calls one at a time):

| Command | Before kill | After restart |
|---|---|---|
| SET EX | 0.51 / 0.55 / 12.7 | 0.47 / 8.5 / 39.1 |
| GET | 0.11 / 0.24 / 4.7 | 0.14 / 6.7 / 8.4 |
| GET missing | 0.10 / 0.19 / 3.9 | 0.23 / 6.0 / 10.6 |
| SET+GET 64 KiB | 0.88 / 2.5 / 8.3 | 3.7 / 10.3 / 18.7 |

Run 1 is the clean one (sub-millisecond for small values). Runs 2 and 3 show much higher latency and spread. The machine was shared with other agent sessions during runs 2 and 3, so those figures are probably noise from host load, not Garnet; this was not isolated, so treat the latency figures as indicative only. No latency or restart threshold was set (open item 5), so none is judged.

Control (not a counted run): the same run with persistence off (no `--aof`, restart still with `-r`) read back 0 of 1000 keys (1000 missing). So the survival check does detect data loss, and the survival in runs 1 to 3 comes from the AOF, not from the test.

Separate finding, presence pub/sub (step 5d; not part of the pass criteria): plain `PUBLISH`/`SUBSCRIBE` works through StackExchange.Redis against Garnet. In all six batteries (3 runs, before and after restart) 10 of 10 published messages arrived on a subscriber on another connection, `PUBLISH` returned the right receiver count, and one `PSUBSCRIBE` pattern message was delivered. Order of arrival matched publish order in 5 of 6 batteries; in run 1 after restart the 10 messages arrived complete but not in order. StackExchange.Redis runs subscription handlers on the thread pool, so arrival order in the handler is not guaranteed by the client; this was not isolated to Garnet or to the client. A presence design should not rely on handler order (carry a sequence or timestamp in each delta). Publish latency median was 0.3 to 12.8 ms (same load caveat).

Other observations: Garnet starts without errors with the flags above and logs "Ready to accept connections"; `DBSIZE` after restart (1250) counted the recovered pre-kill keys, so the AOF replayed all data including the batteries' keys. Short-TTL keys were removed on restart. Not tested: power cut, concurrent clients, large data, checkpoint-only persistence, or cluster mode.

## Result
**pass.** All used commands (SET with expiry, GET, GET of a missing key, 64 KiB snapshot values, TTL expiry) passed in all three runs before the kill and after restart, and all 1000 of 1000 survival keys matched the checksum after a `taskkill /F` and restart with AOF persistence (`--aof --aof-commit-wait`, restart with `-r`) in every run. The restart-to-connect time was 1.4 to 3.9 s. Caveats: only a hard process kill was tested (open item 10), persistence must be enabled with the flags above (without it all data is lost, as the control shows), and the latency numbers from runs 2 and 3 are noisy.
