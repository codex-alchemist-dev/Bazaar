# Design-doc drift audit, 2026-11-16

Read-only audit of `main` (commit 5a2a8054) against the decided rules in `docs/design/`, `docs/deep-dives/`, `docs/design/DECISIONS-LOG.md`, `docs/FEATURES.md`, the ROADMAP files and the CI and release docs. Eight audit passes ran in parallel, one per doc group. Findings below are ranked by severity. Each item cites the doc and the code. Items the audits could not verify are listed under "Not checked" in each group.

Owner-decided items are card material for the coordinator, not fixes for this PR. This PR adds only the prevention layer described at the end.

## CRITICAL: structure

1. **No `Bazaar.Core` project exists.** Rule: features are module projects on Bazaar.Core; Core holds no functionality (CLAUDE.md, docs/design/40 §1, §4, §6.1, docs/design/41b §1–2, DECISIONS-LOG). Code: the kernel sits in `src/Bazaar.Server/Components/` (`IBazaarComponent`, `ComponentManifest`, `ComponentGraph`). Feature folders sit inside `src/Bazaar.Server/` (Gc, Council, Gateway, Skimmer, Vault, Souls, Constellation, Memory, Agents, Calendar, Org, Interrupts, Mail, Identity, Security and about 30 more; the audit counts roughly 37 folders).
2. **Feature code in `Bazaar.Client.Core`.** Rule: Client.Core holds no feature code (docs/design/41b; docs/design/40 §5 step 7). Code: `src/Bazaar.Client.Core/Panes/{GcPaneModule,ConstellationPaneModule,DashboardPaneModule,VaultSearchPaneModule,FirstPartyPanes}.cs`, `Chat/`, `Constellation/`, `Vault/`, `Souls/`, `Pairing/`, `Mobile/` (`PhoneShell.cs`, `RadialMenu.cs`). The planned `Bazaar.Client.GC` and `Bazaar.Client.Constellation` projects do not exist. Heads compose panes from `FirstPartyPanes.Modules`, so a head cannot choose its panes.
3. **Feature modules reference each other's implementations.** Rule: a component implementation does not reference another's implementation; it uses an `Abstractions` contract (BAZAAR-COMPONENTS §6, DECISIONS-LOG round 25). Code: `src/Bazaar.RyuseiFuda/Bazaar.RyuseiFuda.csproj` and `src/Bazaar.Server.Components.Kanban/*.csproj` reference `Bazaar.Server` or Kanban directly. Kanban grants `InternalsVisibleTo` to RyuseiFuda. Only five `*.Abstractions` projects exist (Constellation, GC, Secrets, Vault, and one more), so Gateway, Council, Memory, Agents, Kanban and Backup have no contract project.

## HIGH

4. **DM owner read.** Rule: the owner reads all DMs (Bazaar.md §2; doc 02). Code: `src/Bazaar.Server/Gc/Read/GcReadAccess.cs:113` loads every member except the viewer as a human principal. The owner can be denied DM streams. DECISIONS-LOG GLUE (line 170) says the owner shortcut does not apply to subscriptions.
5. **Loop-guard trip to Psych Ward.** Rule: loop-guard trips go to the Psych Ward (doc 01 Flood; DECISIONS-LOG C34). Code: the server path only refuses and logs (`src/Bazaar.Server/Agents/Turns/Posting/GcAgentPostSink.cs`, round 24: "Logged only... no Psych Ward hand-off"). The `IPsychWardAdmission` seam exists only in RyuseiFuda and defaults to a no-op (`src/Bazaar.RyuseiFuda/Orrery/RyuseiEventBridge.cs:48`).
6. **`gc_member` key.** Rule: insert-only, primary key `(gc_id, principal_id, joined_seq)` (docs 01, 04). Code: `src/Bazaar.Server/Data/Sql/common/0001_core_schema.sql:78` uses `(gc_id, principal_id)`, so a rejoin insert would conflict. Not verified whether an upsert hides this.
7. **Identity KEK default.** Rule: `identity.kek_provider` default `dpapi` for the first host (doc 14). Code: the default is `FileKekProvider` (random key file in the data root; `src/Bazaar.Server/Identity/Keys/FileKekProvider.cs`, wired at `src/Bazaar.Server/Hosting/BazaarHostServiceCollectionExtensions.cs:25-27`). No `identity.kek_provider` setting exists. The same key seals GC bodies (`src/Bazaar.Server/Gc/Body/AesGcmGcBodyCodec.cs:86`). `WindowsKekProvider` is TPM/CNG, not DPAPI, and is not wired.
8. **Owner merge gate.** Rule: the server merges only on signed owner approval (DECIDED C25; docs/design/21). Code: `SquashMergeAsync` (`src/Bazaar.Server.GitHub/Adapter/GitHubAdapter.cs:174`) takes no approval or signature. The doc comment says it is "only called on signed owner approval", but nothing enforces that. Latent until wired.
9. **Module signing and permission approval not enforced.** Rule: unsigned modules are not installable; the owner approves declared permissions; the event `module.permissions.approved` is audited; the runtime enforces the approved set (docs/design/48 §1; docs/design/50 §5). Code: `ModuleInstallCheck.Evaluate` (`src/Bazaar.Server/Modules/Trust/ModuleInstallCheck.cs:26`) has no caller. No code emits `module.permissions.approved`.
10. **Legal hold and crypto-erase.** Rule: legal hold blocks removal; crypto-erase destroys keys and produces a signed proof (docs/design/48 §9). Code: `ErasureCoordinator.cs:32-64` destroys keys with no hold check. No legal-hold type exists. `IErasureProofSigner` says it "holds no key" and has no implementation. No production caller of `EraseAsync` exists, so the risk is latent.
11. **Data checksums.** Rule: data checksums at initdb (docs/design/42 §6.4, DECIDED). Code: `src/Bazaar.Components.ManagedPostgres/Process/PostgresProcessController.cs:236-241` runs initdb without a checksum flag.
12. **Portability importers are not modules.** Rule: importers and exporters are modules with a manifest, declared permissions and a health contract (docs/design/44 §9, D3). Code: `src/Bazaar.Portability/Contracts.cs:24-40` defines `IPortabilityImporter`/`IPortabilityExporter` with only `Id` and `Version`. Parsing runs in-process.
13. **Setup Nigerian Prince step ignores its own setting.** Rule: enabled only through the risk wizard with a dated acknowledgement (docs/design/45 §1.11). Code: `SetupScamMailSection.Enabled` (`src/Bazaar.Server/Setup/SetupPlan.cs:160-164`) is never read by the validator or the apply path. No acknowledgement check exists.
14. **Release channels.** Rule: LTSC, Stable, Beta, Alpha, Latest-Commit (CLAUDE.md, DECISIONS-LOG, docs/VERSIONING §4). Code: `src/Bazaar.Server.Modules/Releases/ReleaseChannel.cs` defines Stable, Beta, Nightly, Lts. The operator setting `update.channel` does not exist in `src/Bazaar.Server/Settings/SettingRegistry.cs`.
15. **Release signing and SBOM.** Rule: every release is signed and ships an SBOM (docs/design/49 §3). Code: `.github/workflows/release.yml` (~line 272) says "archives only, unsigned". `sbom.yml` covers only the NuGet graph, with no bundled PostgreSQL or pgvector entries.
16. **Settings registry incomplete.** Rule: settings are registered in the doc 03 registry (round-13 configurability rule). Code: `src/Bazaar.Server/Settings/SettingRegistry.cs` `Known` covers host, calendar, gc, knowledge, constellation, gateway, security and module-manager only. Missing: `auto.*`, `pairing.*`, `signin.*`, `privacy.*`, `backup.*`, `coworker.*`, `client.*`, `windows.*`, `android.*`, `linux.*`, `packaging.*`, `update.channel`. Several documented keys are absent from GC (`gc.message_max_bytes`, `gc.dm_access_approvers`, `gc.unarchive_policy`, `gc.broadcast_mentions`, `gc.blob_max_bytes`, `gc.type_defaults`, `gc.vault_embed_pin`), Skimmer (`skimmer.mode`, `skimmer.threshold_bp`, `skimmer.scorer_model`, `skimmer.outage_policy`) and Erasure (`erasure.backup_window_days`). The GC wire handler uses 64 KiB, not the documented 32 KiB default (`src/Bazaar.Server/Gc/Wire/GcWireHandlers.cs:55`).
17. **Backup cookie exclusion.** Rule: `security.backup.include_cookie_profiles` defaults to false (docs/design/15). Code: the setting is registered, but nothing reads it. The backup component has no cookie or browser-profile exclusion.
18. **Council follow-up trigger.** Rule: follow-up on no decisive result or on high-impact dissent above `council.followup_dissent_share` (0.33), docs/design/10. Code: `src/Bazaar.Server/Council/Tally.cs:64` sends every non-unanimous bigger-change round to follow-up. The dissent setting is absent.
19. **Blind peer review.** Rule: the review packet strips the author name and model badge (docs/design/11 line 73, DECIDED). Code: no implementation. A grep for "blind" finds nothing under `src/Bazaar.Server`.

## MEDIUM

20. **Rate limits are process-local.** Rule: `rate_bucket` is a Postgres table for runtime counters (doc 15). Code: `InMemoryRateBucketStore` (`src/Bazaar.Server/Security/Policy/RateBuckets.cs:47-53`), reset on restart. No migration exists.
21. **Service terms Deny rule has no storage.** Rule: any action on a platform without a verified ServiceTerms record is Deny (doc 15). Code: no `service_terms` table. Quarantine and handover tables from doc 15's SQL sketch are absent. These may be unbuilt work packages; confirm before treating them as drift.
22. **Windows host has no cache provider.** Rule: cache and presence are per-OS (Garnet on Windows; docs/deep-dives/Bazaar.Server.md §3). Code: `src/Bazaar.Server.Providers.Windows/WindowsProviders.cs` defines ServiceHost and VM candidates only. The only cache is `src/Bazaar.Server/Providers/Linux/ValkeyCacheProvider.cs`.
23. **Constellation Skia fallback not built.** Rule: Skia fallback behind `IConstellationRenderer` (docs/deep-dives/Bazaar.Constellation.md §1, DECIDED 2026-11-01). Code: only `src/Bazaar.Constellation.Vulkan/VulkanConstellationRenderer.cs` implements it. The 2D pane draws outside the interface. The Vulkan project is referenced by no production csproj.
24. **Email back ends short of v1.** Rule: four v1 back ends (docs/deep-dives/Bazaar.Server.md §9). Code: `src/Bazaar.Server.MailBackends` has Cloudflare, Generic and ScamBait. No built-in SMTP/IMAP server.
25. **Rubedo not wired into clients.** Rule: views are Rubedo documents, shared by server and every head (docs/design/41b §2; 41c accepted 2026-11-15). Code: `src/Bazaar.Rubedo` is referenced only by its tests. Four hand-written `.axaml` views remain in Client.Core.
26. **Sign-in page absent.** Rule: sign-in page scope, C42, off by default (docs/design/32 §4). Code: no `/signin` or `/auth/handoff` routes and no `signin.enabled` setting.
27. **Client parity guard not wired.** Rule: phone widget policy filters profiles (docs/design/29). Code: `PhoneWidgetPolicy` is called only from tests.
28. **Decided kernel items not built.** Rule: `SoftDependsOn` flag (docs/design/40 §6.2). Code: absent from `src/Bazaar.Server/Components`. Also `ryusei-schedule` component id (docs/design/40 §6.3) not read.
29. **Three manifest types.** Rule: one manifest format, `bazaar-component.json`, with `kind: dependency` (docs/design/42 §8). Code: `ComponentManifest`, `ModuleManifest` (`src/Bazaar.Contracts/Modules/ModuleManifest.cs`) and `DependencyManifest` (`src/Bazaar.Server.Modules/Deps/DependencyManifest.cs`). No code reads `bazaar-component.json`. `ModuleManifest` has no origin class.
30. **Repo ships client installers.** Rule: "This repo ships server builds only; client packages are produced per company" (docs/design/37 line 10, owner 2026-11-12). Code: `.github/workflows/release.yml` (~lines 221-305) attaches installer artifacts.
31. **Migration namespaces.** Rule: `common/` is frozen; each component owns `Data/Sql/<component_id>/` (`src/Bazaar.Server/Data/Sql/README.md`, DECISIONS-LOG line 295). Code: Skimmer, Identity, Calendar, Org and Constellation migrations still sit in `common/`. Kanban SQL sits in `src/Bazaar.Server/Data/Sql/kanban/`, outside its project.
32. **Versioning bump not enforced.** Rule: every PR bumps `VersionPrefix` (docs/VERSIONING §1). Code: `Directory.Build.props:6` is still `0.1.0`, and no workflow enforces a bump.
33. **Renovate and Dependabot overlap.** Rule: FORWARD-FACING says Renovate is installed; ROADMAP-TECHNICAL T10 says the install was denied. `.github/dependabot.yml` ignores only xunit.v3 packages, while `renovate.json` tracks other packages.
34. **Stale dependency pins in FORWARD-FACING.** MailKit/MimeKit 4.18.2 in the doc vs 5.0.0 in code (major bump, not reviewed). Avalonia, StackExchange.Redis, Microsoft.Extensions.AI and TimeProvider.Testing also differ. The Android row says no TargetSdkVersion is set, but `src/Bazaar.Client.Android/Bazaar.Client.Android.csproj:17` pins API 37.
