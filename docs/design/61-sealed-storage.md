# Sealed storage: encryption and tamper detection for on-disk data

Status: DECIDED for the requirement (owner, 2026-11-19, message `cmsg_01MC1BkUhiVHzqr38uyxWzeHKwHGpbCxbmcQVzZBXGVhhR`); the mechanics below are DECIDED unless tagged otherwise.
Depends on: `14-identity-service-and-passport.md` (KEK, DEKs), `48-gap-decisions-security-identity.md` (sections 5, 6, 10), `07-soul-system.md`, `08-memory-system.md`, `18-vault.md`, `16-agent-vms-and-environments.md`
Module: `Bazaar.Server.SealedStorage` and `Bazaar.Server.SealedStorage.Abstractions` (component id `sealed-storage`)

## Owner requirement (DECIDED)
Owner, 2026-11-19: "soul data should be encrypted in their folders and shouldn't be able to be manually edited from the outside ... as well as any data that needs security like that."

Made concrete:
1. **No plaintext on disk.** Every file in the sealed set (inventory below) is stored only as authenticated ciphertext. The server writes no plaintext copy, temp file or cache of it outside process memory.
   - **Exception (DECIDED, owner ruling 2026-11-20, card tap):** the running Vault mount ("Vault adoption" below) may hold the plaintext git dir and checkout, but only on the doc 63 encrypted volume or a tmpfs. Any other location is refused; the condition is a floor, not a setting. Ciphertext stays the only copy at rest everywhere else, and the mount is wiped when it ends.
2. **Authenticated encryption under the KEK.** Each file is AES-256-GCM encrypted under a data key (DEK). DEKs are wrapped by the host KEK through `IKekProvider` (doc 14; DPAPI on Windows, protected key file elsewhere). This module does not implement a KEK, a secret store or a Vault.
3. **Edits from outside fail closed.** Any change to a sealed file or its store made outside Bazaar (edit, truncate, swap with another sealed file, restore of an older copy, deletion, unknown file added (reported, never read)) is detected on read. The read throws `SealTamperedException`, returns no data, writes an audit entry (`seal.tamper`, doc 48 section 5) and raises a Kodo health event. There is no "repair", "ignore" or "read anyway" mode. Recovery is restore from backup (doc 33) or an owner-approved reseal.
4. **Not a setting.** This is a security floor (doc 48 section 4.1 style): an operator may add stores to the sealed set, never remove the set below the inventory, and never turn off verification.

## What this does and does not protect
Protects against: someone with file-system access who is not Bazaar (a person editing a Soul charter in Notepad, a script, malware that can write but not call DPAPI as the service account, an agent VM escape that reaches the share, a stolen disk or copied data root on another machine).
Does not protect against: an attacker running as the Bazaar service account on the live host (the KEK is usable there; true for every provider), full memory compromise, or loss of the KEK (data is then unreadable by design; recovery bundle and backups are the answer, doc 48 section 6). Rollback of the whole data root to an older consistent snapshot is detected only when a counter anchor is configured (section 3).

## Design
**Scope and key.** A scope is a named group of files with one DEK (`soul:<id>`, `memory:<agent-id>`, `passport:<agent-id>`, `host:bootstrap`). The DEK is 32 random bytes, wrapped by `IKekProvider.WrapAsync` with associated data `bazaar.sealed.dek.v1|<scope>|<kekId>`, and stored in the scope's header file. **Crypto-shred:** deleting a scope's header destroys its data (matches doc 14, doc 48 section 9). **Rotation:** rewrap the DEK under a new KEK; files are not re-encrypted.

**File format v1.** Each sealed file is `magic "BZSL" | format byte 1 | generation (u64) | nonce (12) | ciphertext | tag (16)`. Cipher is AES-256-GCM with a fresh random nonce per write. Associated data is `bazaar.sealed.file.v1|<scope>|<logical-path>|<generation>|<format>`, so a file moved to another path or scope, or replaced by an older generation of itself, fails the tag check. The logical path is normalised (forward slashes, no `..`, no absolute paths, ordinal case compare) and is the same on every OS. Disk names are the logical path hashed (HMAC-SHA-256 under a key derived from the DEK), so file names leak nothing.

**Manifest.** Each scope has a sealed manifest listing every logical path with its generation and the SHA-256 of its stored bytes, and a manifest generation that only increases. Reading a file checks it against the manifest; listing a scope lists the manifest, not the folder. A manifest entry with no file, and a hash or generation mismatch, are tamper. A file on disk that the manifest does not know is never read or listed, and `VerifyAsync` reports it (`seal.unreferenced`). A write puts the new file under a new name (`<name-hmac>.<generation>.bzs`, never overwriting), then replaces the manifest by atomic rename (the commit point), then deletes the old generation. File generations come from the manifest counter, so a deleted and recreated path never reuses one. A crash before the commit leaves an unreferenced file that is never read; a crash after leaves a stale old file that is likewise never read. `VerifyAsync` reports both.

**Anti-rollback anchor.** The manifest generation and a manifest hash are published to an `ISealAnchor` after each write. Shipped anchors: the audit log (a checkpoint entry, doc 48 section 5.2, the default when Postgres is up) and a local counter file under a separate location (fallback for bootstrap and offline). At open, a manifest older than the anchor is tamper. An install with only the local anchor detects in-place edits and swaps, and rollback only on the same host.

**API (Abstractions).** `ISealedStore` (`OpenScopeAsync`), `ISealedScope` (`ReadAsync`, `ReadAllAsync`, `WriteAsync` with expected generation, `WriteBatchAsync`, `DeleteAsync` with optional expected generation, `ListAsync`, `VerifyAsync`, `AcquireLeaseAsync`, `ShredAsync`), `SealedSnapshot`, `SealedWrite`, `ISealedLease`, `SealTamperedException`, `SealGenerationConflictException`, `ISealAnchor`, `ISealAuditSink`. Writes and deletes carry the expected generation; a stale one is rejected, like `soul_versions` (doc 07). Reads return bytes or a stream; plaintext is held in pinned, zeroed buffers where the runtime allows.
- `ReadAllAsync` returns one consistent snapshot: the manifest generation and every file with its generation, read and authenticated under one in-process gate and the scope's OS lock, so a concurrent writer cannot produce a mix of old and new files. Any failure throws, clears what was decrypted and returns nothing.
- `WriteBatchAsync` applies many writes and deletes with one manifest commit. Paths, sizes and every expected generation are checked before the first byte is written; new files go under new names, the manifest rename is the single commit point, old generations are removed after it. A failure before the rename removes the batch's files, so readers see all of the batch or none of it.
- `DeleteAsync(path, expectedGeneration)` is the checked delete; the overload without it keeps the unchecked behaviour.
- `AcquireLeaseAsync(timeout)` takes the scope lease, a second OS lock file (`scope.lease`) held until disposed, so a long cycle (sealed git: materialise, work, reseal) is exclusive against every other lease holder in any process or store instance. Single operations do not take it. A lease not free within the timeout throws `TimeoutException`.
- The batch and snapshot hold their files in memory, so their total is bounded by `SealedStoreOptions.MaxBulkBytes` (operator setting, default 1 GiB); each file stays at most 256 MiB.

**Known limits (from the 2026-11-19 security review).** The local counter-file anchor is not itself authenticated: deleting a scope's folder and its anchor file together looks like a scope that never existed. Detecting that needs an authenticated, monotonic index of scopes held in the audit-log anchor (WP6); until then the audit-log anchor is the recommended default when Postgres is up. A manifest with writes but no anchor, or a manifest missing next to other files, is already tamper. KEK rotation fails closed (a scope wrapped under another KEK id does not open); the rewrap path is WP9. A crash during shred can leave a scope that reports tamper until it is shredded again. The Vault mount (2026-11-20 security review) holds plaintext while it runs, on tmpfs or the encrypted volume only; its limits (trusted while running, operator-attested encrypted volume, adopted stale mounts trusted as found, serialised writes) are listed under "Vault adoption".

**Concurrent writers.** Each operation is serialised by a per-scope OS lock file (polled for up to 30 seconds) and flushed to disk before each rename. Multi-file restores use `ReadAllAsync` (no torn snapshot), multi-file updates use `WriteBatchAsync` (one commit point), and deletes can carry a generation check. A cycle that spans operations takes the scope lease; the lease is advisory towards writers that do not take it, whose changes are caught by the generation checks of the lease holder's batch (the whole batch then fails and nothing is committed). Opening a scope removes leftover `*.tmp` files of interrupted writes under the OS lock and audits `seal.cleanup`; leftover `.bzs` files stay unreferenced and are reported by `VerifyAsync`. The OS locks are advisory `flock` locks on Linux and share-mode locks on Windows; on Windows a scope cannot be shredded while a lease on it is held. The polling locks are not fair: a writer that never pauses can delay others up to the timeout.

**Failure behaviour.** Missing KEK, wrong KEK, bad tag, bad magic, unknown format, manifest mismatch and anchor mismatch all throw and audit; none returns partial data. An unsealed (plaintext) file found where a sealed file is expected is tamper, not a legacy path. First-time migration of existing plain data is a separate, owner-started, audited import that seals and then securely removes the plaintext.

**Consumers.** Souls (`Bazaar.Server.Souls`, doc 07), Memory (`Bazaar.Server.Memory`), Identity/Passport and Host bootstrap call `ISealedStore` through their own modules. Adoption is one work package per consumer; each is its own PR and PROPOSED until merged. Nothing here puts feature code in Bazaar.Core, Bazaar.Server or Bazaar.Client.Core.

## Vault adoption [mechanics PROPOSED; mount location DECIDED]
Implements Q1 (DECIDED) for the company Vault. The Vault engine (`IGitProvider`, LibGit2) works on a persistent main checkout and worktrees by path, and the Vault writer and the memory vault write files into those folders directly, so the per-call `ISealedGitRepo.WithWorkingTreeAsync` cycle does not fit. Instead the repo is **sealed at rest** and **mounted** in plaintext only under an operator-chosen mount root while the server runs. **Owner ruling (2026-11-20, DECIDED):** that mount root must be the doc 63 encrypted volume or a tmpfs (the documented exception to invariant 1).

- **Module.** `Bazaar.Server.SealedVault` and `Bazaar.Server.SealedVault.Abstractions` (component id `sealed-vault`, hard dependencies `sealed-git` and `memory`). It references `Bazaar.Vault.Abstractions` and the sealed git and storage abstractions, never `Bazaar.Server` (placement rule, doc 40); the LibGit2 provider it decorates comes from DI.
- **Mount (in `Bazaar.Server.SealedGit`).** `ISealedGitRepo.MountAsync(SealedGitMountRequest(MountRoot, CheckoutPath, Verifier, ScratchPath, AdoptStaleMount))` returns `ISealedGitMount : IAsyncDisposable` (`Path`, `GitDir`, `ScratchPath`, `IsFaulted`, `ResealAsync()`). The mount takes the scope lease and holds it until disposed, materialises the git dir from one `ReadAllAsync` snapshot into `<CheckoutPath>/.git`, writes its own fixed config (non-bare, `core.symlinks = false`, no reflogs) and checks out HEAD with the hardened git runner (`GIT_*` stripped, hooks redirected to an empty folder, fsmonitor and auto gc off). HEAD counts as unborn only when it is a symref whose target is in neither the snapshot's loose refs nor its packed-refs; any other git failure fails the mount. `ResealAsync` seals the git dir's changes in one `WriteBatchAsync` with generation checks; content-addressed objects and packs already sealed are not re-read. While mounted, `WithWorkingTreeAsync` and a second mount of the repo are refused; export still works. The checkout and the import use the git executable (`SealedGitOptions.GitPath`, else `git` on PATH), so a host with the sealed Vault enabled needs git installed even though LibGit2 itself does not.
- **Mount root.** Configured by the operator (`Bazaar:SealedVault:MountRoot`); the start fails without it. It must have no link in any component, is created owner-only, and is refused when (Unix) open to group or others. An `IMountRootVerifier` must confirm it is protected before any plaintext is written; the default (`ProcMountsRootVerifier`) accepts a Linux `tmpfs`/`ramfs` found in `/proc/self/mounts`, or an operator attestation `Bazaar:SealedVault:MountRootAttested=true` for the encrypted volume (which cannot be told apart from a plain disk). Otherwise the mount and the import are refused and audited (`sealvault.mount_unverified`, `sealgit.mount_unverified`). Checkout and scratch folders are canonicalised (every link component resolved, device and UNC forms rejected) and must be strictly inside the root; missing parents are created owner-only. Every mount, unmount (with its wipe result), stale wipe and refusal is audited (`sealgit.mount`, `sealgit.unmount`, `sealgit.unmount.wipe_failed`, `sealgit.mount.stale_wiped`, `sealgit.mount.failed`, `sealvault.refused`).
- **Paths are not remapped.** The mount is made at the configured repo path itself (`Memory:Vault:RepoPath`), and worktrees go to `Memory:Vault:WorktreeRoot` as the scratch folder; both must lie inside the mount root after canonicalisation (checked at start). A remap is not possible without changing the Vault writer and `GitMemoryVault`, which write into those folders by path. `SealedGitProvider` therefore maps the logical path to the mounted one as the identity and enforces containment on canonical paths: an alias (link) of the checkout is treated as the checkout, so it is resealed; a Vault worktree outside the worktree root, a prefix sibling (`vault2` next to `vault`), or any other path inside the mount root is refused and audited. Calls on other repositories (for example GitHub workspaces) pass through untouched.
- **What is sealed.** Objects, packs, refs, packed-refs and HEAD. Never sealed from a mount: `hooks/`, `config`, `index`, `info/`, `logs/` (reflogs), `modules/`, `description`, `COMMIT_EDITMSG`, pending operation state (`MERGE_*`, `ORIG_HEAD`, `AUTO_MERGE`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `sequencer/`, `rebase-*`, `BISECT_*`), lock and temp files, links, and `worktrees/` metadata. In every sealed repo (mount or cycle) a `config` file or a `hooks/` folder below the top level is never sealed or restored (ref names such as `refs/heads/hooks/x` are not affected), and object alternates (`objects/info/alternates`, `http-alternates`) are refused on reseal and on restore. Worktrees live under the scratch folder, outside the sealed git dir; their commits and branch refs are sealed (they are in the common git dir), but the per-worktree metadata in `.git/worktrees` is not, so worktrees do not survive a remount (branches do). A pending merge does not survive a remount either; the next mount starts clean at HEAD, as startup recovery would leave it.
- **Provider.** `SealedGitProvider : IGitProvider` (also `IAsyncDisposable` and `IDisposable`) decorates the engine. Reads (`HeadAsync`, `ReadTextAsync`, `ListFilesAsync`, `DiffAsync`, ...) mount on first use. `CommitAsync`, `MergeAsync`, `AbortMergeAsync`, `AddWorktreeAsync`, `PruneWorktreesAsync` and `RecoverAsync` run under one write gate per Vault and are followed by `ResealAsync` (also when the call throws), so a reseal never sees a ref without its objects. This serialises worktree commits with merges into the main checkout. A failed reseal faults the mount: every later Vault call fails closed until a restart remounts.
- **Lifetime, crash and sweep.** A marker file `<folder>.bazaar-sealed-mount` next to each mounted folder records that the folder is ours. On dispose the checkout and scratch folder are zero-wiped (`SecureTemp`, links deleted, never followed) and the markers removed; a failed wipe keeps the markers and is audited. On the next mount a checkout with a marker is a stale mount of a crash. Its refs (HEAD, packed-refs, `refs/`) are compared with the sealed ones first: when they match it is wiped; when one is new or different (a commit made but not resealed) the mount is refused and audited (`sealgit.stale_unsealed`) and the folder is left untouched. The operator inspects it and either moves it away or sets `Bazaar:SealedVault:AdoptStaleMount=true`, which reseals the stale git dir under the lease with generation checks (`sealgit.stale_adopted`) before mounting. Unsealed commits are never wiped silently. A non-empty folder without a marker is plaintext the mount did not make and is refused, untouched. Every other marker under the mount root is audited (`sealgit.mount.unknown_marker`) and left in place. Leftover import folders under the root are wiped. With the sealed Vault disabled, the start is refused while a marker sits next to the Vault path, so the unsealed engine never works on a sealed repo's plaintext. Worktree folders that `GitMemoryVault` deletes itself are not zero-wiped; that plaintext stays on the encrypted volume or tmpfs.
- **Import.** `ISealedGitRepo.ImportCheckoutAsync(path, mountRoot, verifier)` seals an existing plaintext checkout into an empty sealed repo once. It refuses: links in the git dir; a detached HEAD; a pending merge, cherry-pick, revert, rebase, sequencer or bisect; worktrees; submodules (`.gitmodules`, `.git/modules`, a mode-160000 entry in HEAD); object alternates; more than one stash entry (older stashes live only in the reflog, which is not sealed); and `core.autocrlf`/`core.eol` values outside the allowlist. It seals the git dir in one batch (same exclusions as a mount) and verifies in an owner-only folder under the mount root, never the system temp folder: every file reads back identically, HEAD matches, `git fsck` passes, and the source checkout has no change, untracked or ignored file (`status -z`, any output refuses). Git runs on the restored copy's config, never the source's; only the allowlisted line-ending keys are copied into the verify config. Only then is the whole plaintext checkout zero-wiped. A failed verification rolls the sealed copy back and keeps the plaintext. When the sealed repo is not empty and its HEAD equals the source's (an earlier import whose wipe failed), nothing is sealed again: the source is checked clean and wiped (`sealgit.import.already_done`); any other non-empty repo is refused. The component runs it before the first mount when `Bazaar:SealedVault:ImportFrom` names an existing folder outside the mount root; once that folder is gone the setting is ignored. This replaces `SealedImporter` for git repos, because a git dir needs the hooks, config and per-checkout exclusions.
- **Configuration.** `Bazaar:SealedVault:Enabled` (default `false` until the plaintext import is done), `Bazaar:SealedVault:Name` (scope `vault:<Name>`), `Bazaar:SealedVault:MountRoot`, `Bazaar:SealedVault:MountRootAttested` (default `false`), `Bazaar:SealedVault:AdoptStaleMount` (default `false`; a recovery switch, set only after inspecting the stale mount), `Bazaar:SealedVault:ImportFrom` (optional). Disabled, the component changes nothing (except refusing a start over a mount marker). Enabled, it replaces every unkeyed `IGitProvider` registration made before it runs with the decorator, and any missing or unsafe value fails the start. A keyed `IGitProvider`, or one registered after this component, is not decorated and must not point at the Vault path.
- **Known limits.** The mount trusts its plaintext while it runs: the root is owner-only on tmpfs or the encrypted volume, and an attacker running as the service account can change it (as for every provider, section "What this does and does not protect"). A stale mount adopted with `AdoptStaleMount` is trusted as found, so only an operator who has inspected it should adopt it. The tmpfs check reads the mount table and the encrypted-volume case rests on the operator's attestation; Windows and macOS always need the attestation. A commit whose reseal failed faults the mount and stays only in the plaintext mount until the operator adopts or discards it at the next start. Worktrees and pending merges do not survive a remount. Writes to the Vault are serialised.
- **Not here.** Host wiring (`sealed-storage`, `sealed-git` and `sealed-vault` are not in the host component list yet), other git repos (the Archive repo, GitHub workspaces), the agent memory scopes (`memory:<agent-id>`) and the Constellation graph.

## Passport adoption [PROPOSED; plaintext profile folders DECIDED (owner, 2026-11-22)]
Work package 4 for doc 14's browser profiles (cookie profile at rest, Q3 there). The legacy profile code in `Bazaar.Server/Identity/BrowserProfiles` (an in-memory store with a stand-in key) is not changed; the sealed store replaces it through the Browser module's ports, so no feature code goes into `Bazaar.Server`.
- **Module.** `Bazaar.Server.SealedPassport` and `Bazaar.Server.SealedPassport.Abstractions` (component id `sealed-passport`, hard dependency `sealed-storage`). It references the Browser, sealed storage and sealed git abstractions and `Bazaar.Server.SealedStorage` (for `SealedImporter`), never `Bazaar.Server`. It registers `ISealedPassportStore`, the Browser ports `IBrowserProfileDirectory` and `IBrowserCookieSource`, `ISealedProfileDirectories` and `ISealedPassportImporter`. Sealing has no off switch (invariant 4).
- **Scopes.** `passport:<agent-id>` holds each profile's metadata (`profiles/<profile-id>.json`: agent, anonymous or account, allowlist); `passport-index` maps a profile id to its agent (no secret), so the Browser port can find a profile by id; `cookies:<profile-id>` holds the jar (`jar.json`); `browserdir:<profile-id>` holds an account profile's Chromium folder. Agent ids are limited to letters, digits, `.`, `_` and `-`. Creating writes the metadata, then the index.
- **Cookies.** Writes carry the expected generation (0 for the first jar); a stale one throws the store's conflict exception. An anonymous profile takes no cookie, and an account cookie outside the allowlist is refused (the error names the cookie, never its value). The cookie port reads the sealed jar for each launch and returns only unexpired cookies of allowlisted sites, checks the profile against its sealed record (an agent's own account profile only), and caches nothing. Decrypted buffers are zeroed after use; cookie values handed out are managed strings and cannot be.
- **Tamper.** Any `SealTamperedException` (including metadata that does not match its index entry or does not parse) is audited as `passport.tamper` next to the store's `seal.tamper` and thrown as `PassportProfileUnavailableException`: no data, a message that says the profile cannot be used and must be restored or resealed, no content or key material in the message or the audit entry.
- **Deletion and erasure.** `DeleteProfileAsync` removes the index entry (the browser can no longer find it), crypto-shreds `cookies:<profile-id>` and `browserdir:<profile-id>`, then removes the metadata, and audits `passport.profile.shredded`. It is refused while the profile's folder is open (its scope lease is held) and for another agent's profile. The folder scope's lease is held from the check through the shreds (on Windows it is released just before the folder scope itself is shredded, because an open lease file cannot be deleted there; the index entry is already gone and an open re-checks after taking the lease). A crash part way leaves the remaining ciphertext sealed; repeating the call finishes it. `ShredAgentAsync` deletes every profile of the agent and shreds `passport:<agent-id>`; it collects ids from the file names in the agent scope and the index without parsing metadata, so tampered metadata cannot stop an erasure: tamper is audited (`passport.tamper`) and the shred carries on (an index entry that cannot be read cannot be attributed and is left alone).
- **Plaintext profile folders [DECIDED (owner, 2026-11-22), Q3].** Chromium needs its profile folder in plaintext. `ISealedProfileDirectories.OpenAsync(agentId, profileId)` is refused and audited unless `Bazaar:SealedPassport:AllowPlaintextProfileFolders` is true (default false) AND the mount root is set and verified; it makes the folder only as `profile-<id>` strictly inside `Bazaar:SealedPassport:MountRoot`, after the same floor as the Vault mount: a full path with no link component, owner-only (refused when open to group or others on Unix; on Windows the root's DACL may grant only the service account, SYSTEM and Administrators), and confirmed by the registered `IMountRootVerifier` (the sealed git abstraction the Vault uses; the module does not bring its own). No mount root, no verifier, or an unconfirmed root refuses the open and audits `passport.profiledir.mount_unverified`. The open takes the `browserdir` scope lease (one open folder per profile across processes), restores an account profile from one `ReadAllAsync` snapshot (a tampered file wipes what was written and fails closed) and writes a marker `<folder>.bazaar-passport-mount`. `ResealAsync` and close seal changed, new and removed files in one `WriteBatchAsync` with generation checks; links (Chromium's `Singleton*` links) and the excluded cache folders are never sealed. Close always zero-wipes the folder (links deleted, never followed), also when the reseal fails (`passport.profiledir.reseal_failed`; the session's changes are lost, the sealed copy stays). An anonymous profile's folder is never sealed and starts empty each time. At open, a folder with a marker is a crashed session and is wiped (`passport.profiledir.stale_wiped`; its unsealed changes are discarded, the protective default); a folder without a marker is refused and left untouched (`passport.profiledir.refused`). A failed wipe keeps the marker and is audited. **Links are never followed:** a folder or marker that is a link or reparse point (the marker must be a regular file) is refused and audited (`passport.profiledir.link_refused`) before any wipe; files are zeroed through a no-follow handle (`O_NOFOLLOW`, `FILE_FLAG_OPEN_REPARSE_POINT`) after re-checking their identity on that handle, and a file with more than one hard link is deleted without zeroing. **Races:** the open re-reads the profile after it takes the folder lease and refuses (`KeyNotFoundException`) when it was deleted meanwhile; `OpenAsync`, the cookie calls and the importer take the caller's agent id and refuse another agent's profile; cookie writes require an expected generation. **Leftovers:** at component start the module sweeps every `profile-<id>` marker under the mount root (a folder whose profile still exists is wiped only when its lease is free; unknown markers are audited and left), and a profile delete wipes its `profile-<id>` folder when the marker is present, under the folder lease. **Reseal:** call `ResealAsync` only after the browser has exited (a file Chromium is still writing can be sealed half written); file names are normalised like the store's (NFC, forward slashes, no colon) and a name the store refuses is skipped and audited (`passport.profiledir.name_skipped`); a folder whose projected total would pass the store's bulk limit is refused before anything is sealed (`passport.profiledir.reseal_refused`), so the scope stays readable in one snapshot.
- **Import.** `ISealedPassportImporter.ImportProfileDirectoryAsync(profileId, folder)` imports an existing plaintext Chromium folder into an existing account profile under the scope lease with `SealedImporter` (each file sealed, read back and compared, then zeroed and deleted); paths already sealed are kept in plaintext and reported; links are not imported; the excluded cache folders are neither imported nor removed; the plaintext is zeroed through the same no-follow wipe as the profile folders; the folder is removed only when no file is left. Anonymous profiles are refused and their plaintext kept. Audited as `passport.import`. Owner-started; nothing runs it at start.
- **Settings (configurability rule, protective defaults).** `Bazaar:SealedPassport:MountRoot` (default none: no plaintext folder at all), `Bazaar:SealedPassport:AllowPlaintextProfileFolders` (default false; must be true as well), `Bazaar:SealedPassport:LeaseTimeoutSeconds` (default 30), `Bazaar:SealedPassport:ExcludedFolders` (Chromium cache folder names never sealed; default `Cache`, `Code Cache`, `GPUCache`, `ShaderCache`, `GrShaderCache`, the Dawn caches, `Crashpad`, `component_crx_cache`).
- **Known limits.** The wipe's residual race is a parent folder swapped for a link between its last check and the system call; the root is owner-only, so only the service account can make that swap. On Windows the root is created with an owner-only DACL and an existing root is refused unless its DACL is owner-only; folders inherit it. A crashed session's unsealed changes are lost. The guest-side profile path in `BrowserOptions` is not mapped to the host folder yet.
- **Not here.** Host wiring (the component is not in the host list, and no host registers an `IMountRootVerifier` service yet: the sealed Vault constructs `ProcMountsRootVerifier` itself), the doc 14 mounted folder writer (`LocalMountFileSystem` in `Bazaar.Server` still writes the session-cookie profile in plaintext and must move under this mount root when it is wired), the Postgres `browser_profile` table, OAuth token caches, and the legacy in-memory store's removal.
