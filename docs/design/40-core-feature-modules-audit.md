# 40. Core feature modules: GC, Constellation, RyuseiFuda

Status: AUDIT (2026-11-09). Written from the code at this branch's base. Follows `MODULARITY-AUDIT.md` (2026-10-30) and `BAZAAR-COMPONENTS.md`. The owner's question: are GC, Constellation and RyuseiFuda just modules of Bazaar, and does the shape `Bazaar.Core` plus feature modules that slot into `Bazaar.Server` and each `Bazaar.Client.*` head exist?

## 1. Short answer

- **The kernel exists; the module boundaries do not yet.** `src/Bazaar.Server/Components/` has `IBazaarComponent`, `ComponentManifest`, `ComponentGraph` (validation and ordering) and `BazaarComponentRegistration` (enable/disable). `HostComponents.All` lists 29 components. GC, Constellation, Vault, Kanban and RyuseiFuda's schedule are registered through it.
- **Server side, most features are still folders, not modules.** GC and Constellation are folders inside the one `Bazaar.Server` assembly. Vault is its own server module project, `Bazaar.Server.Vault` (namespaces `Bazaar.Server.Vault.*`), with its contracts in `Bazaar.Vault.Abstractions` (recorded 2026-11-18; see step 6). Kanban and RyuseiFuda sit in their own projects, `Bazaar.Server.Components.Kanban` and `Bazaar.RyuseiFuda`. Nothing stops a folder-based feature (GC, Constellation) from using another feature's internals, because the assemblies are shared.
- **Client side, there is no module at all.** The panes for GC, Constellation, Kanban and the dashboard are registered by hand in `Bazaar.Client.Core/Panes/FirstPartyPanes.cs`, which has a `TODO(component)` for the missing client kernel. RyuseiFuda's client view model sits in `Bazaar.Client.Core/Ryusei/`.
- **So the answer to "Bazaar.Core plus Bazaar.GC etc. that slot in" is: yes, that is the target, and the kernel half is already built. The feature half is not.**

## 3. Gaps

1. **Undeclared hard dependencies.** RyuseiFuda resolves the GC listener and the audit log but declared only `kanban`. This PR declares `gc` and `audit` and adds a test (`RyuseiScheduleDependencyTests`). The kernel now refuses to start RyuseiFuda without them.
2. **The manifest has no optional dependencies.** Kanban and RyuseiFuda use GC only when it is present. Declaring GC as `DependsOn` would make Kanban fail when GC is disabled, which is wrong. Declaring nothing hides the link. The model needs an `OptionalDependsOn` (or a `soft` flag). That is a schema choice, so it needs an owner answer before code changes.
3. **Constellation's dependency on Vault is a type reference, not a declared dependency.** It only runs when `Constellation:VaultId` is set, so it is optional too. Same fix as item 2.
4. **GC is effectively core, but it is not declared as core.** Thirteen files outside `Gc/` depend on it. No consumer declares `gc`. Calendar, Org, Agents and Http are not components yet, so the kernel cannot see their edge.
5. **Single assembly for the server features.** GC and Constellation are folders in `Bazaar.Server`, so no project boundary is enforced for them. Vault has moved out to `Bazaar.Server.Vault` (step 6), which gives it a project boundary; the architecture tests do not yet enforce it as a rule. The architecture tests check only Contracts and Client.Core layering, not component boundaries. Rules 1 and 2 of `BAZAAR-COMPONENTS.md` section 6 are not yet tests.
6. **RyuseiFuda is inside the Kanban project.** Layer 1 (Kanban) and layer 2 (RyuseiFuda) share one assembly. The `kanban` dependency is therefore not a project boundary.
7. **Migration namespace mismatch (DECIDED 2026-11-09: rename the id to `ryusei`; applied as code, see PR #360 follow-up).** The `ryusei-schedule` component maps to namespace `ryusei_schedule`, but its SQL folder is `ryusei`. The runner still applies it (after the component namespaces, by name), so nothing breaks today, but the ordering and ownership are not what the manifest says. `DECISIONS-LOG.md` already records this as an owner choice: rename the component id or the folder. Renaming the folder would change applied history, so the component id is the safer side. Resolved 2026-11-16 (coordinator): the folder stays `ryusei` and the namespace is `ryusei`; the folder is not renamed.
8. **GC, Constellation and Vault tables sit in `common/`**, which is frozen (see `BAZAAR-COMPONENTS.md` section 5). Their components own no migration namespace yet. This is correct under the freeze, and moving it would re-run applied files, so it stays until a wave decides otherwise.
9. **Client panes are hard-wired.** `FirstPartyPanes.CreateRegistry` names each pane. Heads cannot add or drop a feature pane without editing Client.Core.
10. **Version format.** Manifests use SemVer (`0.1.0`). The owner's rule (2026-11-12) is plain SemVer with the commit appended (`0.1.0+a1b2c3d`) for internal modules too, so the manifest and the display show the same string. No code change is needed, but the rule belongs in `BAZAAR-COMPONENTS.md`.

## 4. Target layout

The owner's picture is right. The target, for each feature `<F>`:

```
Bazaar.Core                       kernel: IBazaarComponent, manifests, graph, migrations, DI, wire base
Server (per feature <F>):
  Bazaar.<F>.Abstractions         contracts other modules may reference (no implementation)
  Bazaar.<F>                      implementation; registers via one AddBazaar<F>() / IBazaarComponent
  migrations                      Data/Sql/<f>/NNNN_*.sql, its own namespace
Client (per feature <F>):
  Bazaar.Client.<F>               pane views and view models, referencing Bazaar.Client.Core only
Heads (Windows, Linux, Android, Terminal) compose the client modules they ship.
```

### 4c.1 Floors and the child process (PROPOSED)

- **Loopback only.** The child listens on loopback. A non-loopback listen is not a setting (the doc 42 section 15 floor).
- **Port.** `deps.valkey.managedPort` of 0 (the default) means a free loopback port is chosen per child start. Clients re-resolve the endpoint on every call and do not cache it at construction, so a restarted child on a new port is picked up without a host restart.
- **Password custody (PROPOSED, 4c.4 items 1 and 12).** The managed child's password is generated per run and held in memory as a secret value. It is delivered to the child on stdin. It rotates on every start, and it is never written to disk, to an environment variable, to a command line, to a log, to the status page or to a Kodo fact. Nothing durable needs custody here, because this is a local cache. An externally configured Valkey takes its password from the secret store (doc 14), through the `SecretReference` path of `ValkeyCacheOptions`. The managed child's in-memory password is the one deviation from doc 14's custody rule.
- **Parent death.** On Linux the child starts through the util-linux `setpriv --pdeathsig` wrapper named by `deps.valkey.parentDeathWrapper`. A managed start is refused when no parent-death mechanism is available. This is a floor, not a warning, so an orphaned `valkey-server` cannot outlive the host.
- **Stale-child sweep (PROPOSED).** Before a managed start, the host reads `valkey-server.pid` in `deps.valkey.runtimeDirectory`. If that pid is alive and `/proc/<pid>/comm` reads `valkey-server`, the host stops it before starting a new child. If the pid is dead or does not match, the host removes the stale file. A process whose comm does not match is never killed.
- **Startup order (PROPOSED, 4c.4 item 8).** The managed child starts before the cache provider probe in doc 03 startup step 5. The probe retries inside the bounded window `deps.valkey.startWindowSeconds`, with the per-attempt bound of `ValkeyCacheOptions.ProbeTimeout`. The window expiring marks the probe unusable. It does not fail startup, because the cache is not a required readiness role (doc 03).
- **Restart and stop.** The restart policy follows doc 42 sections 6.2 and 6.3. Stop happens in the host's shutdown path (doc 03 steps 1 to 4). Tree kill of the child with the host is a doc 42 section 16 test (PROPOSED for this child).

### 4c.3 Failure mapping (PROPOSED, C07)

- The cache is a cache. A Valkey outage is `degraded`, never `failing`. Doc 03 already states that GC delivery and turns do not depend on the cache, and GC fan-out is Postgres NOTIFY (C07).
- A down child or a failed probe makes the `valkey` module amber, with a reason and an audit event. Kodo does not open the readiness gate of any dependent module, and the server's readiness roles (doc 03 `host.readiness.required_roles`) do not include the cache.
- While the cache is unusable, `ICacheProvider` callers get misses and dropped writes (the existing degrade behaviour of `ValkeyCacheProvider`). What presence shows while the cache is down is doc 23's decision and is not decided here (OPEN).
- Restart backoff exhausted: the module stays amber and the operator sees it in the module manager (doc 42 section 12). It is not red and it does not start an incident.

Order of checks: secret and database configured (else 503, so an unconfigured install never accepts a delivery), `Content-Length` and a bounded body read against `MaxBodyBytes` (default and ceiling 25 MiB; 413), constant-time `X-Hub-Signature-256` check with `WebhookSignature` (401 when missing or wrong), `X-GitHub-Delivery` and `X-GitHub-Event` present (400), then `insert ... on conflict (source, delivery_id) do nothing` into `github_delivery` with source `github` (`dedupe_key = github:<delivery>`). Retention follows the audit rule: keep forever by default, crypto-shred on erasure, no sweeper. A replay keeps the first payload.

**Events poller (doc 21 Ingress, work package 5).** `GitHubEventsPollingService` is a hosted service registered by `AddBazaarGitHub`; it runs `GitHubEventsPoller` (namespace `Bazaar.GitHub.Ingress`). Config is `Bazaar:GitHub:Ingress`: `InstallationId`, `Repositories` (`owner/name`), `PollIntervalMinutes` (the `github.poll_interval_minutes` setting, default 10, floor 1), `AgentLogins`, `MemberLogins`, `MaxEventAge` (default 24 h, 0 disables), and the backoff bounds. It stays off, with one log line, until an installation id and a repository list are set **and** a real `IGitHubEventSink` is registered. Per repo it reads `GET /repos/{o}/{r}/events` through `IGitHubAdapter.ListRepositoryEventsAsync` with a caller-held ETag (a 304 delivers nothing), waits the larger of the configured interval and `X-Poll-Interval`, waits until the reset time when the rate limit is exhausted or deferred, and backs off exponentially (30 s doubling to 15 min) on any other failure; no failure escapes the loop. Events are parsed (`GitHubEventsApiParser`), dropped when older than `MaxEventAge`, deduped on `github:poll:<id>` through `IGitHubDeliveryStore` (Postgres `github_delivery` when an `NpgsqlDataSource` is registered, else in memory), ordered oldest first, checked with `GitHubEventOrdering` against the last applied state per PR (in memory), mapped by `GitHubEventMapper`, and handed to `IGitHubEventSink` as a `GitHubEventDelivery` (`Apply` false and no effects for an older event). An event is marked processed only after the sink accepted it. `github_rate_state` now backs `IGitHubRateState` when a data source exists (`PgGitHubRateState`, bucket `core`).

Seams left open: (1) `IGitHubEventSink` has no implementation here; the GC log writer (doc 01) and the inbox (doc 06) contracts are not public on main, so wiring them is the PR service work package. (2) The Events API never returns `check_run` or `check_suite`, so check failures arrive only by webhook (a polled `push` is resolved to its PR by the PR lookup below). (3) Only the first page (100 events) is read; a busier repo than 100 events per interval can miss events. (4) Per-PR applied state is in memory and starts empty after a restart (`github_pr` needs `gc_id`, which the PR service owns). (5) The Events API does not state the actor's association, so only logins in `MemberLogins` and `AgentLogins`, or an object whose author is the actor, count as members; everything else is external (hard taint, no wake).


**Webhook processor (doc 21 Ingress, work package 5).** `GitHubWebhookProcessingService` (namespace `Bazaar.GitHub.Processing`) reads the stored `github_delivery` rows that the webhook ingress wrote (source `github`, `processed_at` null) and hands them to the same `IGitHubEventSink` as the poller. Migration `0003_github_delivery_processed.sql` adds `process_attempts`, `next_attempt_at` and `process_error` (and `processed_at` if missing) plus a partial index on unprocessed rows. Several server instances may run it: a claim is one `UPDATE ... WHERE (source, delivery_id) IN (SELECT ... FOR UPDATE SKIP LOCKED)` that bumps the attempt count and pushes `next_attempt_at` out by a lease, so two instances never take the same row and a crashed instance's rows come back after the lease. `GitHubWebhookPayloadParser` reads the webhook body shapes (`pull_request`, `pull_request_review`, `pull_request_review_comment`, `issue_comment`, `issues`, `check_run`, `check_suite`, `push`); other event types (for example `ping`) are marked processed and ignored. Each parsed event goes through `GitHubEventOrdering` (last applied state per PR is kept in memory, per instance), `GitHubEventMapper`, then `IGitHubEventSink.DeliverAsync`; only after the sink accepts it is `processed_at` set. A sink throw leaves the row unprocessed and schedules a retry with exponential backoff (30 s doubling to 15 min, `Bazaar:GitHub:Processor`). A row that cannot be parsed (no payload, bad JSON, missing ids) is a poison row: it is marked processed with the reason in `process_error`, so it never loops. **Dedupe keys differ on purpose:** webhook rows are keyed `(github, <delivery guid>)` and sink key `github:<guid>`, polled events `(poll, <event id>)` and `github:poll:<id>`; the two are not unified, so the same logical change seen by both paths is delivered twice, and the sink's own idempotence (the `#<effect index>` keys) is what makes that safe. `AddBazaarGitHub` registers the service always but it stays idle, with one log line, unless a real sink and an `NpgsqlDataSource` exist. Webhook `check_run`, `check_suite` and `push` bodies carry no PR node id; see the PR lookup paragraph below for how they reach a PR GC.
**GC and inbox sink (doc 21, work package 5).** `GitHubGcEventSink` is the real `IGitHubEventSink`; the poller and the webhook path both end in it. For each mapped effect it appends one event through `IGcLogWriter` (kind `pr_event` for PR entries, `structured` for the rest; idempotent on `<dedupe key>#<effect index>`), then enqueues the inbox rows that effect says wake, through `InboxRepository` (`mention` stays `mention`; assignment, review feedback and check failure all become `assignment` until doc 06 names a kind, which is OPEN). An external effect is written with `SourceTrust.External`, explicit hard taint and no excerpt, and never wakes, even if its draft claims to. The event's own author is never woken by it (loop guard). Owner notices are written to the GC but make no row, because `inbox_item` is agent-only. A PR GC comes from `github_pr.gc_id`, an agent from `github_app.account_login`, and the Inbox GC from `Bazaar:GitHub:Ingress:InboxGcId`; events are written under the GitHub bridge system principal. Bazaar has no principal table to seed, and system authors are fixed ids, so the bridge principal is a stable id derived (version 5 UUID) from a fixed namespace GUID and the name `bazaar.system.github-bridge` (`GitHubBridgePrincipal.Id`). Every instance and every restart derives the same id with no operator input and no stored state, so it is idempotent by construction; `Bazaar:GitHub:Ingress:BridgePrincipalId` is now only an optional override. The sink appends through `IGcLogWriter`, which already lives in `Bazaar.GC.Abstractions` (the PR #1150 contracts `IGcWriteAccess`, `IGcHistorySource` and `IGcMembershipSource` are read-side and have no append). With no GC writer or database the sink stays `UnwiredGitHubEventSink` and the poller stays off. Still open: issue GCs have no table, so issue entries are not posted; the PR service (WP6) must create PR GCs and fill `github_pr`; (the processor below now exists).

**PR GC creation and read model (doc 21, work package 6).** `GitHubPrService` (namespace `Bazaar.GitHub.Pr`) creates a PR's GC once and fills `github_pr`, and `GitHubPrGcEventSink` runs it before the GC sink so `PgGitHubGcDirectory` finds the GC. The GC id is derived from the PR node id, `github_pr.pr_node_id` and `gc_id` are unique, and the row is written with `ON CONFLICT DO NOTHING`, so concurrent callers and replays make one GC and one row. Only `pull_request` events change PR state (title, state, draft, head, base, author login), and an older event is stored but not applied over newer state (`GitHubEventOrdering`, decided under a row lock). A PR first seen through a comment gets a row with the epoch as `updated_at`, so the later real PR event is not rejected as older. Migration `0004_github_pr_read_model.sql` (after the processor's `0003`) adds `title` and `author_login` and lets `head_sha` and `base_ref` be null until an event carries them. Members are the owner, the bridge principal, and the agents that authored the PR, were assigned or were asked to review it; an agent named by a later event is added then. **PR lookup for check and push events (doc 21, Event mapping).** `check_run`, `check_suite` and `push` payloads carry no PR node id, so `GitHubPrResolver` (`Bazaar.GitHub.Pr`, `GitHubPrLookup.cs`) fills it before ordering and mapping, in both the webhook processor and the Events API poller, from the `github_pr` read model through `IGitHubPrLookup` (`PgGitHubPrLookup`; `NoGitHubPrLookup` when there is no database). Rules: only an **open** PR in the same repository matches; `check_run` and `check_suite` match first by the numbers in the payload's `pull_requests[]` (the parser fills `GitHubEvent.PullRequestNumbers`) and otherwise by the stored `head_sha` equal to the checked commit; `push` matches by `head_sha` equal to `after` (a branch-deleting push, whose `after` is all zeros, matches nothing). With several matches the lowest PR number wins. The PR author login comes from `github_pr.author_login`, so a failed check (`failure` or `timed_out`) becomes the `pr_event` entry in the PR GC plus an author inbox item that wakes the authoring agent (doc 21; not for external actors, since checks are not content and never taint). No match (an unknown PR, a fork check with no `pull_requests`, a closed PR) is not an error and produces no effect. The lookup runs inside the processing attempt, so a database failure retries the row. Ordering and dedupe are unchanged: the resolved event goes through `GitHubEventOrdering` against the PR's last applied state like any PR event. **Branch match (PROPOSED, migration `0008_github_pr_head_ref`).** `github_pr.head_ref` stores the head branch name, filled from `pull_request.head.ref` by `pull_request` events only and only for a same-repository PR (fork PRs store null, so a fork branch name cannot match a same-named branch of the base repository). `GitHubEvent.HeadRef` carries it: the pull request object's `head.ref` on PR events, and on `push` the name from `refs/heads/<name>` (null for tags and for a branch-deleting push). `IGitHubPrLookup.FindOpenAsync` takes the branch as a fourth argument and tries number, then head SHA, then branch, so a push to the PR branch before the `synchronize` event has stored the new head SHA lands in the PR GC (one `pr_event` entry, no wake). Limits: a PR first seen through a non-`pull_request` event has no branch until its next `pull_request` event; check events are still matched by number and SHA only (a `check_suite` `head_branch` match is not built); pushes to a fork never reach the base repository's webhook, so fork PR pushes stay unmatched.

**Issue GCs (doc 21, Issue GCs).** `GitHubIssueService` (namespace `Bazaar.GitHub.Issues`) is the PR service's sibling: it creates an issue's GC once and fills `github_issue` (migration `0006_github_issue_read_model.sql`, and `0007_github_issue_gc_type.sql` registers the `issue` GC type, because the core seed has none and the file needs the core schema, like `0005`), and `GitHubIssueGcEventSink` runs it before the GC sink so `PgGitHubGcDirectory` now resolves issue targets from `github_issue.gc_id` instead of null. Creation goes through `IGitHubIssueGcFactory` (real one: `GcProvisionerIssueGcFactory` over `IGcProvisioner`). The sink chain is PR sink, then issue sink, then `GitHubGcEventSink`. The GC id is derived from the issue node id; only `issues` events change state, ordered with `GitHubEventOrdering` under a row lock. `GitHubEvent` gained `IssueNumber`, `IssueTitle`, `IssueState`, `IssueAuthorLogin`, `IssueAssigneeLogins` and `AssignedLogin`, filled by both parsers, and the mapper maps `issues` `assigned` (agent assignee) to an `assignment` wake. Members are the owner, the bridge, and agents that authored, were assigned or were @-mentioned by a member; a stranger's issue that names no agent gets no GC and stays in the Inbox GC, and a stranger never adds a member or wakes. Entries use GC kind `structured`, which the core seed has, so no new event kind. Options under `Bazaar:GitHub:IssueGc`: `OwnerPrincipalId` (falls back to `PrGc:OwnerPrincipalId`, then the bridge), `GcTypeKey` (default `issue`), `MaxAgentMembersAtCreate` (7). OPEN items are listed in doc 21, Issue GCs.

## Gateway catalogue module (doc 05 work package 11)

`Bazaar.Server.Gateway.Catalogue.Abstractions` holds `CatalogueDiff`, `CatalogueRefreshResult`, `IProviderModelLister`, `ICatalogueRefresher` and `ICatalogueSchedule`. `Bazaar.Server.Gateway.Catalogue` holds `CatalogueDiffer` (pure), `OpenAiModelListParser`, `HttpProviderModelLister` (`GET {base_url}/models` for `openai_chat` providers), `CatalogueRefresher`, `CatalogueRefreshService` (reads `gateway.catalogue.refresh_hours`; 0 means no scheduled run) and `CatalogueComponent`. The host maps `ICatalogueSchedule` onto the settings store. The refresher writes only `gw_model` rows: a model that vanished upstream becomes `missing`, one that returned becomes `available`, a new one is inserted `available` with the family and identity of the provider's most recently seen model (a provider with no model to copy from reports the ids as unclassified and inserts nothing). A failed list call changes nothing. No policy, whitelist or route is edited. `HttpProviderModelLister` also reads the Anthropic (`GET /v1/models`, `x-api-key`, `anthropic-version`, paged by `after_id`) and Gemini (`GET /models`, `x-goog-api-key` header, paged by `pageToken`) lists, at most 20 pages, and a list that never ends counts as a failed read so no model is wrongly marked missing.

**Manual check (PROPOSED).** `IAdminCatalogueRefresh` (in `Bazaar.Server.WebAdmin.Abstractions`) is the port behind the panel button; `CatalogueAdminPort` in this module implements it over `ICatalogueRefresher.RefreshAllAsync` and keeps the last result and time in memory (`CatalogueLastRun`, recorded for scheduled runs too). Routes: `POST /admin/api/gateway/catalogue/refresh` and `GET /admin/api/gateway/catalogue` (doc 51 section 5). The report carries only provider id, outcome (`refreshed`, `listFailed`, `skipped`), counts of added, missing and returned models, and unclassified model ids: never a key, URL or response body.

The shipped default catalogue file is built (`DefaultCatalogue/default-catalogue.json`, embedded in `Bazaar.Server.Gateway.Catalogue`): 20 secret-free entries, one per source of doc 05's table (the combined rows are split), typed as `DefaultCatalogueEntry` and `DefaultCatalogue` in the Abstractions project and read by `DefaultCatalogueLoader` (source-generated JSON; rejects duplicate ids, unknown adapters, non-absolute http(s) base URLs and secret-looking names or values). `freeTier`, `termsRisk` and `trainsOnFreeData` are `unknown` for every entry, because doc 05 gives no values; the owner or a raw-page check fills them. `verification` (V, P, U) and its note are copied from the Status column. Nothing consumes the file yet.

`Bazaar.Archive.Http` holds the owner-only routes (`MapArchive`) and is mapped in `Program.cs` behind `HttpSurfaceEndpoints.Guarded`. `GcArchiveSourceFactory` (in `Bazaar.Archive.Gc`) builds the per-owner GC and project sources; the host registers it with `AddGcArchiveBridge` in `ArchiveCompositionExtensions`.

`Bazaar.Client.ColdArchive` and `Bazaar.Client.ColdArchive.Abstractions` hold the owner-only cold-storage pane (`ColdArchivePaneModule`, `HttpColdArchiveClient`, `IColdArchiveClient`), composed in `WindowsModules` and fed through `PaneModuleContext.With<IColdArchiveClient>` in the Windows `Program.cs`. Tests: `tests/Bazaar.Client.ColdArchive.Tests` (HTTP client, view model, headless render).
