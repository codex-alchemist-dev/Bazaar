# 57. Athanor: the built-in IDE and editor

Status: PROPOSED (2026-11-18). Number 57 (52 to 56 taken by other docs). Implements the module split for Athanor. The name, Monaco, the WebView2 island, the key model and the theme rule are DECIDED elsewhere and only restated here with their source. Everything else here is PROPOSED and was filled by the working session where the docs were silent (CLAUDE.md, configurability rule).
Depends on: 41 §4.10, §4.12, §4.14, §4.15; 27 (client architecture, `IEditorHost`); 28 (editor host, process model, Monaco gate); 41b (client module boundaries); 40 (module layout); 49 (keyboard model).

## 1. What is DECIDED (restated, not new)

- Athanor is the built-in IDE and text editor of the Bazaar client, and runs standalone as a replacement for the system text editor (doc 41 §4.10, §4.15; FEATURES.md).
- Monaco in a WebView2 island, composition embedding as the first design. Windows only. Android never uses Monaco (doc 27, 28, CLAUDE.md). The Linux editor waits for a WebKitGTK spike after S12 (doc 27 Q9); `Bazaar.Client.Athanor.AvaloniaEdit` (PROPOSED, §2) is the in-process alternative and the proposed Linux default.
- One client process, many top-level windows, one shared WebView2 environment, one Monaco bundle, one controller per window, tabs swap Monaco models over a JS bridge (doc 28 process model).
- The editor is Monaco per window behind `IEditorHost`, so a native fallback can replace it (doc 28). Local-disk saves follow `windows.editor.local_write`, default `server-backed` (doc 28).
- One theme file drives Athanor's colours, fonts and syntax palette. No second palette (doc 41 §4.15, doc 27). Generator: `MonacoThemeGenerator` (exists).
- Monaco's diff editor is the single diff component, used by the Git client module (doc 41 §4.14, §4.15). No custom editing engine.
- Keys follow the client key model (doc 41 §4.12, doc 49): Vim is the reference when in doubt, no Ctrl chords. Athanor inherits Monaco's keyboard model and documents its exceptions (doc 49).
- Hosting is gated by spike S12. Nothing in this doc assumes S12 passes.
- Renderer crash: reload the bundle and reopen models from the server. Unsaved edits stay in a local draft file until the server accepts them (doc 28).
- Clearance for the name Athanor is a later task (doc 41 §4.14). Keep it out of package IDs that are published publicly until decided; the in-repo project names below are working names.

### 2.1 Linux GTK helper (PROPOSED, 2026-11-20)

Spike S13 showed Monaco works in WebKitGTK but embedding the GTK widget in an Avalonia window is unsolved (XEmbed is X11-only and fragile, Wayland has no re-parenting, two main loops). So the Linux Monaco option is a **separate process**, option (b) of S13.

**Window mode (chosen: companion window).** The helper owns its own top-level GTK window. No XEmbed, no re-parenting, no `NativeControlHost`. The client sends placement messages (`x`, `y`, `width`, `height`, `visible`, `title`); size, title and visibility are always honoured, and the position is honoured only where the display server lets an application move its own window (X11). On Wayland the compositor places the window, so the position is a hint that is ignored, and the pane in the main window shows a "editor is in its own window" state with a button that raises it. Closing the window hides it and reports `helper.windowClosed`; it does not end the helper. A key the client router claims (doc 57 §7) is sent to the client as `keyPressed` as today; raising the main window is the client's job. This is the most robust choice because it works the same on X11 and Wayland and never couples the two event loops.

**Process and transport.** `Bazaar.Client.Athanor.Gtk` starts the helper with redirected standard streams. The wire is **one JSON object per line** (UTF-8, `\n`, no embedded raw newlines; the serializers escape them) on stdin (client to helper) and stdout (helper to client). Standard error carries diagnostics only. A line over the codec payload limit (default 8 MiB) is a protocol error. When the client dies, stdin closes and the helper exits, so no orphan stays.

**Two layers on the same lines.** (1) The doc 57 §4 bridge messages, encoded and decoded by the existing `BridgeCodec`, with the existing `seq` rules, relayed unchanged between the proxy and the Monaco page; the helper never interprets them. (2) A small control layer whose `type` starts with `helper.`, handled by the helper itself and never forwarded to the page:

| Direction | Type | Fields |
|---|---|---|
| helper to client | `helper.hello` (first line) | `protocol` (1), `webkit` (version text), `sandbox` (bool), `pid` |
| helper to client | `helper.pong`, `helper.windowClosed`, `helper.fatal` | `id`; none; `code`, `message` (for example `web_process_terminated`, `load_failed`) |
| client to helper | `helper.window`, `helper.ping`, `helper.shutdown` | placement fields above; `id`; none |

**Handshake.** `helper.hello`, then the page's bridge `ready`. The proxy refuses a helper that sends another first line, a different `protocol`, or `sandbox: false` (unless the operator allows it, below). A handshake that does not finish within the timeout (default 15 s) kills the helper.

**Supervision.** The proxy tracks every open document (latest content, version, read-only flag), the theme and the window placement. A helper death (process exit, `helper.fatal`) raises `Crashed(RendererExited)`; a protocol violation (malformed line, unknown type, oversize line, non-increasing `seq`, wrong first line) kills the helper and raises `Crashed(BridgeFault)`; a missed handshake or ping timeout (ping every 5 s, timeout 10 s) kills it and raises `Crashed(Unknown)`. On any of these the proxy writes the dirty documents to `IEditorDraftStore` (doc 57 §5) and restarts the helper with exponential backoff (default 0.5 s doubling to 30 s, at most 5 restarts in a row; the count resets after a run of 60 s). After a restart it replays the theme, the window and every open document with its latest content, so typing survives a crash. After the last failure the host is `Faulted` until the head calls `RestartAsync`; the head can then swap in `AvaloniaEdit`. All limits are settings with these defaults.

**Sandbox (production).** The helper runs with the WebKit sandbox on: it sets `WEBKIT_FORCE_SANDBOX=1` for its own native environment, refuses to start (exit 3) when `WEBKIT_DISABLE_SANDBOX_THIS_IS_DANGEROUS` is set, and refuses (exit 4) when `bwrap` is not on `PATH`. The only way around this is the command-line flag `--allow-no-sandbox`, which the proxy passes only when the operator sets `AllowNoSandbox` (default false, for root-run containers and CI); the helper then reports `sandbox: false` and the proxy refuses it unless that option is set. No network: the helper loads the bundle through a registered `athanor://app/` scheme served from the directory given by `--bundle`, ignores every navigation to another URI and every new-window request, and the bundle page must carry a content security policy that allows only that scheme. Path traversal outside the bundle directory returns an empty not-found response. WebKitGTK stays a runtime dependency (the P/Invoke libraries are loaded at run time, nothing links to GTK at build time); a missing library makes the helper exit 6 and the proxy report `Crashed(RendererExited)` and fault after the retries.

**Not done here.** The Monaco bundle (`Bazaar.Client.Athanor.Bundle`), IME on Linux (S13 untested), a minimum WebKitGTK version, packaging the helper next to the client head, and the head wiring.

### 2.2 Head composition (PROPOSED, 2026-11-22)

Heads only compose; the choices live in testable classes in the Athanor modules and nothing goes into `Bazaar.Client.Core` or `Bazaar.Server`.

- **Host selection.** `EditorHostSelector` (in `Bazaar.Client.Athanor`) takes an ordered preference and the candidates a head offers (kind, availability check, factory) and returns the first that is available and constructs. Default order (`auto`): Windows is WebView2, then AvaloniaEdit, then the plain-text host; Linux is AvaloniaEdit, then the plain-text host. The operator setting names one kind to try first (`webview2`, `gtk`, `avaloniaedit`, `plain`); the rest of the default order follows it. The plain-text host always ends the chain. A candidate the head does not offer (GTK on Windows), one that reports itself unavailable, or one whose factory throws is skipped and the reason is returned in the choice, so the head can log it. WebView2 is available when the OS is Windows, the WebView2 runtime is installed and the bundle verifies; GTK is available only when the operator selected it, the helper executable exists and the bundle folder holds its host page; AvaloniaEdit is always available.
- **Settings (operator, read by the head from the environment until the settings service reaches clients).** `BAZAAR_ATHANOR_HOST` (default `auto`), `BAZAAR_ATHANOR_DATA` (the data folder; default under the platform's per-user data folder: `LocalApplicationData/Bazaar` on Windows, the XDG state folder on Linux; no drive letter or system path is assumed, so a relocated data folder such as one on a RAM drive works), `BAZAAR_ATHANOR_GTK_HELPER` (path to the helper). Drafts live in `<data>/athanor-drafts` (unchanged on Windows) and the WebView2 profile in `<data>/athanor-webview2`. An unknown host value falls back to `auto` and is reported. `AthanorHeadOptions` parses these.
- **File source.** With a server connection (the head has connection settings) the head uses `WireEditorFileSource` through `AthanorWireConnection` (`Bazaar.Client.Athanor.Wire`: its own `WireClient` on the same endpoint and credential, started on demand and cancelled on dispose, every request bounded by a timeout, default 15 s, after which open throws `editor.unavailable` and save answers `Unavailable`, so the draft stays). Without one it uses `OfflineEditorFileSource`. `EditorFileSourceSelector` makes that choice.
- **Surface.** A host that is an Avalonia control, or implements `IEditorSurfaceHost` (AvaloniaEdit: its `Root`), is placed in the pane in place of the plain `TextBox`; the plain host and the GTK host (own window) keep the `TextBox`/state view.
- **Styles.** The AvaloniaEdit theme (`avares://AvaloniaEdit/Themes/Fluent/AvaloniaEdit.xaml`) is added to the application styles by the head through `AvaloniaEditStyles.Include`, not by `Bazaar.Client.Core`.
- **Hosts are created on the UI thread.** Controls cannot exist before Avalonia starts, so the head builds the editor services when it builds the main window, not in `Main`. `--athanor` shows the editor pane in the main window.
- **Manifests.** `Bazaar.Client.Athanor.WebView2`, `.Bundle`, `.AvaloniaEdit`, `.Gtk` and `.Wire` contribute no pane kind, command or setting, so they declare no `IClientModule` manifest; `bazaar.athanor` (in `Bazaar.Client.Athanor`) is the one module. The module system needs a manifest only for something a head registers.
- **Command host (PROPOSED, 2026-11-22).** No head ran a mnemonic runtime, so no module command was reachable by key. The shared pieces live in `Bazaar.Ex` (the existing mnemonic and command-input module), never in `Bazaar.Client.Core`: `ClientCommandDispatcher` (handlers register by predicate; an id nobody handles is logged and announced, never thrown) and `MnemonicHeadHost` (builds the `MnemonicRuntime` from the commands the loaded modules contributed, with the remaps in `<data>/mnemonics.json`, attaches `MnemonicHost` to the main window, mounts the live region and the palette on the window's overlay layer, and feeds `CommandInvoked` and palette choices to the dispatcher). Each head composes it only with `--athanor`, next to the editor, so a normal start is unchanged and no other module's behaviour changes: their commands have no handler yet and are reported as such. The Athanor handler is registered with `AthanorCommandHandler.Handles` and `AthanorPaneModule.RunCommandAsync`; a result that is not `Done` is announced. Mnemonics stay typed text plus Enter: no Ctrl chord is claimed, and Ctrl+S stays with the editor. The palette mnemonic is `palette` (the same text `EditorRouterTable` already used). `athanor.open` and `athanor.new` still answer "No document picker is available" until a head supplies `IEditorCommandPrompts`; the picker is a later step.
- **Theme source (PROPOSED, 2026-11-22).** No head owned the app theme. `Bazaar.Client.Theme` gains `ClientThemeService` (the current validated `ThemeDefinition`, `Set`, and a `Changed` event; it starts from `<data>/theme.json` when that file validates, else from the built-in dark theme embedded in the project). Athanor gains `IEditorThemeSource` (current theme plus `Changed`), `ClientThemeEditorSource` (adapts the service) and `EditorThemeSync` (pushes the current theme when started and again on each `Changed`, serialised, to the active `IEditorHost`: Monaco through `setTheme`, AvaloniaEdit through `SetThemeAsync`; a failed push is logged, never thrown). Both heads create the service and the sync next to the editor. The Avalonia app styles are not regenerated here; that stays with the shell owner.
- **Not done here.** Swapping the GTK host for AvaloniaEdit after `Faulted` is the head's job later.

## 3. Host contract (PROPOSED)

`IEditorHost` is the seam. A host owns one editor surface (one window) and speaks the bridge in §4.

- `OpenAsync(EditorDocument)`, `CloseAsync(documentId)`, `FocusAsync()`, `SetThemeAsync(themeJson)`, `SetReadOnlyAsync(bool)`, `ShowDiffAsync(original, modified, language)`.
- Events: `Changed` (dirty, version), `SaveRequested`, `KeyPressed` (for the Vim layer), `Ready`, `Crashed`.
- A host never touches the network. All reads and writes go through `IEditorFileSource`, which the head wires to the server connection. The client holds no repository credential (doc 28; doc 21).
- `PlainTextFallbackHost` implements the same interface over an Avalonia `TextBox` for tests, for Linux before its spike, and as the failure fallback if S12 fails. It exists so Athanor works end to end in headless tests.

## 3a. WebView2 hosting and its airspace limit (PROPOSED, from spike S12, 2026-11-20)

S12 (`docs/spikes/S12.md`) hosted Monaco through Avalonia's `NativeControlHost`, which gives a **child HWND** (doc 28 option D), not a composition-embedded visual. This note replaces the "composition embedding as the first design" wording in §1 until the owner decides otherwise; a composition spike is out of scope for now. Consequences the module must live with:

- **Airspace.** Avalonia content cannot draw over the editor rectangle. Popups, tooltips, menus, drag adorners and toasts that overlap the editor must be separate top-level windows, or the editor must be inset. Animations and transitions that cross the editor do not composite.
- **Focus.** Keyboard focus lives inside the WebView2 HWND, so the client key router never sees a key Monaco consumes. The handoff in §7 therefore cannot be a synchronous call per key. The host pushes the table of claimed keys to the page (`setClaimedKeys`, §4); the page decides locally, swallows a claimed key and reports `keyPressed`, and the host then takes focus. Keys not in the table never reach the router.
- **Resize and DPI.** The controller bounds follow the host control's arranged size and the child window's client rectangle.
- **One environment.** All windows share one `CoreWebView2Environment` (pre-warmed at client start), whose user-data folder is set by the caller and lives under the client data folder, never in a system profile path.

## 4. Bridge protocol (PROPOSED)

JSON messages over the WebView2 message channel, source-generated `System.Text.Json` (same rule as the wire format, no reflection, no Protobuf). Two directions:

- Host to editor: `open`, `close`, `setTheme`, `setReadOnly`, `showDiff`, `applyEdit`, `focus`, `setClaimedKeys` (the keys the client key router claims, as `KeyboardEvent.code` chords such as `Alt+KeyM`; never a Ctrl chord; sent on ready and whenever the router's table changes).
- Editor to host: `ready`, `changed`, `saveRequested`, `keyPressed`, `selection`, `error`.

Every message carries a `type`, a monotonically increasing `seq` and the `documentId` where one applies. The codec rejects unknown types, oversize payloads (default 8 MiB, configurable) and out-of-order `seq` from the editor, and never evaluates a script string built from user text. Theme payloads come from `MonacoThemeGenerator` and are pushed without a reload.

## 5. Documents, saves and drafts (PROPOSED)

- A document is identified by a `DocumentId` made of a workspace id, a path inside it and a server revision. Paths are normalised and may not escape the workspace root; the check is on both the client and the server.
- **Save:** the coordinator sends the content with the revision it opened. The server accepts only when the revision still matches; a mismatch returns a conflict, and the editor shows Monaco's diff against the server copy. No silent overwrite.
- **Drafts:** every dirty document is mirrored to a local draft file (debounced, default 1 s), keyed by workspace and path, removed only after the server accepts the save. A draft survives renderer crash and client restart and is offered back on reopen. Draft files hold only what the user typed, are stored under the client data folder, and are covered by the data-portability export as a derived item (doc 44 follows its own rules).
- **Local-disk saves:** `windows.editor.local_write` stays as doc 28 says. `server-backed` (default) keeps local folders read-only until a save is accepted. Athanor never writes a local path itself without that setting.
- **Large and binary files:** open read-only above a size limit (default 5 MiB, configurable) and refuse binary content.
- **Language:** chosen by file extension and a first-line hint from a registry data table. Language servers are Monaco's built-in services only in v1; external language servers need their own design.

## 6. Server side (PROPOSED, not built in the first series)

`Bazaar.Server.Athanor` exposes open and save for files in a workspace the server controls: the Vault repo, agent worktrees and project repos. It adds no file store of its own. It resolves a workspace id through the existing Vault (doc 18) and git (doc 21) providers and never reads outside the workspace root.

**Wire pair (PROPOSED, for doc 02 after review).** Two request and response types on the existing envelope (`k` is `req` and `res`, or `err`). Payloads are JSON records in `Bazaar.Contracts`, namespaced `Athanor`.

| Type | Request payload | Response payload |
|---|---|---|
| `editor.open` | `workspaceId`, `path` | `content`, `revision`, `languageHint?`, `readOnly`, `sizeBytes` |
| `editor.save` | `workspaceId`, `path`, `baseRevision`, `content` | `newRevision` |

Revisions are opaque server strings (for a git workspace, the blob id of the file at the head being edited). Error codes on `err`: `editor.not_found`, `editor.conflict` (carries `serverRevision` and `serverContent`), `editor.forbidden`, `editor.too_large`, `editor.binary`, `editor.read_only_workspace`, `editor.unavailable`. `editor.conflict` maps to `SaveOutcome.Conflict`, and `editor.unavailable` and transport failures map to `SaveOutcome.Unavailable`.

**Authority.** The caller is the signed-in human; the save is the human's own edit, so it needs no approval gate, but it requires the `vault.write` or `git.worktree.write` scope on the workspace (doc 48 §1 vocabulary, doc 15). A save never merges or pushes: it writes the working tree or Vault file, and the normal PR and approval path (doc 21, owner signed approval) governs anything outward. Agents never call these messages. Every accepted save writes an audit row (user, workspace, path, base and new revision, byte count).

**Limits (settings, safe defaults).** `athanor.max_open_bytes` 5 MiB, `athanor.max_save_bytes` 5 MiB, `athanor.save_rate_per_min` 60 per user. Path rules are the client's (§5) enforced again on the server, plus symlink resolution that must stay inside the root.

**Server module details (PROPOSED, first server PR, 2026-11-20).** `Bazaar.Server.Athanor` and `Bazaar.Server.Athanor.Abstractions` hold the open and save handlers, path rules, a per-user sliding-window rate limiter, an in-memory store for tests and the three settings keys. Choices where this section was silent:
- The module does not reference `Bazaar.Server`, so it holds no envelope types. `EditorOpenHandler` and `EditorSaveHandler` take the caller and the payload record and return an `EditorResult<T>` (value, or error code with message, `retryAfterMs` and conflict detail). The host adapter maps that to `res` or `err`. The payload records live in `Bazaar.Server.Athanor.Abstractions` until the pair is accepted into `Bazaar.Contracts` and `WireJsonContext`.
- Storage is `IEditorWorkspaceStore` (workspace lookup, size-capped read, atomic compare-and-set write, symlink containment); authority is `IEditorAuthorizer`, asked for `Read` on open and `Write` on save with the workspace kind (`Vault` needs `vault.write`, `GitWorktree` needs `git.worktree.write`). Open needs read access (`editor.forbidden` otherwise) and returns `readOnly: true` when the workspace is read-only or the caller lacks the write scope.
- Codes where none is named: a malformed path, empty field or path rule violation returns the envelope's `bad_request`; the save rate limit returns the envelope's `rate_limited` with `retryAfterMs`. Saving to a file that does not exist returns `editor.not_found` (the editor creates no files).
- Path rules: backslashes are separators; `.` and empty segments are dropped; `:`, control characters, a leading separator, `..`, a trailing separator, a segment ending in `.` or a space, and paths over 1024 characters are rejected.
- Check order on save: payload, path, workspace (`not_found`), read-only workspace, write scope (`forbidden`), rate limit, size (UTF-8 bytes), binary (NUL or invalid UTF-8), then the store write. Every attempt that passes the scope check counts toward the rate limit, including conflicts. Open and save limits are checked with `>`, so a file of exactly the limit is accepted.
- Settings `athanor.max_open_bytes`, `athanor.max_save_bytes` and `athanor.save_rate_per_min` are install-scope, operator-changed keys, minimum 1, contributed through `ISettingContribution`. The host supplies `IAthanorLimits` from the settings reader.
- The audit row is `kind: editor.save`, actor the user id, payload `{workspaceId, path, baseRevision, newRevision, bytes}`, appended after the write. Rejected and conflicting saves write no row. If the append throws, the error propagates to the host as `internal` and the file stays written.

**Host wiring and on-disk store (PROPOSED, 2026-11-22).** Docs section this implements: §6 above.
- **Adapter location.** `IWireRequestHandler` lives in `Bazaar.Server`, and the Athanor module must not reference it, so the adapter is host glue in `Bazaar.Server.Host/Composition` (`AthanorWireHandlers`, `SettingsAthanorLimits`, `AddBazaarHostAthanor`), where modules are already wired. Nothing is added to `Bazaar.Server`. `editor.open` and `editor.save` are registered as `IWireRequestHandler`s. Only a connection whose principal is `owner` or `human` may use them (`editor.forbidden` otherwise); the user id is the connection's principal id, never the payload's.
- **Mapping.** The `Bazaar.Contracts/Athanor` records are mapped to the module records. A failed result is an `err` with the result's code, message and `retryAfterMs`. A conflict is a normal `res` to `editor.save` with `serverRevision` and `serverContent` and no `newRevision` (answer 1 of the client mapping below). A malformed payload is `bad_request`.
- **Limits.** `SettingsAthanorLimits` reads the three install-scope keys through `ISettingStore`; the adapter refreshes them before each request, so a change applies on the next call. A failed read keeps the last good values. The settings keep minimum 1; no ceiling is added (a tighten-only floor is not in the doc).
- **Workspaces.** `IEditorWorkspaceResolver` maps an id to a host directory. `ConfiguredEditorWorkspaceResolver` reads `Bazaar:Athanor:Workspaces` (`Id`, `Kind` Vault or GitWorktree, absolute `Path`, `ReadOnly`; empty by default, so nothing is editable until the operator names a root). `GitRepositoryEditorWorkspaceResolver` maps `git:<repositoryId>` to the clone in `IGitRepositoryDirectory` (doc 52) when one is registered, read-only when `Bazaar:Athanor:GitRepositoriesReadOnly` is true. The Vault root has no registration in the host yet, so it is a configured workspace.
- **Store.** `DirectoryEditorWorkspaceStore`: the path is re-validated and must already be in normal form; every segment from the root down is checked, and a symlink or reparse point anywhere in the chain (inside or outside the root, file or directory, dangling) is refused; so are a `.git` segment (hooks and config) and Windows device names. A refusal is `EditorReadStatus.Blocked` or `EditorWriteStatus.Blocked`, answered `editor.forbidden`. Reads refuse by length and never read more than the cap plus one byte. A write holds a per-file lock, hashes the current bytes (SHA-256 lower-case hex, the revision), compares with `baseRevision`, and on a match writes a temp file in the same directory and renames it over the target (file mode kept on Unix). A server copy over `athanor.max_open_bytes` cannot be returned as a conflict copy, so the write is `EditorWriteStatus.TooLarge` (`editor.too_large`). A read-only workspace refuses writes in the store as well as in the handler. Residual risk: a link planted between the last check and the rename is not excluded.
- **Authorizer.** `RolesEditorAuthorizer` asks the role checker (doc 48 section 4) as a human principal: Read needs `read`; Write needs `vault.write` over the company scope (Vault) or `git.worktree.write` over the repository scope named by the workspace id (git worktree). A grant at company or instance level covers both. A user id that is not a GUID is refused.

**Client mapping (PROPOSED, 2026-11-20).** `Bazaar.Client.Athanor.Wire` implements `IEditorFileSource` over this pair. The payload records live in `Bazaar.Contracts/Athanor` and are registered in `WireJsonContext` (the generic wire client only encodes registered types); wire type names are `WireTypes.EditorOpen` and `WireTypes.EditorSave`. The `err` envelope (`WireError`) has no field for `serverRevision` and `serverContent`, so a conflict is answered two ways, and the client accepts both: (1) a normal `res` to `editor.save` with `serverRevision` and `serverContent` set and no `newRevision`; (2) `err` `editor.conflict`, after which the client re-reads the server copy with `editor.open` and builds the conflict from that. Mapping: `editor.open` with `editor.not_found` returns null; every other open refusal (`forbidden`, `too_large`, `binary`, `read_only_workspace`, `unavailable`, unknown codes, transport failure, an incomplete reply) throws `EditorFileException` carrying the code (`editor.malformed` for an incomplete reply), because `IEditorFileSource.OpenAsync` has no failure result. `editor.save` maps a reply with `newRevision` to `Saved`, a reply with the server copy to `Conflict`, and everything else (every other error code including `not_found`, transport failure, an empty, incomplete or contradictory reply) to `Unavailable` with the code in the reason, so the draft stays. A missing `languageHint` becomes `plaintext`. The client refuses an unnormalised id before sending. Cancellation is never mapped.

Until the server module exists, `IEditorFileSource` has a read-only in-memory implementation for tests and a no-op "server unavailable" implementation for offline (doc 28: offline shows cached state only, no write queue). A server-backed `IEditorFileSource` over this pair lands as `Bazaar.Client.Athanor.Wire` after the contracts are accepted.

**Conflict hand-off (PROPOSED, 2026-11-22).** `IEditorConflictSink` (in `Bazaar.Client.Athanor.Abstractions`) lets a conflict list, for example the Vault offline-sync module (doc 18), receive each save conflict next to the editor's own diff. `SaveCoordinator` calls `OpenedAsync` once per distinct server revision, with the base revision, the user's content and the server copy, and `ResolvedAsync` when the user keeps their text or takes the server copy. The editor never waits on a sink and ignores its failures; with no sink nothing changes, and the editor's own conflict diff and draft remain the source of truth. No sink implementation ships in Athanor.

**Vault root as a workspace (PROPOSED, 2026-11-22).** Module `Bazaar.Server.Athanor.Vault`. When `Memory:Vault:RepoPath` is set (the Vault's main checkout, doc 18; committer from `Memory:Vault:WriterName` and `WriterEmail`), the host registers the workspace id `vault` as that checkout (kind `Vault`; an operator entry with the same id can only make it read-only) and wraps the directory store in `VaultEditorWorkspaceStore`. Reads, containment and symlink rules stay with the directory store. A save is a compare-and-set on the file's revision (a stale base answers a conflict with the server copy), then the edit goes the Vault write path: a unique `athanor/edit-*` branch in its own worktree (`Bazaar:Athanor:VaultWorktreeRoot`, default `<RepoPath>.athanor-worktrees`) holds one commit, and `IVaultWriter.SubmitAsync` merges it under the Vault lane with the `Bazaar-Agent: athanor` and `Bazaar-Edit-Base` trailers, the frozen-decision check and the indexer notification. A merge conflict because the file moved after the check is a conflict reply; a refused merge (frozen decision) is `editor.forbidden`. Only files already tracked in the checkout can be saved (editing never creates files). The wire request carries no person, so the commit author is the Vault writer identity and the person is in the audit row. Known limits: the merged `athanor/edit-*` branches are not deleted yet (`IGitProvider` has no branch delete; a Vault follow-up), and the owner-only and per-area read rules of doc 18 (`VaultAccess`) are not applied to editor reads yet (the editor is owner and human only, behind `read` and `vault.write`).

## 7. Key model (PROPOSED details)

Monaco gets raw key events. Athanor's `IEditorKeyHandoff` maps a key event to the client key router first: if the router claims the key (a mnemonic, the command bar, a pane switch), Monaco never sees it. Vim-style editing inside the editor is Monaco's own keymap layer configured to match the client Vim reference (doc 41 §4.12); the exact set of exceptions is documented in the module README and in doc 49 when S12 resolves focus handoff. No Ctrl chords are added.

**Claimed-key table (PROPOSED, 2026-11-22).** The table the host pushes with `setClaimedKeys` is derived from the client key router, not written by hand. While the editor has focus the router is in Insert mode (the editor is a text input), so the table is the set of keys a router in Insert mode would not pass through. `RouterClaimedKeySource` (in `Bazaar.Client.Athanor`, over the pure `Bazaar.Client.Input` library) probes every candidate chord (letters, digits, Space, the named keys of the router, F1 to F12, each with every combination of Shift, Alt and Meta) against a fresh `KeyRouter` built from the head's `MnemonicTable`; a candidate the router does not pass through is claimed. With today's router that is `Escape` and `Shift+Escape` (leave Insert); a table change (a remap) is pushed by calling `Refresh()`, which raises `Changed` only when the set differs. **No Ctrl chord is ever a candidate**, so none is ever claimed, and `BridgeEditorHost.SafeChords` stays as the second line of defence. Operators may exclude chords (`excluded` argument, fed from a setting) so that, for example, Monaco keeps `Escape` for its find widget; excluded chords are neither pushed nor claimed. **Key names:** the page reports `KeyboardEvent.code` (`KeyM`, `Digit1`, `Escape`, `Enter`, `ArrowUp`), `AvaloniaEditHost` reports Avalonia `Key` names (`M`, `D1`, `Escape`, `Return`, `Up`). `EditorKeyCodes` is the one place that converts: it accepts either scheme, yields the code form for chords, and yields the router's `KeyStroke` (shifted printable character or `NamedKey`). A key that maps to no stroke (punctuation, unknown names) is never claimed. `RouterKeyHandoff.ForStrokes` builds the handoff from the same probe, so the table and the per-key decision cannot disagree.

## 8. Palette commands and navigation

Registered through the module manifest (doc 41 §8): `athanor.open`, `athanor.new`, `athanor.save`, `athanor.diff`. The syntax-first grammar (doc 41 §4.12) gets the code `ed` (editor), per-company configurable. Registration is a manifest declaration, not an edit to Client.Core.

**Command contributions and save path (PROPOSED, 2026-11-22).** The module contributes each command with a default mnemonic through `ClientModuleBuilder.AddCommand(ClientCommandContribution)`, all under the code `ed`: `athanor.open` (`edopen`), `athanor.new` (`ednew`), `athanor.save` (`edsave`), `athanor.diff` (`eddiff`). They are defaults; the company and the person can re-code them (doc 41 §5). None is a Ctrl chord, and **Ctrl+S is never claimed**: a save from the keyboard is the mnemonic `edsave` then Enter, in Normal mode. `AthanorCommandHandler` executes a command id for the pane; the head forwards `MnemonicHost.CommandInvoked` to it (`Handles(id)` says whether the id is Athanor's).
- `athanor.save` saves the active document through the pane and the `SaveCoordinator` (revision check, conflict, draft kept). It works for every host: hosts that raise `SaveRequested` (the AvaloniaEdit host through `RequestSave()`, the bridge host through `BridgeEditorHost.RequestSave(id)` and so the WebView2 host) reach the same coordinator through the pane's `SaveRequested` subscription. The bridge host raises the event itself for an open document; the page is not asked, because the page has no Ctrl-free save key.
- `athanor.open` asks `IEditorCommandPrompts.PickDocumentAsync` (a head-supplied path picker) and opens the result. `athanor.new` asks `PickNewDocumentAsync`; the server creates no files (§6), so until a create message is accepted it opens the chosen path only when it exists, and otherwise reports "not found". With no prompts supplied both report unavailable.
- `athanor.diff` shows the active document's current text against the server copy (read again through the file source) in the host's diff component, language by `DiffSession`.
- A handler result is `AthanorCommandResult`: `Done`, `NothingToDo` (no active document, user cancelled the picker), `Unavailable` (no prompts, no host) or `Failed` (with a reason). The shell shows the reason in the notice area.
